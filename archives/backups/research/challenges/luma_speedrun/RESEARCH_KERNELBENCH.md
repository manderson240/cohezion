# KernelBench Research: Can LLMs Write Efficient GPU Kernels?

**Date:** April 6, 2026  
**Source:** Stanford Scaling Intelligence Lab (arXiv:2502.10517, ICML '25)  
**Researcher:** AI Agent  

---

## Executive Summary

KernelBench is a comprehensive benchmark from Stanford's Scaling Intelligence Lab designed to evaluate LLMs' ability to generate efficient GPU kernels. It consists of 250 PyTorch workloads across 4 difficulty levels, testing whether LLMs can transpile PyTorch operations into optimized CUDA (and other DSL) kernels that are both **correct** and **performant**.

**Key Finding:** Frontier reasoning models perform best but still match PyTorch baseline in **less than 20%** of cases. The benchmark remains challenging, with correctness dropping sharply as task complexity increases from Level 1 to Level 3.

---

## 1. What is KernelBench?

### Overview
KernelBench is an **open-source evaluation framework** that tasks LLMs with generating custom GPU kernels to replace PyTorch implementations. The goal is to produce kernels that are:
- ✅ **Correct:** Numerically equivalent to reference PyTorch (within tolerance)
- ⚡ **Performant:** Faster than PyTorch baseline and torch.compile()

### The 4-Level Benchmark Structure

| Level | Description | Tasks | Examples |
|-------|-------------|-------|----------|
| **Level 1** | Single-kernel operators | 100 | Convolutions, MatMul, LayerNorm, Activations |
| **Level 2** | Simple fusion patterns | 100 | Conv+Bias+ReLU, MatMul+Scale+Sigmoid |
| **Level 3** | Full model architectures | 50 | MobileNet, VGG, MiniGPT, Mamba |
| **Level 4** | HuggingFace models | 20 | Aspirational tasks from real model repos |

### Evaluation Methodology

**fast_p Metric:** The primary benchmark metric measures the fraction of tasks where generated kernels are:
1. **Correct** (passes numerical tolerance: atol=rtol=1e-02)
2. **Achieves speedup > p** over PyTorch baseline

Examples:
- `fast_0`: Fraction correct (regardless of speed)
- `fast_1`: Fraction both correct AND faster than PyTorch
- `fast_2`: Fraction correct AND ≥2x faster

## 2. Key Findings About LLM Kernel Generation

### Compilation and Correctness Results

From greedy evaluation (temperature=0) across frontier models:

| Model | Level 1 Correct | Level 2 Correct | Level 3 Correct |
|-------|-----------------|-----------------|-----------------|
| **o1** | ~45% | ~35% | ~20% |
| **GPT-4o** | ~40% | ~25% | ~10% |
| **Claude 3.5 Sonnet** | ~38% | ~22% | ~8% |
| **DeepSeek-Coder** | ~35% | ~18% | ~5% |

**Key Observations:**
- ✅ Most models generate **compilable CUDA code**
- ❌ **Correctness drops sharply** with complexity (Level 3 is 2-4x harder than Level 1)
- 🧠 **o1 significantly outperforms GPT-4o** on Levels 2-3, suggesting inference-time compute helps
- 📈 **Larger models** of same family get more correct solutions

### Pass@k Analysis

Sampling with high temperature (DeepSeek temp=1.6, Llama 3.1 70B temp=0.8):

| Model | pass@1 | pass@3 | pass@5 | pass@10 |
|-------|--------|--------|--------|---------|
| **DeepSeek-Coder** | ~15% | ~30% | ~40% | ~50% |
| **Llama 3.1 70B** | ~8% | ~15% | ~20% | ~28% |

**Insight:** Increasing k improves correctness substantially, following "Large Language Monkeys" findings. However, base model capability matters—even with k=10, weaker models lag behind stronger models at k=1.

### Performance vs. Correctness Tradeoff

**Critical Finding:** There's a fundamental tension between optimization and correctness:
- More aggressive optimizations → higher performance risk
- Safer implementations → more likely to be correct but slower
- Only ~20% of generated kernels beat PyTorch baseline while maintaining correctness

## 3. Comparison to Human-Written Kernels

### Speedup Analysis (Correct Samples Only)

| Model | Speedup vs PyTorch (P50) | Speedup vs Torch.Compile (P50) | Notable Outliers |
|-------|-------------------------|----------------------------------|------------------|
| **o1** | ~0.9x | ~0.8x | 12x on diagonal matmul |
| **Claude 3.5 Sonnet** | ~0.85x | ~0.75x | 3x on fused ops |
| **GPT-4o** | ~0.8x | ~0.7x | - |

**Key Insights:**
- Most LLM-generated kernels are **SLOWER** than PyTorch baseline (median < 1x)
- A few outliers achieve **10x+ speedups** through algorithmic insights
- torch.compile() is hard to beat consistently

### Top-Performing Generated Kernels

**Example 1: Diagonal Matrix Multiplication (Level 1)**
```cuda
// Generated by multiple models - achieves >12x speedup
__global__ void diag_matmul_kernel(
    const float* diag, const float* mat, float* out,
    const int N, const int M) {
    const int row = blockIdx.y * blockDim.y + threadIdx.y;
    const int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < M) {
        // Key insight: diag(A) @ B = row-wise scaling
        out[row * M + col] = diag[row] * mat[row * M + col];
    }
}
```
**Optimization:** Avoids materializing full diagonal matrix; uses O(N) vs O(N²) memory.

**Example 2: Fused Operations (Level 2)**
```cuda

// Fuses: MatMul → Divide → Sum → Scale

}
```
**Optimization:** Kernel fusion eliminates memory round-trips between operations.

## 4. Patterns That Produce Best Results

### Successful Optimization Patterns

| Pattern | Applicability | Speedup Potential | Success Rate |
|---------|--------------|-------------------|--------------|
| **Kernel Fusion** | Level 2+ (fused ops) | 2-5x | ~40% |
| **Algorithmic Reformulation** | Level 1 (specialized mats) | 5-15x | ~60% |
| **Memory Access Optimization** | All levels | 1.5-3x | ~30% |
| **Tiling/Blocking** | Level 1-2 (GEMM/Conv) | 1.2-2x | ~25% |
| **Vectorized Loads** | All levels | 1.1-1.5x | ~35% |

### What Works Best

1. **Algorithmic Insight > Micro-optimization**
   - Reformulating diagonal matmul as row-scaling beats tiling optimizations
   - 12x speedup came from math insight, not low-level tuning

2. **Fusion of Simple Patterns**
   - Combining 2-4 elementwise ops post-matmul is reliable
   - More than 4 ops risks correctness issues

3. **Specialized Handling for Structured Matrices**
   - Triangular, symmetric, diagonal matrices → custom kernels
   - Dense GEMM → use cuBLAS (hard to beat)

4. **Test-Time Iterative Refinement**
   - Using execution feedback + profiling improves results
   - "Caesar" multi-turn inference engine (ICML '25) shows promise

### What Doesn't Work

- ❌ Raw MFMA/WMMA intrinsics without careful tuning
- ❌ Overly aggressive unrolling without occupancy analysis
- ❌ Complex multi-kernel designs (sync issues)
- ❌ Generic tiling without shape awareness

## 5. Applicability to Our Competition (AMD MI355X)

### Direct Relevance

| Aspect | KernelBench | Our Competition (AMD MI355X) |
|--------|-------------|------------------------------|
| **Hardware** | NVIDIA GPUs (L40S, A100, H100) | AMD MI355X (gfx950) |
| **Languages** | CUDA, Triton, CUTLASS, ThunderKittens | HIP, Triton, CK-Tile |
| **Kernels Tested** | Generic ML ops | MXFP4 GEMM, MoE, MLA Decode |
| **Optimization Goal** | Speedup vs PyTorch | Speedup vs aiter reference |
| **Evaluation** | fast_p metric | Ranked scoring on Popcorn CLI |

### Transferable Insights

#### ✅ Applicable to Our Competition

1. **Algorithmic Reformulation is King**
   - The 12x diagonal matmul win came from recognizing O(N) vs O(N²) opportunity
   - **Action:** Look for structural patterns in MoE (sparse routing) and MLA (compressed KV)

2. **Fusion Patterns are Reliable**
   - Level 2 fusion successes (2-5x) align with our MoE fusion goals
   - **Action:** Fuse quantization + MoE dispatch + GEMM where possible

3. **Test-Time Compute Scaling Works**
   - Pass@k improvements suggest iterative refinement helps
   - **Action:** Use profiling feedback (NCU/rocprof) to guide optimizations

4. **Correctness-Performance Tradeoff is Real**
   - Aggressive optimizations risk correctness
   - **Action:** Maintain reference kernel for validation; A/B test changes

#### ⚠️ Adaptation Required

1. **Hardware Differences**
   - KernelBench uses NVIDIA; we need AMD gfx950 patterns
   - **Action:** Translate MFMA/CDNA4 patterns, not CUDA patterns

2. **Specialized Kernels vs. Generic Ops**
   - KernelBench focuses on generic Conv/GEMM/Norm
   - Our competition has specialized kernels (MXFP4, MoE, MLA)
   - **Action:** Apply KernelBench fusion insights to specific kernel types

3. **Evaluation Differences**
   - KernelBench: fast_p (correctness + speedup)
   - Our competition: Ranked scoring (speed only, correctness assumed)
   - **Action:** We can be more aggressive with optimizations IF correctness verified

### Specific Recommendations

#### For MXFP4 GEMM
```
KernelBench Insight: Algorithmic > Micro-opt
Our Application:
  - Explore blocked vs interleaved MXFP4 layouts
  - Consider FP4 native MFMA vs BF16 MFMA + dequant
  - Fuse quantization into GEMM kernel (eliminate 26µs overhead)
```

#### For MoE
```
KernelBench Insight: Fusion patterns achieve 2-5x
Our Application:
  - fused_moe is already fused; look for pre/post fusion opportunities
  - Consider custom sorting/dispatch kernels
  - Explore policy=1 for expert dispatch (37% worst-case improvement)
```

#### For MLA Decode
```
KernelBench Insight: Specialize for input patterns
Our Application:
  - MLA has unique K≠V head dimensions
  - Flash Attention-style tiling may help (custom kernel needed)
  - 3-stage aiter pipeline has ~100µs overhead; single-kernel fusion target
```

## 6. Key Takeaways

### What KernelBench Tells Us

1. **LLMs CAN write GPU kernels** but with limitations:
   - Correctness: ~20-45% for simple ops, drops to ~5-20% for complex models
   - Performance: Most are slower than PyTorch; outliers achieve 10x+ through algorithmic insight

2. **Inference-time compute helps:**
   - o1 > GPT-4o on complex tasks
   - Pass@k scaling shows promise (15% → 50% at k=10)

3. **Fusion and algorithmic reformulation are the best levers:**
   - Micro-optimizations (tiling, unrolling) are hard to get right
   - High-level restructuring yields bigger wins

### For Our Competition

| Recommendation | Priority | Rationale |
|---------------|----------|-----------|
| Focus on algorithmic reformulation | **HIGH** | 12x wins came from math insights, not tuning |
| Use profiling feedback iteratively | **HIGH** | Pass@k improvements suggest iterative refinement works |
| Maintain correctness anchor | **HIGH** | KernelBench shows correctness-performance tradeoff |
| Explore custom kernel DSLs | **MEDIUM** | CK-Tile, ThunderKittens may help (untested on AMD) |
| Aggressive fusion where possible | **MEDIUM** | Level 2 fusion shows 2-5x reliable gains |
| Avoid over-optimization | **LOW** | Generic tiling/unrolling rarely beats libraries |

# Luma AMD Speedrun: Phase 12 — hiprtc + Local Model Delegation

## Context

Phases 1–11 exhausted all Python-level API paths. The bottleneck is **Python dispatch
overhead (~130µs)** — the leader at 4.3µs MUST bypass Python entirely.

| Kernel | Our Time | Leader | Gap | Bottleneck |
|--------|----------|--------|-----|------------|
| MLA | ~70 µs | 4.3 µs | 16x | Python dispatch + aiter pipeline |
| GEMM | ~23 µs | 9.7 µs | 2.4x | Two-kernel pipeline (quant + GEMM) |
| MoE | ~155 µs | 145 µs | 1.07x | Near API ceiling |

**Token budget constraint:** ~50% of weekly Claude Code budget used in 2 days.
Claude must act as **architect + reviewer + submitter only**. All heavy-lifting
(kernel drafting, iteration, debugging) delegated to local finetuned models.

## Architecture: Claude as Orchestrator

```
Claude Code (architect)
  │
  ├─ Designs kernel specs (HIP C++ structure, MFMA patterns, memory layout)
  ├─ Writes structured prompts for local model
  ├─ Reviews local model output (correctness check)
  ├─ Submits via popcorn-cli
  │
  ▼
Local Finetuned Model (kernel engineer) — runs on Strix Halo (128GB RAM)
  │
  ├─ Drafts HIP C++ kernel source from spec
  ├─ Iterates on correctness (compile errors, numeric issues)
  ├─ Generates submission.py variants
  └─ Runs via Ollama API or cohezion compound system
```

**Token savings:** ~10x reduction in Claude usage. Claude writes ~500 tokens of spec,
local model generates ~2000 tokens of kernel code. Claude reviews ~200 tokens.
vs current: Claude generates entire kernel (~3000+ tokens per iteration).

# Luma AMD Speedrun: Phase 9 — Team-Parallel Kernel Optimization

## Context

**Phase 8 is complete.** Three kernels are on the leaderboard. Significant gaps remain.

| Kernel | Our Time | Leader | Gap | Current Approach | Bottleneck |
|--------|----------|--------|-----|-----------------|------------|
| MLA | ~129 µs | 4.3 µs | **30x** | FlashDecoding + hybrid routing (threshold=100k) | VGPR pressure (kv1[64,512]=256 VGPRs); bf16 bandwidth |
| GEMM | ~20.6 µs | 9.7 µs | **2.1x** | `gemm_afp4wfp4` (Triton) | API ceiling; gemm_a4w4 blocked by callsite sensitivity |
| MoE | ~155 µs | 145 µs | **1.07x** | Adaptive KSPLIT routing | API ceiling |

**Phase 8 key learnings** (skills: `gfx950-vgpr-pressure-triton-mla`, `amd-triton-jit-callsite-correctness`):
1. VGPR pressure from KV tile, not accumulator — BLOCK_M tiling didn't help
2. BLOCK_M tiling increases KV bandwidth (nq/BLOCK_M independent KV loads)
3. ref_kernel has ~130 µs fixed overhead (metadata + JIT dispatch)
4. gemm_a4w4 HIP ASM produces ~1-3% different results from submission.py callsite
5. For shapes under 100k tokens, kernel launch + Python overhead dominate

**Why a team approach:** Phase 8 was sequential — one agent doing MLA, then GEMM, then MoE.
The three kernels are independent (different files, leaderboards, and optimization strategies).
A team can parallelize research and code writing while the lead handles sequential submissions.

- Each kernel's research is highly specialized (MLA: attention algorithms; GEMM: quantized matmul)
- A generalist researcher would duplicate context that kernel-specific agents already need

## Task Details

### Task 1: MLA — FP8 Score GEMM (mla-dev)

**Why:** bf16 tl.dot uses half the MFMA throughput of fp8. For compute-bound shapes (bs≤32),
fp8 scoring gives ~1.5-2x speedup. The input already provides `kv_data["fp8"]`.

**Approach:**
1. Read `reference.py:quantize_fp8()` for Q quantization pattern
2. Inside `_mla_flash_decode` kernel: load fp8 Q + fp8 KV tiles
3. `qk = tl.dot(q1_fp8, tl.trans(kv1_fp8))` with fp32 accumulator
4. Apply `q_scale * kv_scale * SM_SCALE` after the dot product
5. Keep value accumulation in bf16 initially (Task 2 upgrades this)

**Constraint:** `tl.dot` with fp8 requires BLOCK_M ≥ 16 and BLOCK_N ≥ 16 on gfx950.
Current BLOCK_M=16, BLOCK_N=64 — both satisfy this.

### Task 2: MLA — FP8 Value Path (mla-dev)

**Why:** For bandwidth-bound shapes (bs=256, kv=8k), KV bandwidth dominates at ~288 µs (bf16).
FP8 KV halves this to ~144 µs. Using fp8 for BOTH score AND value means only ONE KV load.

**Approach:**
1. Load fp8 KV once per tile (instead of bf16 KV for values)
2. Score: `tl.dot(q_fp8, tl.trans(kv_fp8))` — already done in Task 1
3. Value: `tl.dot(p.to(fp8), kv1_fp8)` — accumulate in fp32, scale at end
4. Final output: `acc * kv_scale` → bf16

**Risk:** FP8 value accumulation may exceed rtol=1e-2 tolerance. Mitigation: if fp8 value
fails correctness, keep bf16 value path and only use fp8 for score (Task 1 alone).

### Task 3: MLA — BLOCK_N Tuning (mla-dev)

**Why:** The real VGPR bottleneck is `kv1[BLOCK_N, 512]`. At BLOCK_N=64: ~256 VGPRs (saturates budget).
At BLOCK_N=32: ~128 VGPRs (fits with accumulator). Smaller BLOCK_N trades tile efficiency for
register pressure — may eliminate spilling and improve throughput.

**Approach:**
1. Parameterize BLOCK_N as a tunable constexpr
2. Test BLOCK_N ∈ {32, 64, 128} via benchmark
3. Smaller BLOCK_N = more loop iterations but less spilling
4. Larger BLOCK_N = fewer iterations but more register pressure

### Task 4: MLA — Threshold Sweep (mla-dev)

**Why:** Current threshold=100k was set empirically in Phase 8. With fp8 and BLOCK_N changes,
the optimal threshold shifts. Need to re-benchmark.

**Approach:** After Tasks 1-3, benchmark all shapes with FlashDecoding forced on vs ref_kernel.
Set threshold at the crossover point.

### Task 5: GEMM — Fix Fused Kernel (gemm-dev)

**Why:** `submission_tritonblas_fused.py` has the Origami XCD remapping bug (non-bijective for
`total_tiles % 8 != 0`). Fixing this with group-M swizzle could unlock the fused kernel path,
eliminating ~10 µs of quant + launch overhead.

**Approach:**
1. Copy `submission_tritonblas_fused.py` → working copy
2. Replace Origami XCD block with group-M swizzle (see `tritonblas-origami-xcd-remapping-bug` skill)
3. Test correctness across all 5 GEMM shapes
4. If passes: benchmark and compare against 20.6 µs baseline

### Task 6: GEMM — CUDA Graph Wrapping (gemm-dev)

**Why:** Our ~10 µs overhead per shape = A quant launch + GEMM launch + allocation.
CUDA graphs capture the entire sequence and replay with ~2-3 µs overhead.

**Approach:**
1. Wrap `dynamic_mxfp4_quant` + `gemm_afp4wfp4` in a CUDA graph
2. Use `torch.cuda.CUDAGraph()` with warmup + capture + replay
3. Challenge: dynamic shapes require separate graphs per shape (5 shapes = 5 graphs)
4. Pre-warm all 5 during first invocation

**Risk:** CUDA graph capture may not work with aiter's Triton kernels (JIT compilation
happens at capture time, not replay). Test empirically.

### Task 7: GEMM — Explore CK Direct GEMM (gemm-dev)

**Why:** If neither fused kernel nor CUDA graphs work, explore Composable Kernel (CK)
for a direct fp4 GEMM path that bypasses both aiter and Triton overhead.

**Approach:**
1. Check if `ck` or `composable_kernel` is importable on MI355X runner
2. Search for fp4/mxfp4 GEMM kernels in CK Python bindings
3. If found: write a minimal submission using CK directly

# Brainstorming Ideas Into Designs

Help turn ideas into fully formed designs and specs through natural collaborative dialogue.

Start by understanding the current project context, then ask questions one at a time to refine the idea. Once you understand what you're building, present the design and get user approval.

<HARD-GATE>
Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it. This applies to EVERY project regardless of perceived simplicity.
</HARD-GATE>

## Anti-Pattern: "This Is Too Simple To Need A Design"

Every project goes through this process. A todo list, a single-function utility, a config change — all of them. "Simple" projects are where unexamined assumptions cause the most wasted work. The design can be short (a few sentences for truly simple projects), but you MUST present it and get approval.

## Checklist

You MUST create a task for each of these items and complete them in order:

1. **Explore project context** — check files, docs, recent commits
2. **Offer visual companion** (if topic will involve visual questions) — this is its own message, not combined with a clarifying question. See the Visual Companion section below.
3. **Ask clarifying questions** — one at a time, understand purpose/constraints/success criteria
4. **Propose 2-3 approaches** — with trade-offs and your recommendation
5. **Present design** — in sections scaled to their complexity, get user approval after each section
6. **Write design doc** — save to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and commit
7. **Spec review loop** — dispatch spec-document-reviewer subagent with precisely crafted review context (never your session history); fix issues and re-dispatch until approved (max 5 iterations, then surface to human)
8. **User reviews written spec** — ask user to review the spec file before proceeding
9. **Transition to implementation** — invoke writing-plans skill to create implementation plan

## The Process

**Understanding the idea:**

- Check out the current project state first (files, docs, recent commits)
- Before asking detailed questions, assess scope: if the request describes multiple independent subsystems (e.g., "build a platform with chat, file storage, billing, and analytics"), flag this immediately. Don't spend questions refining details of a project that needs to be decomposed first.
- If the project is too large for a single spec, help the user decompose into sub-projects: what are the independent pieces, how do they relate, what order should they be built? Then brainstorm the first sub-project through the normal design flow. Each sub-project gets its own spec → plan → implementation cycle.
- For appropriately-scoped projects, ask questions one at a time to refine the idea
- Prefer multiple choice questions when possible, but open-ended is fine too
- Only one question per message - if a topic needs more exploration, break it into multiple questions
- Focus on understanding: purpose, constraints, success criteria

**Exploring approaches:**

- Propose 2-3 different approaches with trade-offs
- Present options conversationally with your recommendation and reasoning
- Lead with your recommended option and explain why

**Presenting the design:**

- Once you believe you understand what you're building, present the design
- Scale each section to its complexity: a few sentences if straightforward, up to 200-300 words if nuanced
- Ask after each section whether it looks right so far
- Cover: architecture, components, data flow, error handling, testing
- Be ready to go back and clarify if something doesn't make sense

**Design for isolation and clarity:**

- Break the system into smaller units that each have one clear purpose, communicate through well-defined interfaces, and can be understood and tested independently
- For each unit, you should be able to answer: what does it do, how do you use it, and what does it depend on?
- Can someone understand what a unit does without reading its internals? Can you change the internals without breaking consumers? If not, the boundaries need work.
- Smaller, well-bounded units are also easier for you to work with - you reason better about code you can hold in context at once, and your edits are more reliable when files are focused. When a file grows large, that's often a signal that it's doing too much.

**Working in existing codebases:**

- Explore the current structure before proposing changes. Follow existing patterns.
- Where existing code has problems that affect the work (e.g., a file that's grown too large, unclear boundaries, tangled responsibilities), include targeted improvements as part of the design - the way a good developer improves code they're working in.
- Don't propose unrelated refactoring. Stay focused on what serves the current goal.

## After the Design

**Documentation:**

- Write the validated design (spec) to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
  - (User preferences for spec location override this default)
- Use elements-of-style:writing-clearly-and-concisely skill if available
- Commit the design document to git

**Spec Review Loop:**
After writing the spec document:

1. Dispatch spec-document-reviewer subagent (see spec-document-reviewer-prompt.md)
2. If Issues Found: fix, re-dispatch, repeat until Approved
3. If loop exceeds 5 iterations, surface to human for guidance

**User Review Gate:**
After the spec review loop passes, ask the user to review the written spec before proceeding:

> "Spec written and committed to `<path>`. Please review it and let me know if you want to make any changes before we start writing out the implementation plan."

Wait for the user's response. If they request changes, make them and re-run the spec review loop. Only proceed once the user approves.

**Implementation:**

- Invoke the writing-plans skill to create a detailed implementation plan
- Do NOT invoke any other skill. writing-plans is the next step.

## Key Principles

- **One question at a time** - Don't overwhelm with multiple questions
- **Multiple choice preferred** - Easier to answer than open-ended when possible
- **YAGNI ruthlessly** - Remove unnecessary features from all designs
- **Explore alternatives** - Always propose 2-3 approaches before settling
- **Incremental validation** - Present design, get approval before moving on
- **Be flexible** - Go back and clarify when something doesn't make sense

## Visual Companion

A browser-based companion for showing mockups, diagrams, and visual options during brainstorming. Available as a tool — not a mode. Accepting the companion means it's available for questions that benefit from visual treatment; it does NOT mean every question goes through the browser.

**Offering the companion:** When you anticipate that upcoming questions will involve visual content (mockups, layouts, diagrams), offer it once for consent:

- **Use the browser** for content that IS visual — mockups, wireframes, layout comparisons, architecture diagrams, side-by-side visual designs

A question about a UI topic is not automatically a visual question. "What does personality mean in this context?" is a conceptual question — use the terminal. "Which wizard layout works better?" is a visual question — use the browser.

# Competitive Kernel Optimization: Beyond Parameter Tuning

## Problem

After exhausting all tunable parameters in a library (e.g., aiter's `fused_moe`), ranking
stays in the lower half of the leaderboard. The reference implementation is already
well-optimized; parameter sweeps either have no effect, cause correctness failures, or
degrade performance.

## Context: When to Use This

- All accessible API parameters have been tested (documented in `aiter-kernel-parameter-semantics`)
- Still ranked outside top 20 with >2x gap to leader
- Considering whether to abandon vs. continue the challenge
- Wanting to plan next iteration with higher expected value

## The Decision Hierarchy

### Level 1: Local Proxy (Low effort, immediate)

Before expensive remote submissions, build a local model of the performance space:

**Parse aiter's tuned CSV configs:**
```bash
cat /path/to/aiter/aiter/configs/tuned_fmoe.csv
cat /path/to/aiter/aiter/configs/model_configs/dsv3_fp4_tuned_fmoe.csv
```

These CSVs contain: `(n_experts, batch_size, d_hidden, d_expert, topk, block_m, ...)` → `(kernel_name, cycles)`.
Reading them reveals:
- Which tile configs the auto-tuner selects for which shapes
- Whether there are shape-specific configs that differ from the defaults
- Whether your benchmark shapes have dedicated tuned entries or fall back to defaults

**Roofline model estimate:**
```python
# For MXFP4 GEMM: theoretical peak = GPU_TFLOPS * efficiency
# Compare against actual timing to determine if compute-bound or memory-bound
bytes_per_token = d_hidden * sizeof(fp4)  # input
bytes_weights = d_expert * d_hidden * sizeof(fp4)  # per expert, per token
arithmetic_intensity = 2 * d_hidden * d_expert / bytes_weights  # FLOPs/byte
```

### Level 2: The "Two Builders" Pattern (Medium effort)

From the Anthropic VLIW take-home challenge (see `research/challenges/anthropic_challenge/`):

The winning approach used two separate kernel builders:
- **Builder A (Correctness Anchor):** Delegates to `ref_kernel` or matches reference exactly.
  Never changes. Used to verify correctness of Builder B.
- **Builder B (Custom Explorer):** Reimplements the same computation differently.
  Can be tested against Builder A as ground truth.

For AMD MoE, this means writing a **custom dispatch + GEMM pipeline** that:
1. Uses the same shuffled weights and scales (pre-computed by aiter)
2. Implements its own token sorting (potentially simpler than aiter's)
3. Calls CK GEMM kernels directly instead of through `fused_moe`

```python
# Template: Two Builders pattern for AMD kernel submission
from reference import ref_kernel  # Builder A: correctness anchor

def custom_kernel(data: input_t) -> output_t:
    # Try Builder B; fall back to Builder A on any exception
    try:
        return custom_builder(data)
    except Exception:
        return ref_kernel(data)  # Safety net during development
```

### Level 3: Custom HIP/ASM Kernel (High effort, highest impact)

What top leaderboard entries do:
- Write kernel in HIP C++ or assembly, compiled with `hipcc`
- Bypass the aiter library entirely for the hot path
- Use hardware-specific optimizations (e.g., MI355X matrix core layouts, gfx950 ISA)
- Typically requires familiarity with ROCm programming model

This is only worth pursuing if:
- You have HIP/CUDA experience
- The competition has days remaining (not hours)
- The performance gap justifies the implementation risk

## VLIW Cross-Pollination: Applicable Lessons

The Anthropic VLIW take-home (`research/challenges/anthropic_challenge/`) shares structural
parallels with AMD GPU kernel challenges:

| VLIW Concept | AMD Kernel Analog |
|---|---|
| Instruction slots (alu, valu, load) | GPU execution units (VALU, SALU, memory) |
| `VLIWPacker` data-dependency tracking | aiter's 2-stage pipeline dependency between gate+up GEMM and down GEMM |
| "Temporal Instruction Leakage" across barriers | `doweight_stage1=True` leaking weight mul across the SiLU activation barrier |
| N_VEC=28 window interleaving for latency hiding | `num_kv_splits` in MLA for hiding KV cache memory latency |
| `multiply_add` fusion optimization | CK `moe_ck2stages_gemm1_*MulABScaleShuffled*` kernel name encodes similar fusion |
| Local simulator (instant feedback) | Popcorn CLI remote (~2-10 min/iteration) |

**Key VLIW insight transferable to AMD:**
The VLIW challenge was NOT won by parameter tuning the packer. It was won by:
1. Understanding how the scheduler works internally (`last_write`, `last_read` tracking)
2. Discovering that barriers needed explicit data-dependency injection
3. Building a custom kernel generator that produced different instruction schedules

Equivalent for AMD: understand how aiter selects kernels (`get_2stage_cfgs()` in `fused_moe.py`),
what the tile configs mean, and build something that uses them differently.

## Iteration Budget Management

With ~2 min test + ~8-10 min benchmark per remote submission (Luma AMD Speedrun):

## Phase 4: GEMM Correctness Breakthrough (March 2026)

**Root cause was NOT "JIT callsite sensitivity" — it was an UNPATCHED QUANTIZATION BUG.**

`get_triton_quant(QuantType.per_1x32)` dispatches to the unpatched `fp4_utils.py` kernel
(ROCm/aiter issue #974). The fix is `dynamic_mxfp4_quant` from `aiter.ops.triton.quant`
(PR #975 patched this path). See `amd-triton-jit-callsite-correctness` v1.4.0 for details.

| Kernel | Approach | Outcome | Key Insight |
|--------|----------|---------|-------------|
| GEMM | `dynamic_mxfp4_quant` + `gemm_a4w4` | ✅ 0.0 error, ~24.1 µs | Patched Triton quant bypasses buggy dispatch |
| GEMM | `gemm_a4w4` with `log2_k_split=N` | ❌ RuntimeError | Torch op schema is fixed — no `log2_k_split` kwarg |
| GEMM | `gemm_a4w4_asm` direct call | ❌ Kernel name not found | Only 2 pre-compiled `.co` files; name selection is internal |
| GEMM | CUDA/HIP graph replay | ❌ ~36 µs (+50% overhead) | `copy_()` for 3 static input tensors exceeds kernel time |

**GEMM performance ceiling:** ~24.1 µs vs leader's 9.7 µs (2.49x gap).

## Phase 5: MLA Pipeline Bypass (March 2026)

**Key insight: aiter's 3-stage MLA pipeline has fixed overhead that dominates for small batches.**

aiter's `mla_decode_fwd` runs: metadata computation → split-K ASM kernel → parallel reduce.
This pipeline is optimized for large workloads but has ~100-150 µs of constant overhead
regardless of batch size. For small batches (bs=4), the actual compute is tiny — the
overhead is the bottleneck.

**Approach:** Bypass the pipeline entirely with `torch.einsum` for small decode workloads:

```python
# Torch-native: Q@K^T + softmax + @V, all bf16
kv = kv_data["bf16"].view(bs, kvseqlen, 576)
scores = torch.einsum("bnh,bsh->bns", q, kv) * SM_SCALE
weights = torch.softmax(scores, dim=-1)
out = torch.einsum("bns,bsd->bnd", weights, v)
```

**Hybrid routing strategy (optimal):**
- `bs * kvseqlen <= 400_000` tokens: torch-native (pipeline overhead > compute)
- `bs * kvseqlen > 400_000` tokens: ref_kernel/aiter fp8 ASM (bandwidth-bound, fp8 wins)

**Results (all qseqlen=1, fp8 reference tolerance rtol=2e-2, atol=8e-3):**

| Shape | Previous (aiter fp8) | Hybrid | Factor |
|-------|---------------------|--------|--------|
| bs=4, kv=1k | ~150 µs | **27.7 µs** | 5.4x |
| bs=4, kv=8k | ~169 µs | **40.5 µs** | 4.2x |
| bs=32, kv=1k | ~179 µs | **46.2 µs** | 3.9x |
| bs=32, kv=8k | ~206 µs | **171 µs** | 1.2x |
| bs=64, kv=1k | ~175 µs | **64.7 µs** | 2.7x |
| bs=64, kv=8k | ~241 µs | **245 µs** | ~tie |
| bs=256, kv=1k | ~196 µs | **178 µs** | 1.1x |
| bs=256, kv=8k | ~397 µs | **399 µs** | ~tie |
| **Geomean** | ~199 µs | **~100 µs** | **2x** |

**Key learnings:**
- `fav3_sage_mxfp4` (Triton SAGE Attention) can't be used for MLA — requires separate K/V
  with same head_dim; MLA's fused buffer (K=576, V=512) is fundamentally incompatible.
- Correctness with bf16 KV vs fp8 reference: max error 5e-05 (tolerance: 8e-03) — excellent.
- The bottleneck shifts from pipeline overhead to memory bandwidth at ~400k tokens.
- Torch einsum is 2x more bandwidth-hungry than fp8 ASM (bf16 vs fp8 KV cache).

**Ceiling reached:** The hybrid approach exhausts pure-torch improvements.
Further MLA speedups require a custom Triton kernel with MXFP4 KV cache (4x bandwidth
savings vs fp8, requires decomposing the fused KV buffer).

**Conclusion: A standard tiled Triton MXFP4 GEMM cannot outperform aiter's `gemm_afp4wfp4` on MI355X.**

Fully implemented and benchmarked a custom `tl.dot_scaled` kernel with:

**Why the gap persists:** `gemm_afp4wfp4` uses a persistent kernel with split-K (`skip_reduce=True`)
and dozens of per-shape configs from `AITER_TRITON_CONFIGS_PATH`. A standard tiled kernel with
autotune cannot replicate this — the persistent kernel amortizes kernel launch overhead across
the entire problem, while a tiled kernel pays full launch cost per block.

**Key learnings:**
- Confirmed correctness: custom `tl.dot_scaled` with `dynamic_mxfp4_quant` gives 0.0 max error

- `gemm_afp4wfp4` internal API: `skip_reduce=True` returns `[num_splits, M, N]` float32 partial

- **Custom Triton GEMM ceiling:** A fused quant+GEMM persistent Triton kernel remains the only
  realistic path to beating `gemm_afp4wfp4`. The A quantization (~10-13 µs) and GEMM (~7-10 µs)

**Decision:** Restore `gemm_afp4wfp4` submission (20.6 µs geomean, 2.12x gap). Custom kernel
path requires a persistent fused kernel which is a multi-day implementation effort.

### GEMM: The silent graph failure trap

`try/except: pass` around `torch.cuda.graph()` is an optimization anti-pattern:

### MLA: The ~130 µs Triton dispatch floor

The ~130 µs overhead is NOT unique to aiter's 3-stage MLA pipeline. It applies to ANY
Triton kernel dispatched from Python on this problem:
- aiter `mla_decode_fwd` (3-stage): ~130 µs
- Custom Triton FlashDecoding (fp8, BLOCK_N=32): ~130 µs
- torch.einsum (vendor hipBLAS GEMV): **27–46 µs** ← the only way to escape the floor

The overhead is Python-level dispatch + Triton JIT, not the attention algorithm.
Escape requires a single CK/ASM kernel with no Python dispatch overhead.

## Phase 10: Metadata Caching + Graph Capture Definitively Benchmarked (March 2026)

Three independent paths explored. One improved (MLA caching), two confirmed regressions.

|--------|----------|---------|--------------|---------|

### GEMM: ASM Graph Capture Succeeds but Still Regresses

Phase 9 showed gemm_afp4wfp4 (Triton JIT) silently fails graph capture.
Phase 10 confirmed gemm_a4w4 (ASM .co) successfully captures — but +78% regression:

```
m=4:   without=17 µs, with=32 µs (+88%)
m=16:  without=25 µs, with=49 µs (+96%)  ← copy_() dominates
m=256: without=24 µs, with=37 µs (+56%)
```

**Root cause:** Three `copy_()` calls per invocation (A, B_shuffle, B_scale_sh) scale
with tensor size. For A: M×7168 fp16, the copy alone exceeds the 8-34 µs GEMM time.
**Rule:** Data movement IS the bottleneck — not kernel dispatch. Graphs only help if inputs
already reside in static GPU buffers. For MXFP4 GEMM, they never do.

### MoE: Non-Temporal Loads Are Neutral

`AITER_USE_NT=1` bypasses L2 cache for weight reads. Hypothesis: weights aren't reused,
so NT loads avoid polluting L2 with stale data. **Wrong hypothesis:**
CK kernel tiles ARE reused across tokens — multiple tokens map to the same expert block.
L2 reuse IS beneficial for MoE. NT loads remove this benefit but also remove the reload
cost — the effects cancel at ~155 µs. Zero change across all 6 shapes.

### MLA: Metadata Caching Saves 25%

`get_mla_metadata_info_v1` + `get_mla_metadata_v1` allocate and populate 8 work buffer
tensors (`work_meta_data`, `work_indptr`, `work_info_set`, `reduce_indptr`,
`reduce_final_map`, `reduce_partial_map`, `kv_indices`, `kv_last_page_len`) on every call.
These are deterministic for fixed `(bs, qseqlen, kvseqlen)` — safe to cache:

```python
_cache: dict = {}

def _build_cache(bs, qseqlen, kvseqlen, qo_indptr, kv_indptr) -> dict:
    # ... get_mla_metadata_info_v1 + get_mla_metadata_v1 calls ...
    return {"kv_indices": ..., "work_meta_data": ..., ...}  # 8 tensors

key = (bs, qseqlen, kvseqlen)
if key not in _cache:
    _cache[key] = _build_cache(...)
c = _cache[key]
mla_decode_fwd(..., work_meta_data=c["work_meta_data"], ...)
```

Also lowered the einsum↔fp8 threshold from 400k→100k tokens (tighter crossover point).
Combined result: large shapes improved 27-43% while small shapes remained at einsum speed.

```python
    return 32
```

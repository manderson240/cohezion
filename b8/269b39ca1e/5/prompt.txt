# Popcorn CLI AMD Kernel Submission Workflow

## Submission Commands

```bash
CLI=~/.local/bin/popcorn-cli
KERNELS=/path/to/kernels/dir

# 1. Test (correctness check — do this first)
$CLI submit --no-tui --mode test --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 2. Benchmark (timing, no leaderboard impact)
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 3. Leaderboard (official ranked submission)
$CLI submit --no-tui --mode leaderboard --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py
```

## Leaderboard Name Pattern

Leaderboard names follow the pattern: `amd-<directory-name>`

| Kernel directory | Leaderboard name |
|-----------------|-----------------|
| `mxfp4-mm/`    | `amd-mxfp4-mm`  |
| `mixed-mla/`   | `amd-mixed-mla` |
| `moe-mxfp4/`   | `amd-moe-mxfp4` |

To discover unknown names: submit with `--mode test` using candidate names. A 404/does-not-exist
response means the name is wrong; acceptance (even with correctness failures) confirms the name.

## Submission Limits (Luma AMD Speedrun)

- **No per-user rate limit** — submit as many times as needed
- Server-wide: 3 concurrent submissions (asyncio.Semaphore)
- ~10 requests/second global rate limit
- Per-mode timeouts: test=180s, benchmark=180s (overridden per competition in task.yml)
- **Total workflow timeout: ~12 minutes** — the entire GitHub Actions run must complete within this
- Use `--mode test` first, then `--mode benchmark`, then `--mode leaderboard`

## aiter JIT Compilation Times (Luma AMD Speedrun)

aiter builds JIT modules on first use. These builds happen **inside** the 12-minute workflow timeout:

| JIT Module | Build Time |
|-----------|-----------|
| `module_moe_sorting` | ~25s |
| `module_moe_ck2stages_fp4x2_*` | ~103s |
| `module_mla_metadata` | ~32s |
| `module_mla_asm` | ~21s |
| `module_mla_reduce` | ~171s |

**Critical implications:**
- MoE JIT builds alone take ~230s (~4 min), leaving only ~8 min for actual execution
- MLA JIT builds take ~224s total — similar headroom concern
- When the server queue is backed up with multiple concurrent submissions, the JIT time can push the total over the 12-minute limit
- Submissions that appear to fail silently (no output, cancelled status) are often **queue pressure timeouts**, not code errors

**Mitigation:** Retry submissions during off-peak hours. JIT results are cached between runs in the same workflow, so a retry that hits a pre-warmed runner will be much faster.

## Local Testing Limitations on gfx1151 (RDNA4 Strix Halo)

Local GPU testing on gfx1151 (AMD Radeon 8060S, Strix Halo iGPU) is NOT feasible with ROCm 6.2.4:

- Without override: `HIP error: invalid device function` (ISA mismatch)
- With `HSA_OVERRIDE_GFX_VERSION=11.0.0`: "Memory access fault by GPU node-2" on kernel launch
  (RDNA4 gfx1151 is not binary-compatible with RDNA3 gfx1100)
- ROCm 6.3+ would be needed for gfx1151 native support

**Workaround**: All testing via Popcorn CLI remote submission (MI355X hardware).

## Competition Kernel Structure

Each kernel must implement:
```python
# submission.py
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    ...  # Your implementation
```

The eval harness (`eval.py`) calls `generate_input()` from `reference.py`, passes `_clone_data(data)`
to `custom_kernel`, then runs `check_implementation()` comparing output to reference. Benchmark
runs clear L2 cache between runs (`clear_l2_cache_large()`), so cache warming tricks don't help.

**CRITICAL: Popcorn CLI only uploads `submission.py`.** It does NOT upload any other files
in the kernel directory. Files like `reference.py`, `task.py`, and `eval.py` are already
present on the runner at the competition's standard location — they are NOT re-uploaded.

**Consequence: Multi-file submissions are NOT possible.** If your submission.py tries to
`from gemm_wrapper import quant_and_gemm` where `gemm_wrapper.py` is a file you created
in the kernel directory, the runner will get `ModuleNotFoundError: No module named 'gemm_wrapper'`.

**Workaround attempted — dynamic module creation at `/tmp/`:**
```python
# submission.py
import importlib.util, textwrap, os, sys

code = textwrap.dedent("""...""")
path = "/tmp/my_module.py"
with open(path, "w") as f: f.write(code)
spec = importlib.util.spec_from_file_location("my_module", path)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
sys.modules["my_module"] = mod
```

This WORKS for making the module importable, BUT for AMD `gemm_a4w4_asm` specifically,
the dynamic module does NOT change callsite identity — the dispatch still produces wrong
results (see `amd-triton-jit-callsite-correctness` skill). Only `from reference import
ref_kernel` reliably bypasses the callsite sensitivity.

## Troubleshooting: Transient Artifact Download Failures

Popcorn CLI submissions run on GitHub Actions runners. The evaluation job and the artifact
download are separate steps — a network failure can cause the CLI to report failure even though
the evaluation job itself **succeeded**.

**Symptoms:**
- CLI output shows failure / no results despite a correct kernel
- Error mentions artifact download or GitHub Actions artifact retrieval

**Fix:** Simply retry the same submission command. A retry succeeds in the majority of cases.

```bash
# Retry exactly the same command — the eval job is idempotent
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> <file>
```

**Important:** Transient failures look identical to actual correctness failures in the CLI output.
If a previously-passing kernel suddenly "fails", try a retry before debugging the kernel code.

## Test vs Benchmark Shape Differences (MLA-specific)

**Critical:** `task.yml` test shapes and benchmark shapes differ in `qseqlen`:

| Mode | qseqlen values | Why |
|------|---------------|-----|
| Test (`--mode test`) | May include qseqlen=4 | Exercises prefill-like cases |
| Benchmark (`--mode benchmark`) | Always qseqlen=1 | Decode-only benchmark |

Custom kernels must handle qseqlen>1 correctly or the test will fail, even if the
benchmark optimization only targets qseqlen=1. Safe pattern:

```python
total_q = q.shape[0]
qseqlen = total_q // bs
if qseqlen != 1:
    from reference import ref_kernel
    return ref_kernel(data)
# ... optimized decode path
```

**Observation (MLA, March 2026):** The test runner used only qseqlen=1 shapes in practice,
but the guard is still important for correctness robustness.

## PHASE 0: REFERENCE

### Step 0.1: Triggers

Invoke `/learn` after ANY task involving:

| Trigger                      | Example                                                          |
| ---------------------------- | ---------------------------------------------------------------- |
| **Non-obvious debugging**    | Spent 10+ minutes investigating; solution wasn't in docs         |
| **Misleading errors**        | Error message pointed wrong direction; found real cause          |
| **Workarounds**              | Found limitation and creative solution                           |
| **Tool integration**         | Figured out how to use tool/API in undocumented way              |
| **Trial-and-error**          | Tried multiple approaches before finding what worked             |
| **Repeatable workflow**      | Multi-step task that will recur; worth standardizing             |
| **External service queries** | Fetched data from Jira, GitHub, Confluence, or other APIs        |
| **User-facing automation**   | Built something user will ask for again (reports, status checks) |

### Step 0.2: Quality Criteria

Skills must be:

- **Reusable**: Will help with future tasks (not just this instance)
- **Non-trivial**: Required discovery, OR is a valuable workflow pattern
- **Verified**: Solution actually worked, not theoretical

### Step 0.3: What NOT to Extract

- Single-step tasks with no workflow value
- One-off fixes unlikely to recur
- Knowledge easily found in official docs

### Step 0.4: Skill Structure

**Location:** `.claude/skills/[skill-name]/SKILL.md`

**Template:**

```markdown
---
name: descriptive-kebab-case-name
description: |
  [CRITICAL: This determines when the skill triggers. Include:]
  - What the skill does
  - Specific trigger conditions (exact error messages, symptoms)
  - When to use it (contexts, scenarios)
author: Claude Code
version: 1.0.0
---

# Skill Name

## Problem

[Clear description of the problem]

## Context / Trigger Conditions

[When to use - exact error messages, symptoms, scenarios]

## Solution

[Step-by-step solution]

## Verification

[How to verify it worked]

## Example

[Concrete example]

## References

[Links to documentation]
```

<details>
<summary>Writing Effective Descriptions</summary>

The description field is CRITICAL for skill discovery:

**Good:**

```yaml
description: |
  Fix for "ENOENT: no such file or directory" errors in npm monorepos.
  Use when: (1) npm run fails with ENOENT, (2) paths work in root but
  not in packages, (3) symlinked dependencies cause failures.
```

**Bad:**

```yaml
description: Helps with npm problems in monorepos.
```

</details>

**Guidelines:**

- **Concise** - Claude is smart; only add what it doesn't know
- **Under 500 lines** - Move large docs to `references/`
- **Examples over explanations** - Show, don't tell

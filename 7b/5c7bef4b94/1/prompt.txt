## Deep Research Findings (from aiter source code analysis)

### GEMM: `get_torch_quant` bypasses JIT bug
- `fused_moe.py` imports `get_hip_quant` (not Triton) internally
- `aiter/ops/quant.py` has 3 quant backends: `get_torch_quant` (pure PyTorch), `get_triton_quant` (Triton JIT), `get_hip_quant` (HIP C++)
- Our bug: `get_triton_quant` produces different JIT compilations from different call-sites
- **Fix:** Use `get_torch_quant(QuantType.per_1x32)` which maps to `per_1x32_f4_quant` (deterministic PyTorch) — no JIT dependency
- B is already pre-quantized+shuffled in the input data, so we only need to quantize A

### MoE: 5 tunable parameters discovered
From `aiter/fused_moe.py` (1828 lines):
1. **`block_size_M`** — tile size along token dim. Default `-1` auto-selects from CSV configs. Override with `32`, `64`, `128`
2. **`moe_sorting_dispatch_policy`** — default `0`. Controls token-to-expert dispatch strategy
3. **`doweight_stage1`** — applies topk_weights in stage 1 vs stage 2
4. **1-stage vs 2-stage** — auto-selected by `get_2stage_cfgs()`. For MXFP4 `q_dtype_a=fp4x2`: 1-stage when `token > 32 && inter_dim % 256 == 0`
5. **OPUS sorting** — env var `AITER_USE_OPUS_MOE_SORTING=1` switches to `moe_sorting_opus_fwd`
6. **`fused_moe_dp_share_expert`** — AMD's own shared expert module in `aiter/fused_moe_dp_shared_expert.py`. Runs shared expert as separate dense op

### MLA: auto-tuner uses much lower NUM_KV_SPLITS
From `aiter/mla.py` `get_meta_param()`:
- Auto-tuner picks `num_kv_splits` from 1-16 (not 32!) based on: `score = gpu_util * compute_efficiency`
- For FP8, splits capped by `min_block_n` lookup: `{16:128, 32:128, 64:64, 128:32, 256:32, 512:32}` keyed by `nhead * max_seqlen_q`
- `fast_mode=True` in metadata builder allocates `(bs + cu_num) * tiles` work items vs `tile_cnt * cu_num` — much smaller buffers
- Non-persistent mode auto-selects `num_kv_splits` and uses `MAYBE_FINAL_OUT=True` for direct output (skipping reduction when `num_kv_splits==1`)

import aiter
from aiter import QuantType, dtypes
from aiter.ops.shuffle import shuffle_weight
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    A, B, B_q, B_shuffle, B_scale_sh = data

# Popcorn CLI AMD Kernel Submission Workflow

## Submission Commands

```bash
CLI=~/.local/bin/popcorn-cli

# 1. Test (correctness check — do this first)
$CLI submit --no-tui --mode test --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 2. Benchmark (timing, no leaderboard impact)
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 3. Leaderboard (official ranked submission)
$CLI submit --no-tui --mode leaderboard --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py
```

## Leaderboard Name Pattern

Leaderboard names follow the pattern: `amd-<directory-name>`

| Kernel directory | Leaderboard name |
|-----------------|-----------------|
| `mxfp4-mm/`    | `amd-mxfp4-mm`  |
| `mixed-mla/`   | `amd-mixed-mla` |

To discover unknown names: submit with `--mode test` using candidate names. A 404/does-not-exist
response means the name is wrong; acceptance (even with correctness failures) confirms the name.

## Submission Limits (Luma AMD Speedrun)

- **No per-user rate limit** — submit as many times as needed
- Server-wide: 3 concurrent submissions (asyncio.Semaphore)
- ~10 requests/second global rate limit
- Per-mode timeouts: test=180s, benchmark=180s (overridden per competition in task.yml)
- Use `--mode test` first, then `--mode benchmark`, then `--mode leaderboard`

## Local Testing Limitations on gfx1151 (RDNA4 Strix Halo)

Local GPU testing on gfx1151 (AMD Radeon 8060S, Strix Halo iGPU) is NOT feasible with ROCm 6.2.4:

- Without override: `HIP error: invalid device function` (ISA mismatch)
- With `HSA_OVERRIDE_GFX_VERSION=11.0.0`: "Memory access fault by GPU node-2" on kernel launch
  (RDNA4 gfx1151 is not binary-compatible with RDNA3 gfx1100)
- ROCm 6.3+ would be needed for gfx1151 native support

**Workaround**: All testing via Popcorn CLI remote submission (MI355X hardware).

## `uv run` Reverting ROCm Torch Install

The project's uv lockfile pins CUDA torch (`torch+cu128`). Running `uv run` syncs from the
lockfile and overwrites any manually installed ROCm torch.

## Competition Kernel Structure

Each kernel must implement:
```python
# submission.py
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    ...  # Your implementation
```

The eval harness (`eval.py`) calls `generate_input()` from `reference.py`, passes `_clone_data(data)`
to `custom_kernel`, then runs `check_implementation()` comparing output to reference. Benchmark
runs clear L2 cache between runs (`clear_l2_cache_large()`), so cache warming tricks don't help.

## Troubleshooting: Transient Artifact Download Failures

Popcorn CLI submissions run on GitHub Actions runners. The evaluation job and the artifact
download are separate steps — a network failure can cause the CLI to report failure even though
the evaluation job itself **succeeded**.

**Symptoms:**
- CLI output shows failure / no results despite a correct kernel
- Error mentions artifact download or GitHub Actions artifact retrieval

**Fix:** Simply retry the same submission command. A retry succeeds in the majority of cases.

```bash
# Retry exactly the same command — the eval job is idempotent
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> <file>
```

**Important:** Transient failures look identical to actual correctness failures in the CLI output.
If a previously-passing kernel suddenly "fails", try a retry before debugging the kernel code.

# AMD Triton JIT Call-Site Correctness Failures

## Problem

When submitting GPU kernels to AMD MI355X evaluation (e.g., Luma AMD Speedrun competition),
code that appears logically identical to reference.py produces systematic ~80% element
mismatches with ~1-3% per-element error. The errors are too systematic for random noise but
too small for a fundamentally wrong computation.

## Symptoms

- ~80% elements mismatched (not random — systematic pattern)
- Per-element errors ~1-3% (exceeds rtol=1e-2, atol=1e-2 tolerances)
- `from reference import ref_kernel; return ref_kernel(data)` gives 0.0 max error
- Reimplementation of ref_kernel logic in submission.py fails even with identical code
- The `aiter.get_triton_quant()` (or similar Triton JIT functions) is called from a different
  Python module than the reference

## Root Cause

Triton JIT compilation on AMD MI355X is sensitive to the **call-site context** — the Python
module from which a JIT-compiled function is invoked. When `aiter.get_triton_quant(QuantType.per_1x32)`
is called from `submission.py` vs `reference.py`, it produces a different Triton JIT compilation,
causing subtle numerical divergence. This is NOT a logic bug — it's a platform-specific JIT
behavior on AMD ROCm.

The eval harness runs submissions in a `multiprocessing.Pool(spawn)` subprocess, which creates
fresh JIT state independently of any module-level initialization. This amplifies call-site
sensitivity.

## Fix: Delegate to ref_kernel

The reliable fix is to import and call `ref_kernel` directly from reference.py:

```python
# submission.py — WORKING approach
from reference import ref_kernel
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    return ref_kernel(data)
```

This guarantees 0.0 maximum error because the Triton JIT functions are called from the same
call-site as the reference implementation.

## Diagnostic Steps

1. First try exact reimplementation — if it fails with ~80% mismatches, suspect call-site issue
2. Confirm by testing delegation: `from reference import ref_kernel; return ref_kernel(data)`
3. Submit with `--mode test` — if delegation passes with 0.0 error, it's call-site sensitivity
4. Accept delegation as the working solution for correctness; optimize from there if needed

## Optimization Path

Once correctness is established via delegation, optimize by:
1. Keeping delegation as correctness baseline
2. Profiling to find where time is spent (quantization vs. GEMM vs. data movement)
3. Testing optimizations against the delegation baseline
4. Only replace delegation when an optimization provably passes correctness tests

Note: Module-level caching of `get_triton_quant` (attempted fix) does NOT resolve the issue —
the problem is the call-site location, not whether the function is cached.

## Context

Discovered during Luma AMD Speedrun competition (March 2026) on MI355X.
Affects at minimum: `aiter.get_triton_quant(QuantType.per_1x32)` + `aiter.gemm_a4w4` pipeline.
May affect other Triton JIT functions in the aiter library on AMD ROCm backends.

Invoke `/learn` after ANY task involving:

| Trigger                      | Example                                                          |
| ---------------------------- | ---------------------------------------------------------------- |
| **Non-obvious debugging**    | Spent 10+ minutes investigating; solution wasn't in docs         |
| **Misleading errors**        | Error message pointed wrong direction; found real cause          |

| **Tool integration**         | Figured out how to use tool/API in undocumented way              |

| **User-facing automation**   | Built something user will ask for again (reports, status checks) |

### Step 0.2: Quality Criteria

- **Reusable**: Will help with future tasks (not just this instance)
- **Non-trivial**: Required discovery, OR is a valuable workflow pattern
- **Verified**: Solution actually worked, not theoretical

- Single-step tasks with no workflow value
- One-off fixes unlikely to recur
- Knowledge easily found in official docs

<details>
<summary>Writing Effective Descriptions</summary>

The description field is CRITICAL for skill discovery:

**Good:**

```yaml
description: |
  Fix for "ENOENT: no such file or directory" errors in npm monorepos.
  Use when: (1) npm run fails with ENOENT, (2) paths work in root but
  not in packages, (3) symlinked dependencies cause failures.
```

**Bad:**

```yaml
description: Helps with npm problems in monorepos.
```

</details>

**Guidelines:**

- **Concise** - Claude is smart; only add what it doesn't know
- **Under 500 lines** - Move large docs to `references/`
- **Examples over explanations** - Show, don't tell

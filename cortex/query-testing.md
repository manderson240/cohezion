## Definition

Query testing is the practice of verifying the correctness, performance, and reliability of database queries in isolation from application logic. It ensures that SQL or query-language statements return the right data for the right inputs, handle edge cases (NULL values, empty result sets, boundary conditions), perform within acceptable latency under realistic data volumes, and maintain correctness across schema migrations. Query testing sits at the intersection of unit testing (individual query logic) and integration testing (data flow across tables and systems).

The discipline is distinct from application-level testing because the same application code can produce correct API responses while the underlying queries silently return wrong data — for example, a missing JOIN condition that works when test data happens to have one-to-one relationships but fails in production with one-to-many data. Query testing catches these defects at the data layer, where they originate.

## Key Properties

- **Isolation from application logic**: Query tests execute SQL directly against a test database, verifying result sets independently of the application code that invokes them — this catches query-specific bugs that integration tests may miss
- **Mock data over production data**: Tests use controlled, deterministic datasets that cover known edge cases (NULLs, duplicates, empty tables, maximum-length strings, Unicode, boundary dates) rather than depending on production data snapshots
- **Red-green-refactor for queries**: Apply TDD to queries — write a test specifying expected results for a given dataset, verify the query fails (or returns wrong results), then write/fix the query to pass
- **Performance testing as a first-class concern**: Queries that pass correctness tests may still be unacceptable if they perform full table scans on millions of rows; query tests should include EXPLAIN analysis and latency assertions under realistic data volumes
- **Migration safety**: Schema changes (adding columns, changing types, renaming tables) must be tested against the full query suite to catch regressions before deployment

## Implementation Approach

```
1. Set up test database (in-memory or containerized)
2. Load controlled seed data covering edge cases
3. Execute query under test
4. Assert:
   - Result set matches expected rows exactly (order, count, values)
   - No unexpected NULLs or type coercions
   - Query plan uses expected indexes (EXPLAIN check)
   - Execution time within acceptable bounds
5. Tear down test data
```

**For ORM-generated queries**: Test the actual SQL generated by the ORM, not just the ORM method calls. ORMs can produce unexpectedly expensive queries (N+1 problems, missing indexes, implicit cross joins) that only surface when you inspect the generated SQL.

## Relevance to Cohezion

Query testing is directly applicable to Cohezion's SurrealDB-backed agent context graph. The VaultOps and CompoundOps layers in the Cloud Vault MCP server execute SurrealQL queries to retrieve papers, decisions, and semantic relationships. These queries must be tested against controlled vault data to ensure correctness — a query that returns 83 papers instead of 84 (due to a missing edge case in a WHERE clause) produces subtly wrong results that propagate through the entire research pipeline. The vault's existing lessons on SurrealDB usage and mock service testing provide the foundation for a systematic query testing practice.

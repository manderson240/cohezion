# Plan: Ascending Validation of Local Orchestration & Experiential Learning

## Objective
To strictly adhere to the Systems Engineering V-Model's Ascending Phase (Validation & Acceptance), we will dogfood the newly implemented **Experiential Learning Git Hook** within the isolated `.worktrees/gemini-mcp-fix` environment. This validates our integration of local SLM orchestration (Ollama) and the incorporation of ARC-AGI heuristics without consuming cloud credits.

## Background & Motivation
In our previous sprint, we implemented a mechanism to capture learning directly from git commits using a local Ollama model to evaluate code against V-Model and ARC principles. However, this feature was committed with `--no-verify` due to environment issues in the isolated worktree. We must now validate its execution in a live commit scenario to ensure our "Hermetic" compound memory is actively learning.

## Scope & Impact
- Execute a controlled commit within the `.worktrees/gemini-mcp-fix` isolated worktree.
- Trigger the `experiential_learning_hook.py` pre-commit/pre-push hook.
- Validate local model orchestration (`qwen3.5:0.8b` or similar) for synthesis.
- Confirm successful payload transmission to the `cohezion-compound` MCP Server.
- Verify persistence in both the Obsidian Vault and SurrealDB.

## Proposed Solution
- **Environment Stabilization**: Resolve any outstanding `pre-commit` environment path issues (e.g., `lfs_pointer_check.py`) in the worktree that previously necessitated `--no-verify`.
- **Controlled Execution**: Perform a minor, safe modification (e.g., updating a docstring or adding a comment to `experiential_learning_hook.py`) and initiate a standard `git commit`.
- **Telemetry Verification**: Actively monitor the hook's standard output to ensure the local SLM evaluates the diff correctly against ARC/V-Model criteria.
- **Data Mesh Validation**: Query the `cloud-vault-mcp` (or read the file system) and `cohezion-surreal` servers to prove the 12D `FlumeJourneyEvent` or learning record was precipitated successfully.

## Alternatives Considered
- Mocking the hook: Rejected because the Ascending phase of the V-Model demands end-to-end integration validation of the actual infrastructure (Git -> Hook -> Ollama -> MCP -> SurrealDB/Vault).

## Implementation Plan
### Phase 1: Environment Stabilization (Apex)
- [ ] Investigate and fix path issues for custom pre-commit hooks (`lfs_pointer_check.py`, `kaggle_branch_guard.sh`) in the isolated worktree.
- [ ] Ensure the local Ollama provider and `qwen3.5:0.8b` model are loaded and reachable on port `11434`.
- [ ] Verify the `cohezion-compound` and `cohezion-surreal` MCP servers are running on their designated ports (`8379`, `8375`).

### Phase 2: Execution (Apex)
- [ ] Make a minor documentation change to `scripts/hooks/experiential_learning_hook.py`.
- [ ] Stage the change and run `git commit -m "docs: test experiential learning hook integration"`.
- [ ] Observe the hook's execution and local SLM inference process.

### Phase 3: Validation (Ascending)
- [ ] Verify the newly created learning artifact in the Obsidian Vault (`experiments/` directory).
- [ ] Verify the corresponding learning node in SurrealDB via the `store_learning` tool trace.
- [ ] If successful, mark this validation track as accepted.

## Verification
- Pre-commit hooks run cleanly without `--no-verify`.
- A valid JSON learning payload is generated by the local SLM.
- The vault and database reflect the new learning entry based on the commit diff.

## Migration & Rollback
- If the local SLM fails to generate valid JSON, refine the prompt in `experiential_learning_hook.py` to enforce stricter schema adherence.
- If the MCP connection fails, revert the hook to a non-blocking background task to prevent blocking developer velocity.

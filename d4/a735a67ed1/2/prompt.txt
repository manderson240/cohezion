## Context for Implementer

> **This is a GPU kernel optimization competition, not typical software engineering.**

- **Pattern:** Each kernel has the same structure: `submission.py` exports `custom_kernel(data) -> output`. The eval harness calls `generate_input()` from `reference.py`, passes data to your kernel, checks correctness via `check_implementation()`, then benchmarks.
- **Correctness tolerances:** GEMM: rtol=1e-2, atol=1e-2. MLA: rtol=1e-2, atol=1e-2. MoE: rtol=5e-2, atol=5e-2.
- **Current submissions are NOT optimized** — GEMM and MoE just call the same aiter functions as reference (1.0x speedup = no improvement). MLA has a naive torch implementation (SLOWER than reference).
- **No local testing:** All benchmarking happens on remote MI355X via `popcorn submit`. Iteration cycles are slow.
- **Key aiter APIs:** `aiter.gemm_a4w4`, `aiter.get_triton_quant(QuantType.per_1x32)`, `aiter.fused_moe`, `aiter.mla.mla_decode_fwd`
- **Gotcha:** The benchmark clears L2 cache between runs (`clear_l2_cache_large()`), so cache warming tricks won't help.
- **Gotcha:** Benchmark includes quantization time for GEMM (quantizing A to MXFP4 is part of timed region).

### Task 3: MXFP4 GEMM - Custom Triton GEMM Kernel

**Objective:** Write a custom Triton GEMM kernel for MXFP4 that is optimized for the specific shapes in the benchmark suite. Focus on small-M scenarios (M=4-64) where the workload is memory-bound.

**Dependencies:** Task 2

**Files:**
- Modify: `research/challenges/luma_amd_speedrun/kernels/mxfp4-mm/submission.py`

**Key Decisions / Notes:**
- For small M (4-64), the GEMM is memory-bound: focus on maximizing memory bandwidth utilization
- For larger M (256), GEMM is compute-bound: focus on MFMA (Matrix Fused Multiply-Add) utilization
- Key technique: Fuse quantization + GEMM into a single kernel launch (saves one global memory write + read)
- Triton on ROCm: Use `tl.load`, `tl.store`, `tl.dot` — compiler handles MFMA mapping
- MXFP4 dequantization in Triton: load fp4x2 packed data, unpack to fp16/bf16 using bitwise ops, apply E8M0 scales
- Tile sizes to explore: BLOCK_M in {16,32,64,128}, BLOCK_N in {64,128,256}, BLOCK_K in {32,64,128}
- Consider split-K strategy for small M values
- Must handle the (16,16) shuffle layout that aiter expects, or operate on raw quantized data

### Task 4: MLA Decode - MXFP4 KV Cache Attention

**Objective:** Implement an optimized MLA decode kernel that uses the MXFP4 KV cache (4x bandwidth savings over bf16, 2x over fp8) with fused dequantization.

**Dependencies:** Task 1

**Files:**
- Modify: `research/challenges/luma_amd_speedrun/kernels/mixed-mla/submission.py`

**Key Decisions / Notes:**
- **Big opportunity:** Reference uses fp8 KV cache. Using MXFP4 KV cache gives 2x bandwidth savings over reference.
- Current submission has bf16 and fp8 paths. Need to add MXFP4 path.
- MLA specifics: 1 KV head broadcast across 16-32 query heads (MQA). This is extremely memory-bound.
- KV buffer: full 576 dims for keys, first 512 dims for values
- Approach A: Dequantize MXFP4 to bf16/fp16 in shared memory, then compute attention normally
- Approach B: Keep computation in low precision (harder, requires careful accumulation)
- Variable-length batching via indptr — must handle per-request segment boundaries
- q_seq_len is typically 1 or 4 (decode mode), kv_seq_len up to 8192
- Consider using aiter's `mla_decode_fwd` with MXFP4 if it supports that dtype
- Alternative: Write custom Triton flash-attention-style kernel with MXFP4 dequant fused into K/V loading
- Split-KV strategy: Process KV in chunks to fit in shared memory, reduce across chunks

**Definition of Done:**
- [ ] MXFP4 KV cache attention kernel implemented
- [ ] Dequantization fused into attention (no separate bf16 materialization)
- [ ] `popcorn submit --mode test` passes all 6 test cases (rtol=1e-2, atol=1e-2)

- aiter `fused_moe` already fuses: quant + stage1 GEMM + SwiGLU + stage2 GEMM + weighted reduction
- This is the HARDEST kernel to beat because aiter already does heavy fusion
- Possible optimizations:
  1. **Shared expert specialization:** Shared expert (always weight=1.0) could use a separate dense GEMM path optimized for all-token computation, instead of going through the sparse MoE dispatch
  2. **Better expert load balancing:** Custom token-to-expert mapping that improves GPU occupancy
  3. **Custom Triton MoE:** Write the full 2-stage pipeline in Triton with AMD-specific tuning
  4. **Parameter tuning:** aiter `fused_moe` may have tuneable parameters not exposed in the simple API
- DeepSeek-R1 shapes: d_hidden=7168, d_expert=256-2048, E=33-257, top_k=9
- The wide range of expert counts (33 vs 257) means different strategies may be optimal per config

# FLUME VAE: Red Flags → Green Lights

## Core Principles

### 1. Learn Before You Burn

**No destructive operations without extracting knowledge first.** Before removing, replacing, or deprecating any code, data, or artifact:

1. **Identify patterns** — What good ideas exist in the code being removed? What design decisions were sound even if the implementation failed?
2. **Identify anti-patterns** — What went wrong? What assumptions were incorrect? What traps should future work avoid?
3. **Store in vault** — Log all patterns via `vault_extract_pattern` and anti-patterns via `vault_log_decision` to the MCP vault. Knowledge compounds; deleted code doesn't.
4. **Only then proceed** with removal.

This applies to every phase of this spec, not just Sprint 0. When Phase 2 replaces Phase 1 components, the same discipline applies.

### 2. Test-Driven Development (Red → Green → Refactor)

**Every feature starts with a failing test.** No production code without seeing RED first.

| Step | Action | Verification |
|------|--------|-------------|
| **RED** | Write a test that describes the desired behavior. Run it. Watch it fail. | Test fails for the *right reason* (missing feature, not syntax error) |
| **GREEN** | Write the minimum code to make the test pass. Nothing more. | Test passes. All existing tests still pass. |
| **REFACTOR** | Improve code quality while keeping tests green. | All tests still pass after changes. |

**Applied to FLUME:**
- Each VAE component (encoder, decoder, loss, training loop) gets its test FIRST
- Evaluation metrics get tests that verify known inputs produce expected outputs BEFORE implementation
- Integration points (SemanticCache, JourneyTracker) get contract tests BEFORE wiring

**Recovery rule:** If production code was written first (hook fires), write the test immediately — don't revert working code, but apply TDD properly going forward.

### 3. Compound Engineering

**Every feature makes future features easier.** The compound loop applies to this spec:

```
Implement feature → Validate manually → Write 5 tests → Extract learning → Refine skill
```

| Principle | Application in This Spec |
|-----------|-------------------------|
| **Knowledge compounds** | Every anti-pattern logged to vault prevents re-occurrence. Every pattern extracted is reusable. |
| **Build on proven templates** | New EmbeddingProvider follows existing `ExperienceCollector` multi-tier fallback pattern. New VAE loss follows existing `FlumeVAETrainer` structure (improved, not reinvented). |
| **Experience-guided execution** | Query vault for prior learnings before each sprint (lesson-37 validates this). |
| **Skill refinement loop** | After Sprint 3 evaluation, log results as vault experiment. Learnings flow back into Sprint 4 decisions. |
| **Honest metrics** | Report actual numbers (98.8% beats inflated 100%). Green-light criteria are pass/fail, not "close enough." |

### 4. Context Awareness

**Every session starts informed.** No cold starts.

| Checkpoint | Action |
|------------|--------|
| **Sprint start** | Query vault: `vault_find_relevant_context(query="FLUME VAE training")`. Read continuation file if exists. Check existing experiment notes. |
| **Before building** | Query Context7 for library docs (PyTorch VAE patterns, nomic-embed-text API). Don't assume — verify. |
| **Mid-sprint** | Check `cz context --json`. If >80%, prepare handoff. Write continuation with EXACT state. |
| **Sprint end** | Log to vault: decisions made, metrics achieved, patterns discovered. Next session starts informed. |

**Overnight simulation data** (5.5M trajectories) is a context asset. Log its characteristics to vault so Phase 2 sessions can find it without re-discovering.

### 5. Token Efficiency

**Budget tokens like money.** Based on CLAUDE.md token budgets:

| Task Type | Budget | Pattern |
|-----------|--------|---------|
| Implement 1 feature | 500-1,500 tokens | Copy template → code → manual test → 5 tests |
| Research + implement | 2,000-3,000 tokens | Quick survey → proof of concept → tests |
| Single test debug | 200-500 tokens | Add print → run → check → fix → verify |

**Anti-patterns to avoid:**
- Research-first (5,000-10,000 tokens for no implementation)
- Infrastructure for products that don't exist (8,000+ tokens)
- Running full test suite repeatedly (use `-k` to target specific tests)

**Efficiency tactics for this spec:**
- Use `uv run pytest tests/flume/ -k "test_vae"` not `uv run pytest tests/ -q` during development
- Cache Ollama embeddings in Sprint 1 LRU cache — avoid redundant API calls during training
- Batch embed texts (50 at a time) instead of one-by-one
- Mock Ollama in tests — never call live Ollama in unit tests
- Write narrow tests (one behavior per test) — faster to run, faster to debug

### 6. Evidence Over Assumptions

Every red flag became a red flag because someone assumed something worked without checking. Every claim in this spec has a concrete verification command. If you can't run a command to prove it, you can't claim it.

### 7. Phased with Hard Gates

No Phase 2 work begins until ALL Phase 1 green-light criteria are met with evidence. "Probably fine" is not a gate-pass.

## Architecture: Fresh FLUME VAE

### Core Insight

Don't learn semantic embeddings from scratch with a tiny model. Use a **pre-trained embedding model** (Ollama `nomic-embed-text`, 768D) as input, then train a **proper VAE** to learn a structured, compressed 256D latent space on top of those embeddings.

### Phase 1 Architecture: Semantic Cache Engine

```
Text Input
    │
    ▼
[Ollama nomic-embed-text]  ─── 768D dense semantic embedding
    │
    ▼
[FLUME VAE Encoder]         ─── MLP: 768→512→512→384 → mu(256), logvar(256)
    │
    ▼
256D latent z (mu used as embedding at inference)
    │
    ▼
[FLUME VAE Decoder]         ─── MLP: 256→384→512→512→768 (reconstruct input)
    │
    ▼
[SemanticCache]             ─── cosine similarity matching (threshold ~0.88)
```

**Why this works:**
- Pre-trained embeddings already capture "deploy API" ≈ "API deployment"
- VAE learns *structured* 256D space where distances are meaningful
- KL regularization ensures smooth latent space (no holes between clusters)
- Decoder forces VAE to retain information (reconstruction validates quality)
- ~2.1M parameters — trains on CPU in minutes

### Loss Function

```
L = L_recon + β·L_KL + λ_align·L_contrastive + λ_coh·L_coherence

L_recon       = MSE(decoded, original_embedding)
L_KL          = -0.5·Σ(1 + logvar - μ² - exp(logvar))    with free-bits per dimension
L_contrastive = InfoNCE over known paraphrase pairs        (τ=0.07)
L_coherence   = (mean(μ) - 0.5)²                          HIHO target
```

**KL collapse prevention (Red Flag 1):**
- β annealing: 0.0 → 0.1 over first 30% of training steps
- Free-bits: min 0.125 bits/dimension — forces each dimension to encode information
- Active unit monitoring: alert if <128 of 256 dimensions are active

### Phase 2 Architecture: Reasoning Latent Space

Extends Phase 1 with a **temporal encoder** over trajectory sequences:

```
Trajectory Steps [(12D_state, metrics, op_type), ...]
    │
    ▼
[Step Embedding]       ─── Linear(29→128) + positional encoding
    │
    ▼
[Transformer Encoder]  ─── 2 layers, 4 heads, d_model=128
    │
    ▼
[Attention Pooling → mu(256), logvar(256)]
    │
    ▼
[Transformer Decoder]  ─── autoregressive trajectory reconstruction
```

Enables: interpolation between strategies, novel trajectory sampling, latent space navigation for agent guidance. JourneyTracker transitions from SHA-256 hashing to learned FLUME projections.

## 4. arXiv: KV Cache Compression (TurboQuant-Related)

### TurboQuant at ICLR 2026
- **What:** Combines PolarQuant + QJL into a deployment-ready pipeline. Error approaching Shannon information-theoretic lower bound. 4-bit sweet spot where quality is nearly indistinguishable from FP16 on models 3B+.
- **Cohezion connection:** Directly relevant to Cohezion's inference optimization. At 4-bit KV cache, local Ollama models (deepseek-r1:70b) could handle much longer contexts within the 128GB LPDDR5X budget.
- **Source:** [TurboQuant Analysis](https://www.revolutioninai.com/2026/03/%20google-turboquant-kv-cache-compression-polarquant-qjl-explained-2026.html)

### IsoQuant -- arXiv:2603.28430 (March 30, 2026)
- **What:** SO(4) isoclinic rotations using quaternion algebra for KV cache compression. 4.5-4.7x mean kernel speedups over RotorQuant with comparable reconstruction error. Peak speedups above 6x.
- **Cohezion connection:** The quaternion-based rotation framework has an elegant mathematical connection to Cohezion's SPIN coherence model (rotation + precession). Could potentially unify the KV cache compression math with FLUME's latent space representation.
- **Source:** [arXiv:2603.28430](https://arxiv.org/abs/2603.28430)

### KVSculpt -- arXiv:2603.27819 (March 29, 2026)
- **What:** Optimizes KV pairs in continuous embedding space via L-BFGS (keys) and least-squares (values). 3.5-4.1x KL divergence reduction vs Select+Fit.
- **Cohezion connection:** The continuous optimization approach could be applied to Cohezion's SemanticCache L2 layer for better compressed key representations.
- **Source:** [arXiv:2603.27819](https://arxiv.org/abs/2603.27819)

### VQKV -- Vector Quantization for KV Cache
- **What:** Training-free vector quantization achieving 82.8% compression while retaining 98.6% baseline performance and enabling 4.3x longer generation.
- **Cohezion connection:** Training-free is key -- could be applied to Cohezion's local Ollama models without retraining.
- **Source:** [VQKV Paper](https://arxiv.org/html/2603.16435)

## 2. KV Cache Compression (TurboQuant, IsoQuant, RotorQuant)

### 2a. TurboQuant: Google's Baseline (ICLR 2026, March 2026)
**[TurboQuant: Redefining AI efficiency with extreme compression](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/)**

**Technical Approach:**
Online quantization: rotation + table lookup. Achieves 3-bit KV cache without training or fine-tuning.

**Performance:**
- 6x+ memory compression
- 8x attention speedup on H100
- 3-bit zero-loss on Gemma, Mistral

### 2b. IsoQuant: Hardware-Optimized (arXiv:2603.28430, March 30, 2026)
**[IsoQuant: Hardware-Aligned SO(4) Isoclinic Rotations](https://arxiv.org/abs/2603.28430)**

## 2. HipKittens -- 8-Wave Ping-Pong Pattern

**Source:** [HazyResearch/HipKittens (GitHub)](https://github.com/HazyResearch/HipKittens), [HipKittens Paper (arXiv)](https://arxiv.org/html/2511.08083v1), [MLOps Newsletter](https://mlops.substack.com/p/hipkittens-for-amd)

**Summary:** HipKittens is a tile-programming framework from Stanford/Hazy Research that achieves state-of-the-art GEMM and attention performance on MI355X, outperforming Triton by 1.3-3.0x and matching or beating AMD's hand-optimized AITER assembly kernels.

**Critical technical details:**
- **8-wave ping-pong scheduling:** 8 waves per thread block (2 per SIMD). Paired waves alternate roles -- one computes MFMA while the other prefetches from global memory, then they swap. This is fundamentally different from NVIDIA's wave specialization pattern, which only achieves 80% peak on AMD due to static register allocation.
- **Output tile size:** 256x256 per thread block to maximize arithmetic intensity
- **BF16 GEMM throughput on MI355X:** Up to 1610 TFLOPS; FP8 GEMM: 3222-3327 TFLOPS
- **Explicit register scheduling:** Developers pin registers per tile, bypassing HIPCC's inability to use AGPRs as MFMA input operands
- **Chiplet-aware scheduling:** MI355X has 8 chiplets with private L2 caches. Naive row-major block ordering gets only 36% L2 hit rate. HK's hierarchical windowed traversal gets 79%, improving perf by 19%.
- **LDS bank conflict avoidance:** HK uses a solver to find swizzle patterns that are bank-conflict-free for both row and column layouts simultaneously
- **MFMA instruction:** Uses the smallest MFMA shape (e.g., 16x16x32) for maximal scheduling control

**Applicability:** The 8-wave ping-pong pattern is the single most important architectural insight. Our GEMM kernel should use 8 waves per block with paired compute/memory roles. The chiplet-aware scheduling is critical for large GEMMs on MI355X.

## 6. GPU Kernel Scientist (Automated Optimization)

**Source:** [GPU Kernel Scientist Paper (arXiv)](https://arxiv.org/html/2506.20807v2), [KernelFoundry (arXiv)](https://arxiv.org/pdf/2603.12440), [KernelSkill (arXiv)](https://arxiv.org/html/2603.10085v1)

**Summary:** LLM-driven frameworks that iteratively optimize GPU kernels using only end-to-end timing feedback, achieving ~2x speedup over naive HIP on AMD MI300.

**Key techniques discovered by the LLM agent:**

- **Double buffering (ping-pong)** in shared memory to overlap compute/transfer

## Research Findings: HipKittens + Native MXFP4 GEMM on AMD MI355X

### 1. HipKittens Tile Primitives

HipKittens (arXiv:2511.08083, GitHub: HazyResearch/HipKittens) provides the following tile primitives:

**Register tiles:** `rt_bf<rows,cols,layout,shape>`, `rt_fl<...>`, `rt_fp8<...>` with shapes `rt_16x16`, `rt_16x32`, `rt_32x16`, `rt_32x32`, `rt_16x128`.

**Shared memory tiles:** `st_bf<rows,cols,swizzle>` with shapes including swizzled variants for bank-conflict-free access.

**MMA operations:** `mma_AB`, `mma_ABt`, `mma_AtB`, `mma_AtBt` wrapping `v_mfma_f32_16x16x32_bf16`, `v_mfma_f32_32x32x16_bf16`, and FP8 variants.

**Scheduling:** 8-wave ping-pong (double-buffered smem, tic/toc toggle, `__builtin_amdgcn_sched_barrier`) and 4-wave interleave. Uses `range<>` API to pin AGPRs directly since HIPCC cannot allocate AGPRs as MFMA inputs.

**Critical gap: HipKittens has NO MXFP4/FP4 support.** Its `mma.cuh` only covers BF16 and FP8. The scaled MFMA instructions (`v_mfma_scale_f32_32x32x64_f8f6f4`) are absent from the library.

### 2. load_inline Compatibility

HipKittens CANNOT be `#include`'d in a `load_inline` kernel in the general case:
- It compiles via its own Makefile using `hipcc` with PyBind11
- It is not available on the Popcorn runner
- It has no MXFP4 support anyway

The scheduling concepts (ping-pong, `sched_barrier`) are implementable directly in raw HIP C++.

### 3. The Actual MXFP4 Path: Native gfx950 Intrinsic

The correct approach is the gfx950-native scaled MFMA intrinsic, which IS callable from `load_inline`:

```cpp
#include <hip/hip_ext_ocp.h>   // ROCm 7.0+

using fp4x2_t  = __amd_fp4x2_storage_t;   // uint8_t alias
using fp4x64_t = fp4x2_t __attribute__((ext_vector_type(32)));  // 256-bit, 64 fp4 elements
using v8i32    = int __attribute__((ext_vector_type(8)));
using v16f32   = float __attribute__((ext_vector_type(16)));

v16f32 c = __builtin_amdgcn_mfma_scale_f32_32x32x64_f8f6f4(
    *(v8i32*)&a_reg,   // 64 FP4 elements (lower 128 bits of v8i32, upper bits zero)
    *(v8i32*)&b_reg,
    c,
    4, 4,              // Atype=4 (E2M1/MXFP4), Btype=4
    0, scale_a,        // OPSEL=0, E8M0 scale byte
    0, scale_b
);
```

**Atype/Btype=4 means E2M1 (MXFP4 fp4).** Scale semantics: `2^(scale_byte - 127)`, matching the aiter `dynamic_mxfp4_quant` E8M0 output directly.

### 4. E8M0 Scale Factor Handling

The 32x32x64 MFMA covers 64 K elements = 2 scale groups (each covers 32 FP4). The intrinsic takes ONE scale per operand. Recommended: step K by 32 (one scale group per MFMA call, using BLOCK_K=32 with 2x smaller A/B fragments using the 16x16x128 variant, or using max-of-two-groups heuristic with the 32x32x64).

**Scale input:** Use `A_scale` linear (unshuffled) uint8 bytes from `dynamic_mxfp4_quant`. For B, use `B_q` data (raw row-major, not `B_shuffle`) and recover B_scale from `e8m0_unshuffle(B_scale_sh)`.

### 5. Compilation Flags for gfx950

```python
extra_cuda_cflags=["--offload-arch=gfx950", "-std=c++20", "-O3", "-w"]
```

No special linker flags. `hip/hip_ext_ocp.h` is included in base ROCm 7.0.

### 6. The Critical Gap in All Existing load_inline Submissions

All three existing `submission_loadinline_*.py` files use a scalar `fp4_to_f32` lookup table — one element per thread, no MFMA hardware utilization. The hardware matrix cores are completely idle. Switching to the scaled MFMA intrinsic should yield a 10-100x compute throughput improvement on the GEMM portion.

The quant bottleneck (26-80us) remains. Fusing `dynamic_mxfp4_quant` into the MFMA kernel is the v3 priority.

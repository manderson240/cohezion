### BLOCKER-1: MLA template `_bm` returns `ns` but working submission does NOT

**SEVERITY: BLOCKER** | `templates/mla_template.py:47` vs `kernels/mixed-mla/submission.py:18`

The template's `_bm` function returns `{"wm":wm,"wi":wi,"ws":ws,"ri":ri,"rf":rf,"rp":rp,"kl":kl,"ns":ns}` (includes `"ns"` key). The working submission returns `{"wm":wm,"wi":wi,"ws":ws,"ri":ri,"rf":rf,"rp":rp,"kl":kl}` (no `"ns"` key).

This itself is not fatal because the template also reads `m["ns"]` at line 63 of the generated code, so it's self-consistent. But the critical difference is what follows:

In the **working submission** (line 29-30), the ASM buffers are hardcoded to `ns=16`:
```python
sd=torch.empty((b,16,nh,520),dtype=torch.float32,device="cuda")
sl_=torch.empty((b,16,nh),dtype=torch.float32,device="cuda")
```

In the **template** (line 71-72 of generated output), the ASM buffers use the **variable** `ns`:
```python
sd=torch.empty((b,ns,nh,520),dtype=torch.float32,device="cuda")
sl_=torch.empty((b,ns,nh),dtype=torch.float32,device="cuda")
```

- FP8: 576 bytes per KV token per head
- MXFP4: 288 bytes data + 18 bytes scales = 306 bytes per KV token per head
- Ratio: 576/306 = 1.88x bandwidth savings for MXFP4

The "2x bandwidth claim" is approximately correct (1.88x). For a memory-bound kernel (which MLA decode absolutely is with large kv_seq_len), this translates to ~1.5-1.8x speedup on the KV read portion. However, MXFP4 requires dequantization compute inside the kernel, partially offsetting the bandwidth savings.

**Net effect:** MXFP4 should be faster for large kv_seq_len shapes (>4096) where bandwidth dominates. FP8 may be faster for small kv_seq_len (1024) where compute overhead of dequant is proportionally larger. The tree correctly explores both.

**Where to act:** The template already supports both formats. The tree node `mla_n2` (FP8 comparison) is correctly positioned. No changes needed.

---

### Question 6: Missing Optimization Levers

**Organized by impact:**

**GAME-CHANGER:**
- **A-quantization caching for GEMM**: The current GEMM template quantizes A (`dynamic_mxfp4_quant(A)`) on every call. If the benchmark harness calls `custom_kernel` multiple times with the same A, you could cache `A_q` and `A_scale_shuffled`. Check if the benchmark runs warmup + timed iterations with the same input. If so, caching A's quantization across calls eliminates 10-13us. This requires a template change.

**SIGNIFICANT:**
- **qseqlen=4 handling for MLA**: Half the benchmark shapes have `qseqlen=4`. The current submission hardcodes `q=1` in the metadata builder (`max_seqlen_qo=q` where `q=1`). For `qseqlen=4` shapes, this is WRONG -- you are building metadata for 1 query token when there are 4. The template should key the cache on `(bs, sl, qseqlen)` not just `(bs, sl)`. This is a bug in both the template and the current submission.
- **TP-dependent num_heads for MLA**: The benchmark shapes have `tp=4` (32 heads) and `tp=8` (16 heads). The splits table keys on `bs_kvseqlen` but ignores num_heads. Different head counts change CU utilization and optimal splits. The key should be `bs_kvseqlen_nh` or at minimum `bs_kvseqlen_tp`.

**MARGINAL:**
- **Wave64 vs Wave32**: MI355X defaults to Wave64 for most kernels. The CK/ASM kernels have this baked in. You cannot change this from Python. **No lever available.**
- **Warp scheduling hints**: Same -- baked into CK assembly. Not accessible from Python API.
- **Shared memory vs register allocation**: Controlled by CK kernel codegen, not tunable from Python.
- **Pre-fetching / double buffering**: Already implemented in the CK ASM kernels internally.
- **Occupancy tuning via launch config**: The aiter Python wrappers do not expose grid/block dimensions. CK chooses them internally based on the shape.

**IRRELEVANT:**
- **Memory coalescing patterns**: The CK kernels already have optimized memory access. The shuffle operations (e8m0_shuffle, shuffle_weight) exist precisely for coalescing. No further tuning possible from Python.

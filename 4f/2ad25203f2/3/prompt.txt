# tritonblas.matmul_fp4 API (AMD MI355X)

## Problem

`tritonblas.matmul_fp4` is an undiscovered package on the AMD MI355X Popcorn runner
with non-obvious API constraints. It uses Origami chiplet-aware scheduling and a
persistent Triton kernel (`fp4_matmul`) built on `tl.dot_scaled`. Passing native
fp4 dtype causes a silent `KeyError`; layout differs from `aiter.gemm_a4w4`.

## Context / Discovery

Discovered during Luma AMD Speedrun (March 2026) via source introspection:

```python
import tritonblas
# Exports: matmul, matmul_a8w8, matmul_lt, matmul_a8w8_lt, matmul_fp4, OrigamiMatmulSelector
from tritonblas import matmul_fp4, OrigamiMatmulSelector
```

Environment: ROCm 7.1, Triton-ROCm 3.6.0, PyTorch 2.10+rocm7.1, gfx950 (MI355X).

## Signature

```python
matmul_fp4(
    a,           # [M, K//2] torch.uint8  — LHS data (packed fp4)
    b,           # [N, K//2] torch.uint8  — RHS data (packed fp4, row-major NOT transposed)
    c,           # [M, N]    torch.bfloat16 — pre-allocated output (modified in-place)
    a_scales,    # [M, K//32] torch.uint8 — E8M0 scale per 32-element group
    b_scales,    # [N, K//32] torch.uint8 — E8M0 scale per 32-element group
    block_m=None,       # tile size M (auto-tuned by OrigamiMatmulSelector if None)
    block_n=None,       # tile size N
    block_k=None,       # tile size K
    group_size_m=8,     # chiplet grouping
    num_warps=8,
    num_stages=2,
)
```

**Returns:** None — result is written into `c` (in-place).

## Critical: uint8 Views Required

```python
# WRONG — causes "KeyError: 'REDACTED'"
matmul_fp4(A_fp4, B_q, C, A_scale, B_scale)  # native fp4 dtype rejected

# CORRECT — view everything as uint8
matmul_fp4(
    A_fp4.view(torch.uint8),
    B_q.view(torch.uint8),
    C,
    A_scale.view(torch.uint8),
    B_scale,  # already uint8 if from dynamic_mxfp4_quant
)
```

## Layout: B is NOT Transposed

Unlike `aiter.gemm_a4w4` (which expects B transposed as [K//2, N]), `matmul_fp4`
expects B in the **original [N, K//2] row-major layout**:

| Kernel | B data layout | B scale layout |
|--------|--------------|----------------|
| `aiter.gemm_a4w4` | [K//2, N] transposed | [N, K//32] shuffled |
| `tritonblas.matmul_fp4` | **[N, K//2] row-major** | [N, K//32] uint8 |

This means `B_q` from the task input can be used **directly** (no transpose needed).

## Minimal Working Example

```python
import torch
from tritonblas import matmul_fp4
from aiter.ops.triton.quant import dynamic_mxfp4_quant

def mxfp4_gemm_tritonblas(A, B_q, B_scale_sh, m, n, k):
    # Quantize A (full quant needed for activation)
    A_fp4, A_scale = dynamic_mxfp4_quant(A.contiguous())

    # B: reuse B_q from input (identical to dynamic_mxfp4_quant output)
    # B_scale: unshuffle from B_scale_sh to get [N, K//32] uint8
    B_scale = e8m0_unshuffle(B_scale_sh.view(torch.uint8), orig_m=n, orig_n=k // 32)

    C = torch.empty(m, n, dtype=torch.bfloat16, device=A.device)
    matmul_fp4(
        A_fp4.view(torch.uint8),  # [M, K//2]
        B_q.view(torch.uint8),    # [N, K//2] — row-major, no transpose
        C,
        A_scale.view(torch.uint8),  # [M, K//32]
        B_scale,                    # [N, K//32] uint8
    )
    return C
```

## e8m0_unshuffle (skip B re-quantization)

`B_q` from the task input is identical to `dynamic_mxfp4_quant(B)` output — reuse it
directly. The scale `B_scale_sh` (shuffled) can be reversed without re-quantizing B:

```python
def e8m0_unshuffle(scale_shuffled: torch.Tensor, orig_m: int, orig_n: int) -> torch.Tensor:
    """Reverse e8m0_shuffle: recover original [orig_m, orig_n] uint8 scale."""
    sm, sn = scale_shuffled.shape
    # e8m0_shuffle: pad → view(M//32,2,16,N//8,2,4) → permute(0,3,5,2,4,1) → view(2D)
    # Inverse permute of (0,3,5,2,4,1) is (0,5,3,1,4,2)
    scale = scale_shuffled.view(sm // 32, sn // 8, 4, 16, 2, 2)
    scale = scale.permute(0, 5, 3, 1, 4, 2).contiguous()
    scale = scale.view(sm, sn)
    return scale[:orig_m, :orig_n]

# Usage (Luma AMD Speedrun task format):
B_scale = e8m0_unshuffle(B_scale_sh.view(torch.uint8), orig_m=n, orig_n=k // 32)
```

**Cost**: ~0.1 µs (just a tensor view + permute). Saves ~15 µs vs `dynamic_mxfp4_quant(B)`.

**Requirement**: B_scale_sh padded dims must be divisible by 32 (M) and 8 (N), which
is guaranteed if `B_scale_sh` was created by `e8m0_shuffle`.

## matmul_fp4 Wrapper Internals (tile override logic)

Full wrapper source obtained via `inspect.getsource` (March 2026). Key behaviours:

```python
def matmul_fp4(a, b, c, a_scales, b_scales, block_m=None, ...):
    M, K = a.shape
    _, N = b.shape   # b is [N, K//2]
    if block_m is None:
        selector = _make_matmul_selector(M, N, K, "f4", "f4", ...)
        block_m, block_n, block_k = selector.block_m, selector.block_n, selector.block_k
        group_size_m = selector.group_m
        num_xcds = selector.num_sms    # 8 on MI355X
        # TILE OVERRIDE: if auto-selected tile < matrix dim, force 128
        if block_m < M: block_m = 128
        if block_n < N: block_n = 128
        if block_k < K: block_k = 128  # K here is in bf16 elements
    # Re-derive K from packed A shape (a.shape[1] * 2 = K in fp4 elements)
    M = a.shape[0]; K = a.shape[1] * 2; N = b.shape[0]
    b = b.T.contiguous()  # Transpose B internally before passing to Triton kernel
    chunk_size = min(group_size_m**2, max(1, total_tiles // num_xcds))
    fp4_matmul[grid](a, b, c, ...)
```

**Key insight:** The wrapper transposes B internally. The Triton kernel `fp4_matmul`
receives B as `[K//2, N]` (K-major), so B_scale must still be `[N, K//32]` (N-first).

## Performance (MI355X, 8 benchmark shapes)

| Kernel | Geomean | Notes |
|--------|---------|-------|
| `aiter.gemm_a4w4` | ~24 µs | Current best — CK kernel |
| `tritonblas.matmul_fp4` + e8m0_unshuffle | ~26 µs | No B re-quant, Triton kernel |

| Competition leader | ~9.7 µs | 2.49x gap vs both approaches |

**Note**: tritonblas is slightly slower than aiter despite Origami scheduling. The gap
to the competition leader (~9.7 µs) suggests persistent/split-K optimizations or CK
assembly kernels beyond what tritonblas provides.

## A-Quantization Is the Pipeline Bottleneck

Full end-to-end timing breakdown (MI355X, geomean across 8 benchmark shapes):

| Step | Time |
|------|------|
| `dynamic_mxfp4_quant(A)` | 33–39 µs |
| `e8m0_unshuffle(B_scale_sh)` | ~0.1 µs |
| `matmul_fp4(A_q, B_q, C, A_scale, B_scale)` | 29–58 µs |
| **Total pipeline** | **66–92 µs geomean** |

The A quantization kernel alone is 33–39 µs — roughly **equal to** or larger than the
GEMM itself for small shapes. This makes fusing quant into GEMM the most promising
optimization path.

## Why Other Quant Methods Fail with tritonblas

Tested via nibble-level probe (March 2026): all three aiter quant methods
(`dynamic_mxfp4_quant`, `get_hip_quant`, `get_triton_quant`) produce **identical nibble
ordering** in packed fp4 bytes. The ~1–13% byte-level differences are from **rounding
in E8M0 scale computation** (floor(log2(amax)) uses different precision).

Despite small data differences, GEMM errors are significant:

| A quant method | Tritonblas GEMM max error | Why |
|----------------|--------------------------|-----|
| `dynamic_mxfp4_quant` | 0.0 (exact) | Patched #975 kernel |
| `get_hip_quant` | 6.5–15.25 | Scale rounding mismatch |
| `get_triton_quant` | 6.5–15.25 | Scale rounding mismatch |

**Key insight:** Nibble-swapping the fp4 data made errors WORSE (166–442 error). The
incompatibility is in **scale values**, not bit packing. Only `dynamic_mxfp4_quant`
produces scales that match what the tritonblas Origami kernel expects.

## Fused Quant+GEMM Kernel (Experimental, unverified)

A custom Triton kernel fusing bf16→fp4 A quantization directly into the GEMM eliminates
the 33–39 µs A quantization kernel launch. Architecture:

```python
@triton.jit
def _fused_quant_gemm_kernel(A_ptr, B_ptr, C_ptr, B_scale_ptr, ...):
    # Origami chiplet-aware scheduling (from tritonblas fp4_matmul source)
    for k_start in range(0, K, BLOCK_K):
        a_bf16 = tl.load(A_ptr + ...)      # Load bf16 A tile
        # Compute E8M0 scale in registers
        a_amax = tl.max(tl.abs(a_reshaped).to(tl.float32), axis=2)
        a_scale = floor(log2(a_amax)) + 127  # E8M0
        a_fp4 = quantize_to_fp4(a_bf16, a_scale)
        b = tl.load(B_ptr + ...)
        b_scale = tl.load(B_scale_ptr + ...)
        acc = tl.dot_scaled(a_fp4, a_scale, "e2m1", b, b_scale, "e2m1", acc=acc)
    tl.store(C_ptr + ..., acc.to(tl.bfloat16), ...)
```

# Direct HIP Kernel Dispatch via ctypes (AMD MI355X)

## Problem

Python wrapper overhead (~20-25µs per kernel launch) creates an API ceiling.
Leaders achieve ~33µs (MLA), ~110µs (MoE), ~4.3µs (GEMM) with single fused
kernels that have zero Python dispatch overhead. Can we bypass the wrappers?

### Kernel Name Mangling

CK kernels use C++ name mangling. Pattern:

```python
def mangle_kernel_name(basename_without_co: str) -> bytes:
    """Convert .co filename to C++ mangled kernel name.

    Example: 'mla_a8w8_qh16_qseqlen1_gqaratio16_ps'
    → '_ZN5aiter36mla_a8w8_qh16_qseqlen1_gqaratio16_psE'
    where 36 = len(basename)
    """
    return f"_ZN5aiter{len(basename_without_co)}{basename_without_co}E".encode("utf-8")
```

# DeepSeek MLA Decode: Flash Attention Architectural Gap

## Problem

The aiter `mla_decode_fwd` 3-stage pipeline has ~100-150 µs fixed overhead regardless of
batch size. For small decode workloads (bs ≤ 64), the actual attention compute is <10 µs —
the pipeline overhead is the bottleneck, NOT the compute.

Our best hybrid approach (three-regime einsum + aiter) achieves **69.5 µs ranked geomean** on MI355X.
Competition leaders achieve **4.3 µs** — a 16x gap that cannot be closed by parameter tuning.

## Architectural Context: DeepSeek R1 MLA

MLA (Multi-head Latent Attention) uses an **absorbed** formulation:
- Q: `(total_q, num_heads, 576)` — already has rope/projection absorbed (QK head dim = 576)
- KV: `(total_kv, 1, 576)` — single KV head, fused K and V into one latent buffer
- V is sliced from KV: `V = KV[:, :, :512]` (first 512 of 576 dims)
- Output: `(total_q, num_heads, 512)` — value head dim = 512

This is GQA with 1 KV head and 16-32 Q heads (128 total // tensor parallelism 4-8).

### Key Dimensions (DeepSeek R1, TP=4)

```python
NUM_HEADS = 32        # 128 // TP=4
NUM_KV_HEADS = 1      # MLA always has 1 KV head
QK_HEAD_DIM = 576     # for score computation: Q @ KV^T
V_HEAD_DIM = 512      # for value: KV[:, :, :512]
SM_SCALE = 1.0 / sqrt(576)  # attention temperature
```

## The 3-Stage Pipeline Overhead

aiter's `mla_decode_fwd` runs:
1. `get_mla_metadata_v1()` — computes work distribution, fills 6 metadata tensors (~5-20 µs)
2. `mla_decode_stage1_asm_fwd()` — split-K attention kernel, produces partial results (~70-120 µs)
3. `mla_decode_reduce_fwd()` — parallel reduce of partial results (~10-30 µs)

**Total fixed overhead: ~100-150 µs.** For bs=4, kv=1024 (4096 KV tokens), the actual
attention compute on 32 heads is trivial. The metadata + split-K + reduce dominate entirely.

## What the 4.3 µs Leaders Are Likely Doing

Leaders (Jayluci4, n8_gr8_ at 4.3 µs on MI355X) almost certainly use a **fused Flash
Attention-style kernel** that:

1. Processes Q in tiles (BLOCK_M), iterates over KV in tiles (BLOCK_N)
2. Fuses score, softmax, and value accumulation into a SINGLE kernel (Flash Attention v2 pattern)
3. Eliminates the 3-stage pipeline overhead entirely — one kernel launch per call
4. Handles GQA by broadcasting the 1 KV head across all 32 Q heads within the kernel

For bs=4, kv=1024: `4 * 1 * ceil(32/GROUP) * ceil(1024/BLOCK_N)` = a handful of thread blocks.
A single kernel launch at ~4 µs is consistent with this.

## Critical Layout Constraint: K ≠ V Head Dimension

MLA's fused KV buffer has:
- K dimension: 576 (for score: `Q @ KV^T` uses full 576)
- V dimension: 512 (for value: `@V` uses only first 512 of each KV row)

**Standard Flash Attention assumes K_dim == V_dim.** `fav3_sage_mxfp4` and other standard
attention kernels FAIL here because they expect separate K, V tensors with the same head_dim.

Any custom Flash Attention for MLA must:
```python
# Score computation: use full KV dim (576)
scores = tl.dot(q_tile, kv_tile.T)  # q_tile: [BM, 576], kv_tile: [BN, 576]

# Value extraction: slice first 512 dims of KV
v_tile = kv_tile[:, :512]           # [BN, 512]
acc += tl.dot(weights, v_tile)      # acc: [BM, 512]
```

## Custom Triton Flash Attention for MLA (If No Library Available)

If no library is available, write a Flash Attention v2 variant:

```python
@triton.jit
def mla_decode_flash_kernel(
    Q_ptr, KV_ptr, O_ptr,
    # strides, shapes...
    BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr,
    QK_DIM: tl.constexpr,  # 576
    V_DIM: tl.constexpr,   # 512
    SM_SCALE: tl.constexpr,
):
    # Grid: (num_q_heads * batch, cdiv(total_q, BLOCK_M))
    # Each thread block processes BLOCK_M query positions

    m_i = tl.full([BLOCK_M], float("-inf"), dtype=tl.float32)  # running max
    l_i = tl.zeros([BLOCK_M], dtype=tl.float32)                # running sum
    acc = tl.zeros([BLOCK_M, V_DIM], dtype=tl.float32)         # accumulator

    for kv_start in range(0, total_kv, BLOCK_N):
        kv_tile = tl.load(KV_ptr + kv_start * stride_kv ...)   # [BN, 576]

        # Score: full QK dim
        qk = tl.dot(q, kv_tile.T) * SM_SCALE   # [BM, BN]

        # Flash Attention safe-softmax update
        m_new = tl.maximum(m_i, tl.max(qk, 1))
        alpha = tl.exp(m_i - m_new)
        p = tl.exp(qk - m_new[:, None])
        l_i = alpha * l_i + tl.sum(p, 1)
        acc = alpha[:, None] * acc + tl.dot(p, kv_tile[:, :V_DIM])  # V is first 512 dims
        m_i = m_new

    # Normalize
    acc = acc / l_i[:, None]
    tl.store(O_ptr + ...)
```

Key: `kv_tile[:, :V_DIM]` extracts V from the fused KV buffer without extra memory allocation.

## Phase 7: Q-Padded tl.dot (Split-D) — CONFIRMED SLOWER (March 2026)

**The Q-padding + tl.dot approach was implemented and benchmarked with the split-D trick.**
**Result: 2-34x SLOWER than torch.einsum. DO NOT USE.**

**Split-D trick** (to avoid QK_PAD=1024 shared memory overflow):
- Split QK_DIM=576 into 512+64 (both power-of-2, no arange error)
- Score = Q1@KV1^T + Q2@KV2^T (two tl.dot calls)
- Reuse KV[:,:512] as V tile (zero extra loads)
- Shared memory: 160KB fits vs 393KB for QK_PAD=1024

EINSUM_MAX_TOTAL_KV = 65536   # 64k tokens → einsum wins

    if total_kv <= 16384:   return 4

# Regime 1: Small batch — bypass aiter pipeline
if bs <= EINSUM_MAX_BS and total_kv <= EINSUM_MAX_TOTAL_KV:
    kv = kv_data["bf16"].view(bs, kvseqlen, 576)
    q_r = q.view(bs, qseqlen, nheads, 576)
    scores = torch.einsum("bqnh,bsh->bnqs", q_r, kv).mul_(SM_SCALE)

    v = kv[:, :, :512]
    out = torch.einsum("bnqs,bsd->bqnd", weights, v)

# Regime 2: Medium — aiter a16w8
# Regime 3: Large — aiter a8w8 with Q quantized to fp8

## The Quantization Bottleneck (Fundamental)

For benchmark shapes (geomean ~21µs total), quantization alone costs ~26µs:

```
dynamic_mxfp4_quant: ~26µs (constant regardless of M/N/K)
e8m0_shuffle:        ~1-3µs

─────────────────────────────
Total:               ~34-39µs before fused quant optimization
```

**The leader at 9.7µs must either:**
1. Fuse quant into the GEMM kernel (single launch, no Python dispatch between ops)
2. Use a pre-quantized input path (unlikely — task generates bf16 A)
3. Have a custom ASM quant kernel

No Python-level API composition can reach 9.7µs when quant dispatch alone costs 26µs.

## E8M0 Scale Algorithm (Exact, from aiter source)

```c
// IEEE 754 bit manipulation: round mantissa to nearest, clear mantissa bits
unsigned int rounded = (amax_u32 + 0x200000u) & 0xFF800000u;
int exp_biased = (rounded >> 23) & 0xFF;
int scale_byte = exp_biased - 2;  // E8M0 with fp4 normalization
float quant_scale = exp2f(129.0f - exp_biased);
```

The `+0x200000` adds 0.5 ULP for round-to-nearest-even. The `-2` accounts for fp4 e2m1
max value of 6.0 (= 2^2 × 1.5). This differs from `floor(log2(amax)) + 127`.

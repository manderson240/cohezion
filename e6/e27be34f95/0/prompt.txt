- ~10 requests/second global rate limit
- Per-mode timeouts: test=180s, benchmark=180s (overridden per competition in task.yml)
- **Total workflow timeout: ~12 minutes** — the entire GitHub Actions run must complete within this
- Use `--mode test` first, then `--mode benchmark`, then `--mode leaderboard`

## aiter JIT Compilation Times (Luma AMD Speedrun)

aiter builds JIT modules on first use. These builds happen **inside** the 12-minute workflow timeout:

| JIT Module | Build Time |
|-----------|-----------|
| `module_moe_sorting` | ~25s |
| `module_moe_ck2stages_fp4x2_*` | ~103s |

# aiter Kernel Parameter Semantics (AMD MI355X)

## Problem

aiter's `fused_moe` and `mla_decode_fwd` have parameters that sound like performance flags
but actually change computation or have counter-intuitive effects on MI355X.

## fused_moe: doweight_stage1

### What it does

`doweight_stage1=True` moves the `topk_weights` multiplication from **stage 2** (after SiLU
activation) to **stage 1** (before SiLU activation).

- `doweight_stage1=False` (default): `output = SiLU(gate(x)) * up(x)`, then multiply weights in stage 2
- `doweight_stage1=True`: multiply weights in stage 1 BEFORE activation

### Why it causes correctness failure

SiLU is a **nonlinear** activation. Multiplying weights before vs after a nonlinear activation
produces mathematically different results:

```
w * SiLU(gate(x)) * up(x)   ≠   SiLU(w * gate(x)) * (w * up(x))
```

This is not a subtle numerical difference — it produces ~80% element mismatches with 10-30%
per-element error (well above the 5e-2 tolerance for MoE).

**Rule:** `doweight_stage1=True` only produces correct results for linear activations (ReLU-like),
not for SiLU/GELU. For MXFP4 MoE with SiLU, always use `doweight_stage1=False`.

## fused_moe: OPUS Sorting (AITER_USE_OPUS_MOE_SORTING)

Setting `os.environ["AITER_USE_OPUS_MOE_SORTING"] = "1"` before calling `fused_moe` switches
to the OPUS sorting backend (`moe_sorting_opus_fwd` instead of `moe_sorting_fwd`).

**Correctness:** OPUS sorting only changes token dispatch order — the computation is identical.
Setting this env var passes correctness tests (verified, max error 0.015625).

**Performance on MXFP4 variant:** NO EFFECT. The env var is not wired into the fp4x2 code path
in `fused_moe.py`. JIT still builds `module_moe_sorting` (not `module_moe_sorting_opus`), and
benchmark times are identical to reference. This was verified by running the full benchmark suite.

## fused_moe: block_size_M

Override the auto-selected tile size for the token dimension:

```python
fused_moe(..., block_size_M=64)  # or 32, 128
```

Default is `-1` (auto-selects from tuned CSV configs). For MXFP4 with different model configs:
- bs=8 (small): auto-selects `block_m=32`
- bs=128 (medium): auto-selects `block_m=64`

**DANGER: Forcing `block_size_M=64` causes GPU memory access faults on benchmark configs.**
When `estimated_m_per_expert` is low (e.g., bs=16 with 256 experts = ~1 token/expert), a tile
size of 64 exceeds the actual data bounds and causes a hardware-level `Memory access fault by
GPU node-2`. The auto-tuner correctly selects smaller tiles for these shapes. **Never override
`block_size_M` without verifying it's safe for ALL shapes in the benchmark suite.**

## mla_decode_fwd: fast_mode is SLOWER on MI355X

### What it does

`fast_mode=True` in `get_mla_metadata_info_v1` and `get_mla_metadata_v1` changes the work
distribution strategy: `(bs + cu_num) * tiles` work items vs `tile_cnt * cu_num`.

### Test results (MI355X, DeepSeek R1 MLA, fp8)

| Config | fast_mode=False (reference) | fast_mode=True, adaptive splits | fast_mode=True, fixed splits=32 |
|--------|----------------------------|--------------------------------|--------------------------------|
| bs=4, kv=1024 | ~131 us | ~154 us | ~152 us |
| bs=256, kv=8192 | ~462 us | ~536 us | ~542 us |
| Geomean | ~191 us | ~224 us (+17%) | ~232 us (+21%) |

**fast_mode=True is 17-21% SLOWER than fast_mode=False on MI355X for decode workloads.**

The reference implementation already uses well-tuned defaults. Changing `fast_mode` to `True`
and `num_kv_splits` from 32 to adaptive values (4-16 depending on batch size) both made
performance worse, not better.

**Rule:** For MLA decode on MI355X with the DeepSeek R1 forward_absorb architecture, use:
```python
fast_mode=False
num_kv_splits=32
intra_batch_mode=True
```

## fused_moe: AITER_KSPLIT (Environment Variable)

`AITER_KSPLIT=N` switches `fused_moe` between two entirely different kernel implementations:

- **KSPLIT=0 (default / unset):** Uses `module_moe_ck2stages_fp4x2_fp4x2_preshuffle_*` — MXFP4-optimized CK kernels, fast for dense token distributions
- **KSPLIT>0:** Uses `module_moe_cktile2stages` — generic cktile kernels (not MXFP4-specialized), but better for sparse token distributions

**Critical:** AITER_KSPLIT is **completely ignored** for shapes with pre-tuned CSV configs (e.g., 257-expert DeepSeek-V3 configs in `tuned_fmoe.csv`). Only affects shapes that fall back to default kernel selection.

### Benchmark Data (MI355X, dhidden=7168, with AITER_BYPASS_TUNE_CONFIG=1)

**33-expert shapes (dexp=512/2048):**

| Shape | KSPLIT=0 | KSPLIT=2 | Winner |
|-------|----------|----------|--------|
| bs=16, 33 exp | 94.5 µs | 60.6 µs | cktile (-36%) |
| bs=128, 33 exp | 130 µs | 109 µs | cktile (-16%) |
| bs=512, 33 exp, dexp=512 | 214 µs | 253 µs | CK (+18%) |
| bs=512, 33 exp, dexp=2048 | 352 µs | 703 µs | CK (+100%) |

**257-expert shapes (dexp=256, TP=8 DeepSeek-V3) — BYPASS_TUNE required:**

| bs=16, 257E (est_m≈0) | 152.7 µs | 95.1 µs | 91.3 µs | KSPLIT=4 (-40% vs CK) |

**Rule:** `estimated_m_per_expert = topk_ids.numel() // num_experts`
- `estimated_m >= 50` → KSPLIT unset (CK path, dense shapes)
- `num_experts >= 200 AND estimated_m < 10` → KSPLIT=4 (large expert count, tiny per-expert matrices benefit from K-parallelism)
- `estimated_m < 50` (other) → KSPLIT=2 (cktile path, moderate sparse)

**Why KSPLIT=4 helps for 257E but not 33E:** 257E shapes have dexp=256 (small weight matrices per expert). With K=256, KSPLIT=4 splits K into 64-element chunks which fits better in cache. 33E shapes have dexp=512+ (larger matrices where KSPLIT=2 already saturates K-parallelism).

### Expert-Count-Aware Adaptive KSPLIT Pattern

Setting env var per-call works because AITER checks it at dispatch time (not module import):

```python
import os

num_experts = gate_up_weight_shuffled.shape[0]
estimated_m = topk_ids.numel() // num_experts

if estimated_m >= 50:
    # Dense: CK MXFP4-optimized path
    os.environ.pop("AITER_BYPASS_TUNE_CONFIG", None)
    os.environ.pop("AITER_KSPLIT", None)
elif num_experts >= 200 and estimated_m < 10:
    # Large expert count, very sparse: KSPLIT=4 for K-parallelism
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"
    os.environ["AITER_KSPLIT"] = "4"
else:
    # Moderately sparse or small expert count: KSPLIT=2
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"
    os.environ["AITER_KSPLIT"] = "2"

return fused_moe(...)
```

### Stderr Diagnostics: Reading Kernel Path Selection

The aiter log output tells you definitively which path was taken — critical for debugging KSPLIT behavior:

**CSV-tuned shape (KSPLIT ignored):**
```
[aiter] [fused_moe] using 2stage (kernelName1='moe_ck2stages_gemm1_256x32x128x128_...', kernelName2='...') for (...)
```
The parenthetical `(kernelName1=...)` means a specific CSV-tuned kernel was selected. AITER_KSPLIT has no effect here.

**Default shape (KSPLIT applies):**
```
[aiter] run_1stage = False, ksplit = 2 q_type = QuantType.per_1x32 block_m = 32 use_nt = True, estimated_m_per_expert = 4
[aiter] [fused_moe] using 2stage default for (...)
```
The `using 2stage default` message confirms KSPLIT was read and applied. `ksplit = 2` confirms the cktile path was selected.

**Key log fields:**
- `ksplit = 0` → MXFP4-optimized CK path (KSPLIT unset or =0)
- `ksplit = 2` → cktile path (AITER_KSPLIT=2)
- `use_nt = True` → non-temporal memory loads enabled (AITER_USE_NT env var)
- `estimated_m_per_expert = N` → the computed token density value

### JIT Cost of KSPLIT>0

Enabling KSPLIT>0 for the first time triggers **additional JIT builds**:
- `module_moe_cktile2stages`: ~110s
- `module_activation`: ~22s

Total additional JIT time: ~132s. Combined with base MoE JIT (~128s), this pushes total JIT to ~260s, leaving ~7.5 min of compute time in a 12-min Popcorn workflow.

## fused_moe: AITER_BYPASS_TUNE_CONFIG (Environment Variable)

`AITER_BYPASS_TUNE_CONFIG=1` forces the **heuristic path** for all shapes, even those with pre-tuned CSV configs:

```python
if cfg is None or int(os.environ.get("AITER_BYPASS_TUNE_CONFIG", "0")):
    # Heuristic path — AITER_KSPLIT applies here
    ksplit = get_ksplit(token, topk, expert, inter_dim, model_dim)
    ...
```

**Use case:** When CSV-tuned configs exist (e.g., 257-expert DeepSeek TP=8 shapes) but you want to test the cktile (split_k) path for cold-cache benchmarks.

Combined strategy:
```python
if estimated_m < 50:
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"  # Ignore CSV for sparse shapes
    os.environ["AITER_KSPLIT"] = "2"              # Force cktile path
else:
    os.environ.pop("AITER_BYPASS_TUNE_CONFIG", None)
    os.environ.pop("AITER_KSPLIT", None)           # CK path for dense
```

**Risk:** CSV configs were pre-tuned (possibly at hot cache). Cold-cache benchmarks may or may not prefer cktile — requires empirical testing.

**AITER_ONLINE_TUNE Warning:** `AITER_ONLINE_TUNE=1` blocks on running `gemm_moe_tune.py` (a full benchmark sweep) before returning for the FIRST call. This adds many minutes to the first call and will TIMEOUT a 12-minute workflow.

## fused_moe: cktile Path Trigger Conditions

The cktile kernels (`cktile_moe_stage1` + `cktile_moe_stage2`) are used instead of CK when ALL of:
1. `dtype in [bf16, fp16]`
2. `q_type == QuantType.per_1x32` (MXFP4)
3. `q_dtype_w in [dtypes.fp4x2]` (MXFP4 weights)
4. **`ksplit > 1`** — set by AITER_KSPLIT or get_ksplit()
5. **`is_shuffled=True`** — requires pre-shuffled weights (shuffled variants in submission)

If any condition is false, the CK path is used. Using `gate_up_weight_shuffled` and `down_weight_shuffled` (shuffled=True) is required for cktile.

3. **Print source code first** — if you must combine, print `inspect.getsource()` before CSV content

# aiter MXFP4 API Limitations (AMD MI355X)

## Overview

MXFP4 ("Microscaling FP4") packs **2 fp4 values per uint8 byte** (`torch.REDACTED`),
with an E8M0 block-32 scale factor. This packing creates invisible API contract mismatches
across aiter's kernels. Discovered during Luma AMD Speedrun competition (March 2026, MI355X).

---

## Limitation 1: `gemm_afp4wfp4` rejects PyTorch native fp4 dtype

### Symptom

```
KeyError: 'REDACTED'
```

Raised inside `gemm_afp4wfp4` when passed tensors with `dtype=torch.REDACTED`.

### Root Cause

`gemm_afp4wfp4` is a Triton-based kernel that expects tensors **viewed as uint8** (raw packed
bytes), not PyTorch's native `torch.REDACTED` dtype. The kernel's internal dtype
dispatch table doesn't have an entry for the native PyTorch fp4 type.

### Failing pattern

```python
from aiter.ops.triton.gemm.basic.gemm_afp4wfp4 import gemm_afp4wfp4
quant_func = aiter.get_torch_quant(QuantType.per_1x32)
A_q, A_scale = quant_func(A, quant_dtype=dtypes.fp4x2)
# A_q.dtype == torch.REDACTED  → KeyError in gemm_afp4wfp4
out = gemm_afp4wfp4(A_q, B_q, A_scale, B_scale, dtype=dtypes.bf16)
```

### Fix

View ALL tensors (data + scales) as uint8 before passing to gemm_afp4wfp4:

```python
out = gemm_afp4wfp4(A_q.view(torch.uint8), B_q.view(torch.uint8),
                    A_scale.view(torch.uint8), B_scale.view(torch.uint8),
                    dtype=dtypes.bf16)
```

**Note:** The E8M0 scale dtype (`torch.float8_e8m0fnu`) also triggers a KeyError.
Both data AND scales need uint8 views. The kernel runs successfully after this fix,
but may still produce wrong results if the quantization backend mismatches (see Limitation 3).

### Workaround

Fall back to `ref_kernel` (which uses `get_triton_quant` → `gemm_a4w4` with pre-shuffled inputs):

```python
from reference import ref_kernel
return ref_kernel(data)
```

## Limitation 2: MLA ASM kernel rejects MXFP4 KV cache

### Symptom

```
RuntimeError: mla_decode_stage1_asm_fwd:only support head_size == KV.size(3) for now
```

### Root Cause

The MLA decode ASM kernel (`mla_decode_stage1_asm_fwd`) hardcodes the assertion:
`head_size == KV.size(3)`. For normal KV: `KV.shape = (total_kv, 1, NUM_KV_HEADS, 576)`, so
`KV.size(3) = 576 = head_size`. But MXFP4 packs 2 values per byte, so:
`MXFP4_KV.shape = (total_kv, 1, NUM_KV_HEADS, 288)` (576 / 2 = 288). The assertion fails.

### Data format context

The `kv_data` dict in `mixed-mla` input provides three KV cache formats:
```python
kv_data = {
    "bf16": tensor,              # shape (total_kv, 1, 576) — highest precision
    "fp8":  (tensor, scale),     # shape (total_kv, 1, 576) — 8-bit
    "mxfp4": (tensor, scale),    # shape (total_kv, 1, 288) — 4-bit packed (2x per byte)
}
```

### Status

**No aiter MLA kernel supports MXFP4 KV** in the tested version. There is no
MXFP4-aware MLA decode kernel available to bypass the ASM constraint. The only viable
paths are fp8 or bf16 KV.

### Workaround

Use fp8 KV (the reference implementation path):

```python
kv_buffer_fp8, kv_scale_fp8 = kv_data["fp8"]
return _run_mla(q_fp8, q_scale, kv_buffer_fp8, kv_scale_fp8, qo_indptr, kv_indptr, config)
```

## Limitation 3: ALL `get_*_quant` backends fail with `gemm_a4w4` from submission.py — use `dynamic_mxfp4_quant`

### Symptom

All three quantization backends (`get_triton_quant`, `get_torch_quant`, `get_hip_quant`)
produce wrong GEMM results (81-95% element mismatches, max error 6-165) when their output
is passed to `aiter.gemm_a4w4` from `submission.py`.

### Root Cause (CORRECTED March 2026)

Previously diagnosed as "JIT callsite sensitivity in `gemm_a4w4_asm`". This was WRONG.

The actual root cause is that `get_triton_quant(QuantType.per_1x32)` dispatches to the
**unpatched `fp4_utils.py` kernel** (ROCm/aiter issue #974), which produces systematically
wrong quantization output. The `get_torch_quant` and `get_hip_quant` failures are a
separate issue: their quantization outputs don't match the `gemm_a4w4` input contract.

**Evidence the old diagnosis was wrong:**
- `get_torch_quant` (pure PyTorch, NO Triton JIT) also fails → not a JIT callsite issue
- `get_hip_quant` (HIP C, NOT Triton) also fails → not a Triton issue
- Error values differ between approaches (165, 166, 200 at (0,0)) → inconsistent with single dispatch bug
- `dynamic_mxfp4_quant` + `gemm_a4w4` from submission.py works perfectly (0.0 max error) ← CONFIRMED FIX

### THE FIX: Use `dynamic_mxfp4_quant` from `aiter.ops.triton.quant`

`dynamic_mxfp4_quant` is the patched Triton kernel (ROCm/aiter PR #975). It bypasses the
buggy `get_triton_quant` dispatch path entirely.

```python
from aiter import dtypes
import aiter
from aiter.ops.triton.quant import dynamic_mxfp4_quant
from aiter.utility.fp4_utils import e8m0_shuffle

def custom_kernel(data: input_t) -> output_t:
    A, B, B_q, B_shuffle, B_scale_sh = data
    x_fp4, bs_e8m0 = dynamic_mxfp4_quant(A)
    A_q = x_fp4.view(dtypes.fp4x2)
    A_scale_sh = e8m0_shuffle(bs_e8m0).view(dtypes.fp8_e8m0)
    return aiter.gemm_a4w4(
        A_q, B_shuffle, A_scale_sh, B_scale_sh,
        dtype=dtypes.bf16, bpreshuffle=True,
    )
```

**Result:** 0.0 max error on all 6 benchmark shapes. Verified via Popcorn CLI `--mode test`.

### Quantization backends — status summary

| Function | Backend | Status from submission.py |
|----------|---------|--------------------------|
| `dynamic_mxfp4_quant` | Triton (patched #975) | ✅ WORKS — 0.0 max error |
| `get_triton_quant` | Triton (unpatched, routes to fp4_utils.py #974) | ❌ 89-95% mismatch (wrong quant output) |
| `get_torch_quant` | Pure PyTorch | ❌ ~82% mismatch (different rounding/layout) |
| `get_hip_quant` | HIP compiled C kernel | ❌ 81-95% mismatch (layout mismatch) |

### Note on `fused_moe` internal backend

`fused_moe.py` line 15: `from aiter import get_hip_quant as get_quant`.
The internal quantization backend for MoE is HIP. This is why `fused_moe` called from
`submission.py` works correctly (0.015625 max error) — the hip_quant output matches
the CK stage 1 kernel's input contract for MoE, just not for `gemm_a4w4`.

## Limitation 4: MXFP4 MoE has no tuned CSV configs

### Context

aiter's `fused_moe` uses auto-tuned CSV configs for kernel selection:
- `a4w4_fmoe.csv` — configs for FP4 MoE (MXFP4, `QuantType.per_1x32`)
- `dsv3_fp4_tuned_fmoe.csv` — DeepSeek V3 FP4 configs (but contains **a8w8_blockscale** data!)

### Finding

For `QuantType.per_1x32` (MXFP4), `get_2stage_cfgs` falls back to **default 2-stage configs**

must come from direct `ck_moe_stage1`/`ck_moe_stage2` kernel calls with custom parameters.

| Variable | Effect |

| `AITER_ONLINE_TUNE=1` | Enable online auto-tuning (slow, do not use in benchmarks) |

## Limitation 5: `fused_moe_2stages` requires pre-sorted tokens

### Symptom

```
TypeError: fused_moe_2stages() missing 6 required positional arguments:
'sorted_weights', 'sorted_expert_ids', 'num_valid_ids', 'moe_out', 'isG1U1', and 'block_size_M'
```

### Root Cause

`fused_moe_2stages` is a lower-level API than `fused_moe`. It expects the caller to have
already run `moe_sorting_fwd` to sort tokens into expert-ordered batches. The 6 extra
positional args are the sorting outputs + configuration.

### Key discoveries

1. **`moe_sorting_fwd` location**: `aiter.moe_sorting_fwd` (package level, JIT-injected).
   NOT importable via `from aiter.fused_moe import moe_sorting_fwd`.
2. **`fused_moe_2stages` signature has positional args** before keyword args. Passing
   `isG1U1` as keyword when it's already occupied positionally causes `got multiple values`.
3. **Incorrect buffer allocation causes GPU memory faults**. The sorting buffers must
   match `fused_moe`'s internal sizing exactly, or CK kernels access out-of-bounds memory.
4. **`cktile_moe_stage1/stage2`** exist with signatures:
   - `cktile_moe_stage1(hidden_states, w1, w2, sorted_token_ids, sorted_expert_ids, num_valid_ids, out, topk, block_m, a1_scale, w1_scale, sorted_weights=None, n_pad_zeros=0, k_pad_zeros=0, bias1=None, activation=Silu, split_k=1, dtype=bf16)`
   - `cktile_moe_stage2(a2, w1, w2, sorted_token_ids, sorted_expert_ids, num_valid_ids, out, topk, w2_scale, a2_scale, block_m, activation=Swiglu, sorted_weights=None, zeros_out=False, n_pad_zeros=0, k_pad_zeros=0, bias2=None)`

### Workaround

Use `fused_moe` directly — it handles sorting and 2-stage dispatch internally:

```python
from aiter.fused_moe import fused_moe
output = fused_moe(hidden_states, w1, w2, topk_weights, topk_ids, ...)
```

## Limitation 8: `aiter.gemm_a4w4` (torch op) does NOT accept `log2_k_split`

### Symptom

```
RuntimeError: Unknown keyword argument 'log2_k_split' for operator 'aiter::gemm_a4w4'
```

### Root Cause

`aiter.gemm_a4w4` is a registered `torch.ops.aiter` operator with a **fixed schema**:

```
aiter::gemm_a4w4(
    Tensor A, Tensor B, Tensor A_scale, Tensor B_scale,
    Tensor? bias=None, ScalarType dtype=15,
    float? alpha=1., float? beta=0., bool? bpreshuffle=True
) -> Tensor
```

`log2_k_split` is NOT in this schema. The torch dispatcher rejects unknown kwargs.

### Lower-level API: `gemm_a4w4_asm`

`aiter.gemm_a4w4_asm` (JIT-dispatched module) does accept `log2_k_split`, but requires:
1. Pre-allocated output tensor: `out = torch.empty(M, N, dtype=dtypes.bf16, device='cuda')`
2. A **kernel name string** — computed internally by `gemm_a4w4`'s dispatch logic
3. Only TWO pre-compiled HIP kernel files exist:
   - `f4gemm_bf16_per1x32Fp4_BpreShuffle_32x128.co` (for padded_m ≤ 32)
   - `f4gemm_bf16_per1x32Fp4_BpreShuffle_192x128.co` (for padded_m > 32)
4. The name mapping from padded_m to tile size (`32x128` vs `192x128`) is internal to the
   `gemm_a4w4` wrapper — NOT exposed via public API

### Rule

Do NOT try to call `gemm_a4w4_asm` directly with custom `log2_k_split` values.
The kernel name selection logic is internal. Use `aiter.gemm_a4w4` with its fixed schema.

## Limitation 9: CUDA/HIP graph replay adds ~50% overhead for short kernel sequences

### Symptom

Submission that uses `torch.cuda.CUDAGraph` or `torch.cuda.graph` for `custom_kernel`
runs **slower** than the non-graph version:

| Config | Without graphs | With graphs |
|--------|---------------|-------------|
| GEMM (6 shapes, geomean) | ~23 µs | ~36 µs |
| Relative overhead | — | +50% |

### Root Cause

CUDA/HIP graph replay requires copying input tensors into the graph's static buffers:
```python
# Three copy_() calls per invocation:
static_A.copy_(A)
static_B_shuffle.copy_(B_shuffle)
static_B_scale_sh.copy_(B_scale_sh)
```

For the GEMM kernel (sequence: `dynamic_mxfp4_quant` + `e8m0_shuffle` + `gemm_a4w4`),
the actual kernel execution is 8-34 µs depending on shape. The `copy_()` overhead from
three input tensor copies equals or exceeds the kernel execution time.

### Rule

CUDA/HIP graphs are only beneficial when:
- Kernel launch overhead is the bottleneck (many small kernels, total time >100 µs)
- Input data is already in static GPU buffers (no copy_ needed)

For the MXFP4 GEMM (2-3 kernels, 8-34 µs total), graphs are SLOWER. Do not use them.

### Verified

Tested on AMD MI355X, March 2026. Geomean 36.0 µs with graphs vs 22.8 µs without.
Abandoned after single benchmark submission confirmed overhead.

## Limitation 10: `fav3_sage_mxfp4` Triton SAGE Attention is incompatible with MLA's KV layout

### Context

`aiter.ops.triton.attention.fav3_sage_attention_mxfp4_wrapper` provides a Triton SAGE
Attention v2 kernel tuned for gfx950 (MI355X). It accepts separate Q, K, V tensors and
internally quantizes them to MXFP4 for compute. Discovered via file-tree introspection.

### Two APIs found

```python
# High-level: takes bf16 Q/K/V, internally quantizes
fav3_sage_mxfp4_func(q, k, v, sm_scale, causal=False, ...)
# → q, k, v must have shape (batch, seqlen, heads, head_dim)

# Lower-level: takes pre-quantized MXFP4 tensors + descale factors
fav3_sage_mxfp4_func(q_mxfp4, k_mxfp4, v_mxfp4, q_desc, k_desc, v_desc, sm_scale, ...)
```

### Why it cannot be used for MLA decode

MLA's fused KV buffer encodes K and V together in a **single tensor** with **different dims**:
- K uses the full 576 dims (QK head dimension for scaled dot product)
- V uses the first 512 dims (value dimension, slice of the 576-dim buffer)
- `fav3_sage_mxfp4` requires **separate K and V tensors with the same `head_dim`**

There is no way to pass K (head_dim=576) and V (head_dim=512) as separate equal-sized tensors
to fav3. The architectural incompatibility is fundamental, not a data layout issue.

### MLA task.yml qseqlen>1 edge case

`task.yml` test shapes include `qseqlen=4` (4-token sequences), while all **benchmark** shapes
are `qseqlen=1` (pure decode). Custom kernels must handle qseqlen>1 correctly for the test to pass
even if the benchmark optimization only targets qseqlen=1.

**Safe pattern:** detect qseqlen from Q tensor shape and fall back to `ref_kernel` for qseqlen>1:

```python
total_q = q.shape[0]
qseqlen = total_q // bs
if qseqlen != 1:
    from reference import ref_kernel
    return ref_kernel(data)
# ... optimized decode path below
```

## Limitation 11: `e8m0_shuffle` IS invertible (CORRECTED March 2026)

### Context

`e8m0_shuffle` was initially thought to be non-invertible due to N-dimension padding.
**This was WRONG** — the shuffle is a deterministic 6D permute and CAN be reversed.

### How e8m0_shuffle works

```python
def e8m0_shuffle(scale):  # [M, N] → [M_padded, N_padded]
    m, n = scale.shape
    # 1. Pad: M→ceil(256), N→ceil(8)
    scale_padded = torch.empty((m+255)//256*256, (n+7)//8*8, ...)
    scale_padded[:m, :n] = scale
    # 2. 6D reshape + permute
    sm, sn = scale_padded.shape
    scale = scale_padded.view(sm//32, 2, 16, sn//8, 2, 4)
    scale = scale.permute(0, 3, 5, 2, 4, 1).contiguous()
    scale = scale.view(sm, sn)
    return scale
```

### e8m0_unshuffle (the inverse)

```python
def e8m0_unshuffle(scale_shuffled, orig_m, orig_n):
    sm, sn = scale_shuffled.shape
    # Inverse permute of (0,3,5,2,4,1) is (0,5,3,1,4,2)
    scale = scale_shuffled.view(sm//32, sn//8, 4, 16, 2, 2)
    scale = scale.permute(0, 5, 3, 1, 4, 2).contiguous()
    scale = scale.view(sm, sn)
    return scale[:orig_m, :orig_n]  # Strip padding
```

**Verified:** `e8m0_unshuffle(B_scale_sh, N, K//32)` produces identical output to
`dynamic_mxfp4_quant(B)[1]` — 0.0 max error on all test shapes.

### Implication: ZERO B re-quantization

With `e8m0_unshuffle`, you can recover un-shuffled B_scale from `B_scale_sh` (the
competition input) WITHOUT calling `dynamic_mxfp4_quant(B)`. Saves ~15 µs per call.

```python
# Instead of: _, B_scale = dynamic_mxfp4_quant(B.contiguous())  # ~15 µs
# Use:
B_scale = e8m0_unshuffle(B_scale_sh.view(torch.uint8), orig_m=n, orig_n=k//32)  # ~0.1 µs
```

### B_q data reuse: also NO re-quantization needed

`B_q` from the task input **exactly matches** `dynamic_mxfp4_quant` output for data:

```python
# Verified on all 4/4 MXFP4 GEMM benchmark shapes:
B_fp4_truth, _ = dynamic_mxfp4_quant(B.contiguous())
assert torch.equal(B_q.view(torch.uint8), B_fp4_truth.view(torch.uint8))  # True
```

**Combined:** Reuse `B_q` (data) + `e8m0_unshuffle(B_scale_sh)` (scale) = zero B overhead.

# Helion → Triton Code Generation Workflow

## Problem

Writing Triton MXFP4 kernels for AMD gfx950 requires understanding correct tile shapes,
scale layouts, and hardware constraints — none of which are documented. Helion (a PyTorch DSL
that compiles to Triton) can generate valid Triton code that can be read and adapted.

## Context

**Helion v0.3.1** is a PyTorch DSL by the PyTorch team that compiles `@helion.kernel`
decorated functions to Triton code. It knows about hardware-specific constraints and
generates correct `tl.dot_scaled` calls including the proper `"e2m1"` format string.

**Availability:** Helion is NOT pre-installed on AMD speedrun runners. Install and use locally
only for code generation.

## Setup: Isolated CPU venv

Create an isolated venv OUTSIDE the project (avoid uv's lockfile overwriting torch):

```bash
python3 -m venv /path/to/project/.venv-helion
source /path/to/project/.venv-helion/bin/activate

# Install CPU-only torch + Helion
pip install helion packaging torch --index-url https://download.pytorch.org/whl/cpu
```

**Critical:** Do NOT use `uv run` or `uv venv` — the project's lockfile pins CUDA/ROCm torch
and will overwrite a manually installed Helion. Use a standalone `python3 -m venv` instead.

## Writing a Helion Kernel

**CRITICAL:** Write kernel to a `.py` FILE, not stdin/heredoc.
Helion uses `inspect.getsource()` which fails on non-file modules (raises `OSError: could not get source code`).

```python
# helion_gemm_test.py — must be a real file, not inline
import torch
import helion
import helion.language as hl

@helion.kernel
def mxfp4_gemm(
    A: torch.Tensor,       # [M, K//2] packed fp4 (uint8)
    A_scale: torch.Tensor, # [M, K//32] e8m0 scales (uint8)
    B: torch.Tensor,       # [K//2, N] packed fp4 (uint8), B transposed
    B_scale: torch.Tensor, # [N, K//32] e8m0 scales (uint8)
) -> torch.Tensor:
    M, K_HALF = A.shape
    _, N = B.shape
    C = hl.zeros([M, N], dtype=torch.bfloat16)
    for tile_m, tile_n in hl.tile([M, N]):
        acc = hl.zeros([tile_m, tile_n], dtype=torch.float32)
        for tile_k in hl.tile([K_HALF]):
            a_tile = A[tile_m, tile_k]
            a_scale_tile = A_scale[tile_m, tile_k // 16]
            b_tile = B[tile_k, tile_n]
            b_scale_tile = B_scale[tile_n, tile_k // 16]
            acc = hl.dot_scaled(a_tile, a_scale_tile, "e2m1", b_tile, b_scale_tile, "e2m1", acc=acc)
        C[tile_m, tile_n] = acc.to(torch.bfloat16)
    return C
```

# tritonblas.matmul_fp4 API (AMD MI355X)

## Problem

`tritonblas.matmul_fp4` is an undiscovered package on the AMD MI355X Popcorn runner
with non-obvious API constraints. It uses Origami chiplet-aware scheduling and a
persistent Triton kernel (`fp4_matmul`) built on `tl.dot_scaled`. Passing native
fp4 dtype causes a silent `KeyError`; layout differs from `aiter.gemm_a4w4`.

## Context / Discovery

Discovered during Luma AMD Speedrun (March 2026) via source introspection:

```python
import tritonblas
# Exports: matmul, matmul_a8w8, matmul_lt, matmul_a8w8_lt, matmul_fp4, OrigamiMatmulSelector
from tritonblas import matmul_fp4, OrigamiMatmulSelector
```

Environment: ROCm 7.1, Triton-ROCm 3.6.0, PyTorch 2.10+rocm7.1, gfx950 (MI355X).

## Signature

```python
matmul_fp4(
    a,           # [M, K//2] torch.uint8  — LHS data (packed fp4)
    b,           # [N, K//2] torch.uint8  — RHS data (packed fp4, row-major NOT transposed)
    c,           # [M, N]    torch.bfloat16 — pre-allocated output (modified in-place)
    a_scales,    # [M, K//32] torch.uint8 — E8M0 scale per 32-element group
    b_scales,    # [N, K//32] torch.uint8 — E8M0 scale per 32-element group
    block_m=None,       # tile size M (auto-tuned by OrigamiMatmulSelector if None)
    block_n=None,       # tile size N
    block_k=None,       # tile size K
    group_size_m=8,     # chiplet grouping
    num_warps=8,
    num_stages=2,
)
```

**Returns:** None — result is written into `c` (in-place).

## Critical: uint8 Views Required

```python
# WRONG — causes "KeyError: 'REDACTED'"
matmul_fp4(A_fp4, B_q, C, A_scale, B_scale)  # native fp4 dtype rejected

# CORRECT — view everything as uint8
matmul_fp4(
    A_fp4.view(torch.uint8),
    B_q.view(torch.uint8),
    C,
    A_scale.view(torch.uint8),
    B_scale,  # already uint8 if from dynamic_mxfp4_quant
)
```

## Layout: B is NOT Transposed

Unlike `aiter.gemm_a4w4` (which expects B transposed as [K//2, N]), `matmul_fp4`
expects B in the **original [N, K//2] row-major layout**:

| Kernel | B data layout | B scale layout |
|--------|--------------|----------------|
| `aiter.gemm_a4w4` | [K//2, N] transposed | [N, K//32] shuffled |
| `tritonblas.matmul_fp4` | **[N, K//2] row-major** | [N, K//32] uint8 |

This means `B_q` from the task input can be used **directly** (no transpose needed).

## Minimal Working Example

```python
import torch
from tritonblas import matmul_fp4
from aiter.ops.triton.quant import dynamic_mxfp4_quant

def mxfp4_gemm_tritonblas(A, B_q, B_scale_sh, m, n, k):
    # Quantize A (full quant needed for activation)
    A_fp4, A_scale = dynamic_mxfp4_quant(A.contiguous())

    # B: reuse B_q from input (identical to dynamic_mxfp4_quant output)
    # B_scale: unshuffle from B_scale_sh to get [N, K//32] uint8
    B_scale = e8m0_unshuffle(B_scale_sh.view(torch.uint8), orig_m=n, orig_n=k // 32)

    C = torch.empty(m, n, dtype=torch.bfloat16, device=A.device)
    matmul_fp4(
        A_fp4.view(torch.uint8),  # [M, K//2]
        B_q.view(torch.uint8),    # [N, K//2] — row-major, no transpose
        C,
        A_scale.view(torch.uint8),  # [M, K//32]
        B_scale,                    # [N, K//32] uint8
    )
    return C
```

## e8m0_unshuffle (skip B re-quantization)

`B_q` from the task input is identical to `dynamic_mxfp4_quant(B)` output — reuse it
directly. The scale `B_scale_sh` (shuffled) can be reversed without re-quantizing B:

```python
def e8m0_unshuffle(scale_shuffled: torch.Tensor, orig_m: int, orig_n: int) -> torch.Tensor:
    """Reverse e8m0_shuffle: recover original [orig_m, orig_n] uint8 scale."""
    sm, sn = scale_shuffled.shape
    # e8m0_shuffle: pad → view(M//32,2,16,N//8,2,4) → permute(0,3,5,2,4,1) → view(2D)
    # Inverse permute of (0,3,5,2,4,1) is (0,5,3,1,4,2)
    scale = scale_shuffled.view(sm // 32, sn // 8, 4, 16, 2, 2)
    scale = scale.permute(0, 5, 3, 1, 4, 2).contiguous()
    scale = scale.view(sm, sn)
    return scale[:orig_m, :orig_n]

# Usage (Luma AMD Speedrun task format):
B_scale = e8m0_unshuffle(B_scale_sh.view(torch.uint8), orig_m=n, orig_n=k // 32)
```

**Cost**: ~0.1 µs (just a tensor view + permute). Saves ~15 µs vs `dynamic_mxfp4_quant(B)`.

**Requirement**: B_scale_sh padded dims must be divisible by 32 (M) and 8 (N), which
is guaranteed if `B_scale_sh` was created by `e8m0_shuffle`.

## matmul_fp4 Wrapper Internals (tile override logic)

Full wrapper source obtained via `inspect.getsource` (March 2026). Key behaviours:

```python
def matmul_fp4(a, b, c, a_scales, b_scales, block_m=None, ...):
    M, K = a.shape
    _, N = b.shape   # b is [N, K//2]
    if block_m is None:
        selector = _make_matmul_selector(M, N, K, "f4", "f4", ...)
        block_m, block_n, block_k = selector.block_m, selector.block_n, selector.block_k
        group_size_m = selector.group_m
        num_xcds = selector.num_sms    # 8 on MI355X
        # TILE OVERRIDE: if auto-selected tile < matrix dim, force 128
        if block_m < M: block_m = 128
        if block_n < N: block_n = 128
        if block_k < K: block_k = 128  # K here is in bf16 elements
    # Re-derive K from packed A shape (a.shape[1] * 2 = K in fp4 elements)
    M = a.shape[0]; K = a.shape[1] * 2; N = b.shape[0]
    b = b.T.contiguous()  # Transpose B internally before passing to Triton kernel
    chunk_size = min(group_size_m**2, max(1, total_tiles // num_xcds))
    fp4_matmul[grid](a, b, c, ...)
```

**Key insight:** The wrapper transposes B internally. The Triton kernel `fp4_matmul`
receives B as `[K//2, N]` (K-major), so B_scale must still be `[N, K//32]` (N-first).

## A-Quantization Is the Pipeline Bottleneck

Full end-to-end timing breakdown (MI355X, geomean across 8 benchmark shapes):

| Step | Time |
|------|------|
| `dynamic_mxfp4_quant(A)` | 33–39 µs |
| `e8m0_unshuffle(B_scale_sh)` | ~0.1 µs |
| `matmul_fp4(A_q, B_q, C, A_scale, B_scale)` | 29–58 µs |
| **Total pipeline** | **66–92 µs geomean** |

The A quantization kernel alone is 33–39 µs — roughly **equal to** or larger than the
GEMM itself for small shapes. This makes fusing quant into GEMM the most promising
optimization path.

## Why Other Quant Methods Fail with tritonblas

Tested via nibble-level probe (March 2026): all three aiter quant methods
(`dynamic_mxfp4_quant`, `get_hip_quant`, `get_triton_quant`) produce **identical nibble
ordering** in packed fp4 bytes. The ~1–13% byte-level differences are from **rounding
in E8M0 scale computation** (floor(log2(amax)) uses different precision).

Despite small data differences, GEMM errors are significant:

| A quant method | Tritonblas GEMM max error | Why |
|----------------|--------------------------|-----|
| `dynamic_mxfp4_quant` | 0.0 (exact) | Patched #975 kernel |
| `get_hip_quant` | 6.5–15.25 | Scale rounding mismatch |
| `get_triton_quant` | 6.5–15.25 | Scale rounding mismatch |

**Key insight:** Nibble-swapping the fp4 data made errors WORSE (166–442 error). The
incompatibility is in **scale values**, not bit packing. Only `dynamic_mxfp4_quant`
produces scales that match what the tritonblas Origami kernel expects.

# Competitive Kernel Optimization: Beyond Parameter Tuning

## Problem

After exhausting all tunable parameters in a library (e.g., aiter's `fused_moe`), ranking
stays in the lower half of the leaderboard. The reference implementation is already
well-optimized; parameter sweeps either have no effect, cause correctness failures, or
degrade performance.

## Context: When to Use This

- All accessible API parameters have been tested (documented in `aiter-kernel-parameter-semantics`)
- Still ranked outside top 20 with >2x gap to leader
- Considering whether to abandon vs. continue the challenge
- Wanting to plan next iteration with higher expected value

## The Decision Hierarchy

### Level 1: Local Proxy (Low effort, immediate)

Before expensive remote submissions, build a local model of the performance space:

**Parse aiter's tuned CSV configs:**
```bash
cat /path/to/aiter/aiter/configs/tuned_fmoe.csv
cat /path/to/aiter/aiter/configs/model_configs/dsv3_fp4_tuned_fmoe.csv
```

These CSVs contain: `(n_experts, batch_size, d_hidden, d_expert, topk, block_m, ...)` → `(kernel_name, cycles)`.
Reading them reveals:
- Which tile configs the auto-tuner selects for which shapes
- Whether there are shape-specific configs that differ from the defaults
- Whether your benchmark shapes have dedicated tuned entries or fall back to defaults

**Roofline model estimate:**
```python
# For MXFP4 GEMM: theoretical peak = GPU_TFLOPS * efficiency
# Compare against actual timing to determine if compute-bound or memory-bound
bytes_per_token = d_hidden * sizeof(fp4)  # input
bytes_weights = d_expert * d_hidden * sizeof(fp4)  # per expert, per token
arithmetic_intensity = 2 * d_hidden * d_expert / bytes_weights  # FLOPs/byte
```

### Level 2: The "Two Builders" Pattern (Medium effort)

From the Anthropic VLIW take-home challenge (see `research/challenges/anthropic_challenge/`):

The winning approach used two separate kernel builders:
- **Builder A (Correctness Anchor):** Delegates to `ref_kernel` or matches reference exactly.
  Never changes. Used to verify correctness of Builder B.
- **Builder B (Custom Explorer):** Reimplements the same computation differently.
  Can be tested against Builder A as ground truth.

For AMD MoE, this means writing a **custom dispatch + GEMM pipeline** that:
1. Uses the same shuffled weights and scales (pre-computed by aiter)
2. Implements its own token sorting (potentially simpler than aiter's)
3. Calls CK GEMM kernels directly instead of through `fused_moe`

```python
# Template: Two Builders pattern for AMD kernel submission
from reference import ref_kernel  # Builder A: correctness anchor

def custom_kernel(data: input_t) -> output_t:
    # Try Builder B; fall back to Builder A on any exception
    try:
        return custom_builder(data)
    except Exception:
        return ref_kernel(data)  # Safety net during development
```

### Level 3: Custom HIP/ASM Kernel (High effort, highest impact)

What top leaderboard entries do:
- Write kernel in HIP C++ or assembly, compiled with `hipcc`
- Bypass the aiter library entirely for the hot path
- Use hardware-specific optimizations (e.g., MI355X matrix core layouts, gfx950 ISA)
- Typically requires familiarity with ROCm programming model

This is only worth pursuing if:
- You have HIP/CUDA experience
- The competition has days remaining (not hours)
- The performance gap justifies the implementation risk

## Phase 4: GEMM Correctness Breakthrough (March 2026)

**Root cause was NOT "JIT callsite sensitivity" — it was an UNPATCHED QUANTIZATION BUG.**

`get_triton_quant(QuantType.per_1x32)` dispatches to the unpatched `fp4_utils.py` kernel
(ROCm/aiter issue #974). The fix is `dynamic_mxfp4_quant` from `aiter.ops.triton.quant`
(PR #975 patched this path). See `amd-triton-jit-callsite-correctness` v1.4.0 for details.

| Kernel | Approach | Outcome | Key Insight |
|--------|----------|---------|-------------|
| GEMM | `dynamic_mxfp4_quant` + `gemm_a4w4` | ✅ 0.0 error, ~24.1 µs | Patched Triton quant bypasses buggy dispatch |
| GEMM | `gemm_a4w4` with `log2_k_split=N` | ❌ RuntimeError | Torch op schema is fixed — no `log2_k_split` kwarg |
| GEMM | `gemm_a4w4_asm` direct call | ❌ Kernel name not found | Only 2 pre-compiled `.co` files; name selection is internal |
| GEMM | CUDA/HIP graph replay | ❌ ~36 µs (+50% overhead) | `copy_()` for 3 static input tensors exceeds kernel time |

**GEMM performance ceiling:** ~24.1 µs vs leader's 9.7 µs (2.49x gap).
The bottleneck is quantization time (~10-13 µs per call), which equals the GEMM time itself.
To close the gap requires a **fused quant+GEMM kernel** — not achievable via public aiter API.

**Key lesson:** When 2+ independent approaches all fail with similar-magnitude errors, suspect
the shared downstream component (here: the quantization output being wrong), not the
infrastructure connecting them (here: wrongly blamed callsite dispatch mechanism).

## Phase 5: MLA Pipeline Bypass (March 2026)

**Key insight: aiter's 3-stage MLA pipeline has fixed overhead that dominates for small batches.**

aiter's `mla_decode_fwd` runs: metadata computation → split-K ASM kernel → parallel reduce.
This pipeline is optimized for large workloads but has ~100-150 µs of constant overhead
regardless of batch size. For small batches (bs=4), the actual compute is tiny — the
overhead is the bottleneck.

**Approach:** Bypass the pipeline entirely with `torch.einsum` for small decode workloads:

```python
# Torch-native: Q@K^T + softmax + @V, all bf16
kv = kv_data["bf16"].view(bs, kvseqlen, 576)
scores = torch.einsum("bnh,bsh->bns", q, kv) * SM_SCALE
weights = torch.softmax(scores, dim=-1)
out = torch.einsum("bns,bsd->bnd", weights, v)
```

**Hybrid routing strategy (optimal):**
- `bs * kvseqlen <= 400_000` tokens: torch-native (pipeline overhead > compute)
- `bs * kvseqlen > 400_000` tokens: ref_kernel/aiter fp8 ASM (bandwidth-bound, fp8 wins)

**Key learnings:**
- `fav3_sage_mxfp4` (Triton SAGE Attention) can't be used for MLA — requires separate K/V
  with same head_dim; MLA's fused buffer (K=576, V=512) is fundamentally incompatible.
- Correctness with bf16 KV vs fp8 reference: max error 5e-05 (tolerance: 8e-03) — excellent.
- The bottleneck shifts from pipeline overhead to memory bandwidth at ~400k tokens.
- Torch einsum is 2x more bandwidth-hungry than fp8 ASM (bf16 vs fp8 KV cache).

**Ceiling reached:** The hybrid approach exhausts pure-torch improvements.
Further MLA speedups require a custom Triton kernel with MXFP4 KV cache (4x bandwidth
savings vs fp8, requires decomposing the fused KV buffer).

# Brainstorming Ideas Into Designs

## Overview

Help turn ideas into fully formed designs and specs through natural collaborative dialogue.

Start by understanding the current project context, then ask questions one at a time to refine the idea. Once you understand what you're building, present the design and get user approval.

<HARD-GATE>
Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it. This applies to EVERY project regardless of perceived simplicity.
</HARD-GATE>

## Anti-Pattern: "This Is Too Simple To Need A Design"

Every project goes through this process. A todo list, a single-function utility, a config change — all of them. "Simple" projects are where unexamined assumptions cause the most wasted work. The design can be short (a few sentences for truly simple projects), but you MUST present it and get approval.

## Checklist

You MUST create a task for each of these items and complete them in order:

1. **Explore project context** — check files, docs, recent commits
2. **Ask clarifying questions** — one at a time, understand purpose/constraints/success criteria
3. **Propose 2-3 approaches** — with trade-offs and your recommendation
4. **Present design** — in sections scaled to their complexity, get user approval after each section
5. **Write design doc** — save to `docs/plans/YYYY-MM-DD-<topic>-design.md` and commit
6. **Transition to implementation** — invoke writing-plans skill to create implementation plan


## The Process

**Understanding the idea:**
- Check out the current project state first (files, docs, recent commits)
- Ask questions one at a time to refine the idea
- Prefer multiple choice questions when possible, but open-ended is fine too
- Only one question per message - if a topic needs more exploration, break it into multiple questions
- Focus on understanding: purpose, constraints, success criteria

**Exploring approaches:**
- Propose 2-3 different approaches with trade-offs
- Present options conversationally with your recommendation and reasoning
- Lead with your recommended option and explain why

**Presenting the design:**
- Once you believe you understand what you're building, present the design
- Scale each section to its complexity: a few sentences if straightforward, up to 200-300 words if nuanced
- Ask after each section whether it looks right so far
- Cover: architecture, components, data flow, error handling, testing
- Be ready to go back and clarify if something doesn't make sense

## After the Design

**Documentation:**
- Write the validated design to `docs/plans/YYYY-MM-DD-<topic>-design.md`
- Use elements-of-style:writing-clearly-and-concisely skill if available
- Commit the design document to git

**Implementation:**
- Invoke the writing-plans skill to create a detailed implementation plan
- Do NOT invoke any other skill. writing-plans is the next step.

## Key Principles

- **One question at a time** - Don't overwhelm with multiple questions
- **Multiple choice preferred** - Easier to answer than open-ended when possible
- **YAGNI ruthlessly** - Remove unnecessary features from all designs
- **Explore alternatives** - Always propose 2-3 approaches before settling
- **Incremental validation** - Present design, get approval before moving on
- **Be flexible** - Go back and clarify when something doesn't make sense

| **Tool integration**         | Figured out how to use tool/API in undocumented way              |
| **Trial-and-error**          | Tried multiple approaches before finding what worked             |
| **Repeatable workflow**      | Multi-step task that will recur; worth standardizing             |
| **External service queries** | Fetched data from Jira, GitHub, Confluence, or other APIs        |
| **User-facing automation**   | Built something user will ask for again (reports, status checks) |

### Step 0.2: Quality Criteria

Skills must be:

- **Reusable**: Will help with future tasks (not just this instance)
- **Non-trivial**: Required discovery, OR is a valuable workflow pattern
- **Verified**: Solution actually worked, not theoretical

### Step 0.3: What NOT to Extract

- Single-step tasks with no workflow value
- One-off fixes unlikely to recur
- Knowledge easily found in official docs

### Step 0.4: Skill Structure

**Location:** `.claude/skills/[skill-name]/SKILL.md`

**Template:**

```markdown
---
name: descriptive-kebab-case-name
description: |
  [CRITICAL: This determines when the skill triggers. Include:]
  - What the skill does
  - Specific trigger conditions (exact error messages, symptoms)
  - When to use it (contexts, scenarios)
author: Claude Code
version: 1.0.0
---

# Skill Name

## Problem

[Clear description of the problem]

## Context / Trigger Conditions

[When to use - exact error messages, symptoms, scenarios]

## Solution

[Step-by-step solution]

## Verification

[How to verify it worked]

## Example

[Concrete example]

## References

[Links to documentation]
```

<details>
<summary>Writing Effective Descriptions</summary>

The description field is CRITICAL for skill discovery:

**Good:**

```yaml
description: |
  Fix for "ENOENT: no such file or directory" errors in npm monorepos.
  Use when: (1) npm run fails with ENOENT, (2) paths work in root but
  not in packages, (3) symlinked dependencies cause failures.
```

**Bad:**

```yaml
description: Helps with npm problems in monorepos.
```

</details>

**Guidelines:**

- **Concise** - Claude is smart; only add what it doesn't know
- **Under 500 lines** - Move large docs to `references/`
- **Examples over explanations** - Show, don't tell

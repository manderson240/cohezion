## Context

Cohezion accumulates rich execution experience (phi_score, 12D FLUME trajectories, coherence
metrics) via JourneyTracker but never uses it to update model weights. Four training pipelines
exist in `flume/` but all generate bash scripts and stop — none execute training. Meanwhile
cloud API costs accumulate on Claude Code / Gemini CLI every session.

The goal is a closed **Cohezion Autonomous Learning Loop (CALL)**: Cohezion's own runtime
experiences become the training signal, AgentJet provides the RL loop, Unsloth provides the
fast fine-tuning backend, and improved local models route away from cloud APIs for familiar
tasks. The Ryzen AI MAX+ 395 with 128GB unified memory is uniquely capable for this — MoE
models like nemotron-3-super (120B total / 12B active) fit entirely in unified memory.

**Critical constraints driving the design:**
- OOM prevention: 128GB is shared CPU+GPU; training + inference models loaded simultaneously
  = crash. Must unload inference models before any training job.
- Context window management: KV cache grows quadratically with context. A 128K context uses
  16x more memory than 32K. Ollama settings + context compression must be first-class.
- AMD training gap: Unsloth Studio AMD training is "coming soon" — Phase 1 uses existing
  llama.cpp/llamafactory path. Unsloth slots in as a drop-in when AMD support ships.

## Architecture

```
COHEZION RUNTIME (online)
  CompoundExecutor → JourneyTracker → phi_score + skill_name
  JourneyFinetuneConverter → data/training/finetune_journeys.jsonl
       │
       ▼
AGENTJET RL LAYER  (src/cohezion/agentjet/)
  CohezionWorkflow  — wraps CompoundExecutor as AgentJet rollout function
  PhiScoreJudger    — phi_score → scalar reward (phi×2-1 maps [0.5,1]→[0,1])
  JourneyTaskReader — reads existing JSONL (no new data pipeline)
  AgentJetTrainer   — orchestrates RL loop; manages model unload before training
  ContextOptimizer  — per-model Ollama settings (num_ctx, flash_attn, rope_scaling)
       │
       ▼
TRAINING BACKEND (phased)
  Phase 1 (now):    llamafactory + llama.cpp via LocalFinetuner (already exists)
  Phase 2 (soon):   Unsloth Studio QLoRA when AMD training ships
  Both phases:      Unsloth Data Recipes (available NOW) for vault→dataset pipeline
       │
       ▼
OLLAMA LOCAL (deployment)
  GGUF export → ollama create cohezion-{domain}-v{n}
  SmartRouter updated to prefer domain-specialized fine-tuned models
  OllamaContextManager ensures models loaded with correct context settings
```

## Context Window Optimization Strategy

Key Ollama environment variables to set/expose as Cohezion config:

```bash
# In .env or cohezion config:
OLLAMA_FLASH_ATTENTION=1       # 50% KV cache reduction — enable always
OLLAMA_KV_CACHE_TYPE=q8_0     # Quantized KV cache (further memory reduction)
OLLAMA_NUM_PARALLEL=1          # During training: 1 parallel request max
OLLAMA_MAX_LOADED_MODELS=2     # During training: max 2 models (reduce from 4)
```

Per-model context window sizing rules (to prevent KV cache OOM):

| Scenario | num_ctx | Rationale |
|----------|---------|-----------|
| Routing models (0.8B-2B) | 32768 | Fast, small KV cache |
| Execution models (9B-30B) | 16384 | Balance quality vs memory |
| Deep reasoning (70B+) | 8192 | Prevent OOM at large sizes |
| During QLoRA training | 2048 | Training doesn't need long context |
| Fine-tuned domain models | 8192 | Adequate for specialized tasks |

The `ContextHarness` in `cohezion/reliability/context_harness.py` already does prompt pruning
targeting phi3:mini. Extend it to use per-model `ModelContextProfile` instead of hardcoded target.

## OOM Prevention Protocol (Non-Negotiable)

Before ANY training job, `AgentJetTrainer._safety_check()` must:

1. Call `OllamaContextManager.get_available_memory_gb()`
2. Estimate training memory: `model_params_gb × 3.0` (weights + gradients + optimizer)
3. If `available < required × 1.2` (20% headroom): raise `OOMRiskError`, abort
4. Call `OllamaContextManager.unload_all_for_training()`:
   - `POST http://localhost:11434/api/generate` with `keep_alive: 0` for each model
   - Wait for confirmation (poll `/api/ps` until empty)
5. After training: call `reload_inference_models()` in finally block

`DegradationDetector` already monitors `memory_pressure_threshold: 0.80` — wire it to
trigger model eviction before training starts.

## Platform Resource Manager (Cross-Session)

**The problem**: Multiple Claude Code sessions, Gemini CLI sessions, background scripts, and
training jobs all compete for 128GB unified memory with no coordination. Each session's
`model_pool_manager.py` is a singleton that sees only its own allocations. A training job
can OOM the machine while a separate session is serving inference.

**The solution**: A lightweight persistent resource daemon that acts as the platform's
memory arbiter — any session must check in before loading models or starting training.

### Architecture

```
┌─────────────────────────────────────────────────────┐
│           RESOURCE DAEMON (persistent)              │
│  Polls Ollama /api/ps every 30s                     │
│  Tracks: loaded_models, reserved_gb, training_locks │
│  Backend: SurrealDB (already running at ws://8000)  │
│  API: HTTP :8765 (lightweight, always-on)           │
└───────────┬────────────────────────┬────────────────┘
            │ reads                  │ reads/writes
  ┌─────────▼──────┐       ┌────────▼────────────┐
  │ Claude Code    │       │ Training Job         │
  │ Session A      │       │ (AgentJetTrainer)    │
  │ ResourceClient │       │ ResourceClient       │
  └────────────────┘       └─────────────────────┘
            │
  ┌─────────▼──────┐
  │ Claude Code    │
  │ Session B      │
  │ ResourceClient │
  └────────────────┘
```

### New Component: src/cohezion/platform/resource_manager.py

```python
class ResourceDaemon:
    """Persistent platform resource arbiter.

    Runs as background process between sessions.
    Polls Ollama /api/ps for ground-truth model state.
    Manages training locks to prevent concurrent training OOM.

    Start: uv run python -m cohezion.platform.resource_manager
    Or via systemd: cohezion-resources.service
    """
    POLL_INTERVAL_S = 30         # Ollama /api/ps poll frequency
    PORT = 8765                  # Local HTTP API port
    TRAINING_LOCK_TTL_S = 7200   # Max training job reservation = 2 hours

    async def poll_ollama_state(self) -> OllamaState:
        """Query /api/ps for actual loaded models + memory usage."""
        ...

    async def get_available_memory_gb(self) -> float:
        """Total unified memory - Ollama usage - OS overhead - 10GB safety buffer."""
        ...

    async def request_training_lock(
        self, session_id: str, model: str, required_gb: float
    ) -> TrainingLock | None:
        """Exclusive lock for training. Returns None if insufficient memory.
        Locks are stored in SurrealDB with TTL for crash recovery.
        """
        ...

    async def release_training_lock(self, lock_id: str) -> None: ...

    async def register_session(self, session_id: str) -> None:
        """Track active sessions for cleanup on death."""
        ...

    async def cleanup_dead_sessions(self) -> None:
        """Release locks from sessions that died without cleanup."""
        ...


class ResourceClient:
    """Lightweight client for any session to consult the ResourceDaemon.

    Falls back gracefully if daemon not running (single-session mode).
    All sessions MUST use this before loading large models or training.
    """
    DAEMON_URL = "http://localhost:8765"

    async def check_memory(self) -> PlatformMemoryState:
        """Get current memory state across all sessions."""
        ...

    async def acquire_training_lock(
        self, model: str, required_gb: float, timeout_s: float = 30.0
    ) -> TrainingLock | None:
        """Request exclusive training access. Blocks until available or timeout."""
        ...

    async def can_load_model(self, model_name: str, size_gb: float) -> bool:
        """Check if loading a model is safe given all sessions' current usage."""
        ...

    def is_daemon_running(self) -> bool:
        """Silent check — False = fall back to local-only mode."""
        ...


@dataclass
class PlatformMemoryState:
    total_gb: float              # 128 for Ryzen AI MAX+ 395
    ollama_used_gb: float        # From /api/ps (all sessions combined)
    system_reserved_gb: float    # OS + non-Ollama processes
    training_reserved_gb: float  # Active training lock reservations
    available_gb: float          # total - ollama_used - system_reserved - training_reserved
    safety_buffer_gb: float = 10.0  # Never let available drop below this
    loaded_models: list[str]     # All models currently loaded across ALL sessions


@dataclass
class TrainingLock:
    lock_id: str
    session_id: str
    model: str
    reserved_gb: float
    acquired_at: float
    expires_at: float            # TTL for crash recovery
```

### Session Usage Pattern

Every new Claude Code / Gemini CLI session that uses Cohezion:

```python
# On session start (in CompoundExecutor or via hook)
client = ResourceClient()
await client.register_session(session_id=os.environ["COHEZION_SESSION_ID"])

# Before any model load
if not await client.can_load_model("qwen3-coder-next", size_gb=45.0):
    logger.warning("Insufficient platform memory, falling back to nemotron-3-nano:30b")

# Before training (in AgentJetTrainer)
lock = await client.acquire_training_lock("qwen3.5:9b", required_gb=27.0)
if lock is None:
    raise ResourceUnavailableError("Training blocked: another session holds training lock")
try:
    await self._run_training(...)
finally:
    await client.release_training_lock(lock.lock_id)
```

```python
async def _safety_check(self, model: str, required_gb: float) -> None:
    client = ResourceClient()
    if client.is_daemon_running():
        lock = await client.acquire_training_lock(model, required_gb, timeout_s=30.0)
        if lock is None:
            raise ResourceUnavailableError(
                f"Cannot train {model}: platform has insufficient memory "
                f"or another session holds the training lock"
            )
        self._training_lock = lock  # Released in finally block of train()
    else:
        # Fallback: local-only check (single-session safety)
        state = await OllamaContextManager().get_available_memory_gb()
        if state < required_gb * 1.2:
            raise OOMRiskError(f"OOM risk: need {required_gb}GB, have {state}GB")
```

## Gemini Embedding 2 — Orchestration Anchor

Gemini Embedding 2 (March 10, 2026) is Google's first natively multimodal embedding model:
maps text, images, video, audio, and documents into ONE unified embedding space.

This upgrades Cohezion's orchestration from keyword matching → semantic concept matching.

### Why It Matters

`SemanticCache` already has a plug-and-play `EmbeddingModel` interface. The current
`FlumeVAEEmbeddingModel` uses a 256D SHA-256 hash projection — not truly semantic. Gemini
Embedding 2 slots directly into the same interface as a higher-quality tier.

### Three Uses (in priority order)

**1. Vault Indexing (offline, one-time cost)**
Embed every vault note, decision, pattern, and PRIME skill using Gemini Embedding 2.
Store vectors locally in SurrealDB. Never pay again for the same content.
This makes `vault_find_relevant_context()` orders of magnitude more accurate.

**2. FLUME VAE Distillation (calibration, not runtime)**
Use Gemini Embedding 2 vectors as teacher signal to train the FLUME VAE.
The VAE learns to approximate Gemini's embedding quality locally.
After calibration: near-cloud quality at zero API cost per runtime query.
This is knowledge distillation for embeddings — same principle as DistilBERT vs BERT.

**3. Cross-Modal Orchestration (when cloud available)**
Task descriptions, code snippets, trajectory data, and skill definitions all embedded
into the same space. SmartRouter semantic matching across modalities, not just text.

### New Component: src/cohezion/agentjet/embeddings.py

```python
class GeminiEmbeddingModel(EmbeddingModel):
    """Cloud Gemini Embedding 2 — uses Gemini API, caches locally.

    Never embeds the same content twice. Stores in SurrealDB with content hash key.
    Falls back to FlumeVAEEmbeddingModel when cloud unavailable.
    """
    def __init__(self, cache_backend: SurrealClient, fallback: EmbeddingModel): ...
    async def encode(self, text: str) -> EmbeddingResult:
        key = sha256(text)
        if cached := await self.cache_backend.get(key): return cached
        result = await self._call_gemini_api(text)
        await self.cache_backend.store(key, result)
        return result

class EmbeddingDistiller:
    """Distills Gemini Embedding 2 quality into local FLUME VAE.

    Generates Gemini embeddings for vault corpus, then fine-tunes FLUME VAE
```

# Finishing a Development Branch

## Overview

Guide completion of development work by presenting clear options and handling chosen workflow.

**Core principle:** Verify tests → Present options → Execute choice → Clean up.

**Announce at start:** "I'm using the finishing-a-development-branch skill to complete this work."

## The Process

### Step 1: Verify Tests

**Before presenting options, verify tests pass:**

```bash
# Run project's test suite
npm test / cargo test / pytest / go test ./...
```

**If tests fail:**
```
Tests failing (<N> failures). Must fix before completing:

[Show failures]

Cannot proceed with merge/PR until tests pass.
```

Stop. Don't proceed to Step 2.

**If tests pass:** Continue to Step 2.

### Step 2: Determine Base Branch

```bash
# Try common base branches
git merge-base HEAD main 2>/dev/null || git merge-base HEAD master 2>/dev/null
```

Or ask: "This branch split from main - is that correct?"

### Step 3: Present Options

Present exactly these 4 options:

```
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Which option?
```

**Don't add explanation** - keep options concise.

### Step 4: Execute Choice

#### Option 1: Merge Locally

```bash
# Switch to base branch
git checkout <base-branch>

# Pull latest
git pull

# Merge feature branch
git merge <feature-branch>

# Verify tests on merged result
<test command>

# If tests pass
git branch -d <feature-branch>
```

Then: Cleanup worktree (Step 5)

#### Option 2: Push and Create PR

```bash
# Push branch
git push -u origin <feature-branch>

# Create PR
gh pr create --title "<title>" --body "$(cat <<'EOF'
## Summary
<2-3 bullets of what changed>

## Test Plan
- [ ] <verification steps>
EOF
)"
```

Then: Cleanup worktree (Step 5)

#### Option 3: Keep As-Is

Report: "Keeping branch <name>. Worktree preserved at <path>."

**Don't cleanup worktree.**

#### Option 4: Discard

**Confirm first:**
```
This will permanently delete:
- Branch <name>
- All commits: <commit-list>
- Worktree at <path>

Type 'discard' to confirm.
```

Wait for exact confirmation.

If confirmed:
```bash
git checkout <base-branch>
git branch -D <feature-branch>
```

Then: Cleanup worktree (Step 5)

### Step 5: Cleanup Worktree

**For Options 1, 2, 4:**

Check if in worktree:
```bash
git worktree list | grep $(git branch --show-current)
```

If yes:
```bash
git worktree remove <worktree-path>
```

**For Option 3:** Keep worktree.

## Quick Reference

| Option | Merge | Push | Keep Worktree | Cleanup Branch |
|--------|-------|------|---------------|----------------|
| 1. Merge locally | ✓ | - | - | ✓ |
| 2. Create PR | - | ✓ | ✓ | - |
| 3. Keep as-is | - | - | ✓ | - |
| 4. Discard | - | - | - | ✓ (force) |

## Common Mistakes

**Skipping test verification**
- **Problem:** Merge broken code, create failing PR
- **Fix:** Always verify tests before offering options

**Open-ended questions**
- **Problem:** "What should I do next?" → ambiguous
- **Fix:** Present exactly 4 structured options

**Automatic worktree cleanup**
- **Problem:** Remove worktree when might need it (Option 2, 3)
- **Fix:** Only cleanup for Options 1 and 4

**No confirmation for discard**
- **Problem:** Accidentally delete work
- **Fix:** Require typed "discard" confirmation

## Red Flags

**Never:**
- Proceed with failing tests
- Merge without verifying tests on result
- Delete work without confirmation
- Force-push without explicit request

**Always:**
- Verify tests before offering options
- Present exactly 4 options
- Get typed confirmation for Option 4
- Clean up worktree for Options 1 & 4 only

# Code Review Reception

## Overview

Code review requires technical evaluation, not emotional performance.

**Core principle:** Verify before implementing. Ask before assuming. Technical correctness over social comfort.

## The Response Pattern

```
WHEN receiving code review feedback:

1. READ: Complete feedback without reacting
2. UNDERSTAND: Restate requirement in own words (or ask)
3. VERIFY: Check against codebase reality
4. EVALUATE: Technically sound for THIS codebase?
5. RESPOND: Technical acknowledgment or reasoned pushback
6. IMPLEMENT: One item at a time, test each
```

## Forbidden Responses

**NEVER:**
- "You're absolutely right!" (explicit CLAUDE.md violation)
- "Great point!" / "Excellent feedback!" (performative)
- "Let me implement that now" (before verification)

**INSTEAD:**
- Restate the technical requirement
- Ask clarifying questions
- Push back with technical reasoning if wrong
- Just start working (actions > words)

## Handling Unclear Feedback

```
IF any item is unclear:
  STOP - do not implement anything yet
  ASK for clarification on unclear items

WHY: Items may be related. Partial understanding = wrong implementation.
```

**Example:**
```
your human partner: "Fix 1-6"
You understand 1,2,3,6. Unclear on 4,5.

❌ WRONG: Implement 1,2,3,6 now, ask about 4,5 later
✅ RIGHT: "I understand items 1,2,3,6. Need clarification on 4 and 5 before proceeding."
```

## Source-Specific Handling

### From your human partner
- **Trusted** - implement after understanding
- **Still ask** if scope unclear
- **No performative agreement**
- **Skip to action** or technical acknowledgment

### From External Reviewers
```
BEFORE implementing:
  1. Check: Technically correct for THIS codebase?
  2. Check: Breaks existing functionality?
  3. Check: Reason for current implementation?
  4. Check: Works on all platforms/versions?
  5. Check: Does reviewer understand full context?

IF suggestion seems wrong:
  Push back with technical reasoning

IF can't easily verify:
  Say so: "I can't verify this without [X]. Should I [investigate/ask/proceed]?"

IF conflicts with your human partner's prior decisions:
  Stop and discuss with your human partner first
```

**your human partner's rule:** "External feedback - be skeptical, but check carefully"

## YAGNI Check for "Professional" Features

```
IF reviewer suggests "implementing properly":
  grep codebase for actual usage

  IF unused: "This endpoint isn't called. Remove it (YAGNI)?"
  IF used: Then implement properly
```

**your human partner's rule:** "You and reviewer both report to me. If we don't need this feature, don't add it."

## Implementation Order

```
FOR multi-item feedback:
  1. Clarify anything unclear FIRST
  2. Then implement in this order:
     - Blocking issues (breaks, security)
     - Simple fixes (typos, imports)
     - Complex fixes (refactoring, logic)
  3. Test each fix individually
  4. Verify no regressions
```

## When To Push Back

Push back when:
- Suggestion breaks existing functionality
- Reviewer lacks full context
- Violates YAGNI (unused feature)
- Technically incorrect for this stack
- Legacy/compatibility reasons exist
- Conflicts with your human partner's architectural decisions

**How to push back:**
- Use technical reasoning, not defensiveness
- Ask specific questions
- Reference working tests/code
- Involve your human partner if architectural

**Signal if uncomfortable pushing back out loud:** "Strange things are afoot at the Circle K"

## Acknowledging Correct Feedback

When feedback IS correct:
```
✅ "Fixed. [Brief description of what changed]"
✅ "Good catch - [specific issue]. Fixed in [location]."
✅ [Just fix it and show in the code]

❌ "You're absolutely right!"
❌ "Great point!"
❌ "Thanks for catching that!"
❌ "Thanks for [anything]"
❌ ANY gratitude expression
```

**Why no thanks:** Actions speak. Just fix it. The code itself shows you heard the feedback.

**If you catch yourself about to write "Thanks":** DELETE IT. State the fix instead.

## Gracefully Correcting Your Pushback

If you pushed back and were wrong:
```
✅ "You were right - I checked [X] and it does [Y]. Implementing now."
✅ "Verified this and you're correct. My initial understanding was wrong because [reason]. Fixing."

❌ Long apology
❌ Defending why you pushed back
❌ Over-explaining
```

State the correction factually and move on.

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Performative agreement | State requirement or just act |
| Blind implementation | Verify against codebase first |
| Batch without testing | One at a time, test each |
| Assuming reviewer is right | Check if breaks things |
| Avoiding pushback | Technical correctness > comfort |
| Partial implementation | Clarify all items first |
| Can't verify, proceed anyway | State limitation, ask for direction |

## Real Examples

**Performative Agreement (Bad):**
```
Reviewer: "Remove legacy code"
❌ "You're absolutely right! Let me remove that..."
```

**Technical Verification (Good):**


**Unclear Item (Good):**


### 2. HIGHEST IMPACT: Coalesced Vectorized Loads via LDS Tiling

**Your bottleneck**: The kernel loads A and B data with scalar byte-by-byte loops (`for (int i = 0; i &lt; 16; i++) b_bytes[i] = b_ptr[i]`). This generates 16 separate 1-byte loads per thread where the hardware wants 128-bit vector loads.

**The fix from AMD's FP8 GEMM blog** ([FP8 GEMM Optimization on CDNA4](https://rocm.blogs.amd.com/software-tools-optimization/cdna4-gemm-kernels/README.html)):

The progression is: Naive scalar = 1.15 TFLOPS, Vectorized loads = 336 TFLOPS, Direct global-to-LDS = 506 TFLOPS. That is a **293x** speedup just from fixing loads.

**Actionable pattern for your kernel**:

```cpp
// INSTEAD OF byte-by-byte:
// for (int i = 0; i &lt; 16; i++) b_bytes[i] = b_ptr[i];

// USE 128-bit vectorized load (loads 16 bytes = 32 FP4 values in 1 instruction):
uint4 b_vec = *reinterpret_cast&lt;const uint4*&gt;(b_base + k_byte_off);
b_reg = *reinterpret_cast&lt;b_reg_t*&gt;(&amp;b_vec);  // Direct to register
```

For A (BF16, 32 elements = 64 bytes), use two `uint4` loads:
```cpp
// Load 32 BF16 values with 2 coalesced 128-bit loads
uint4 a_vec0 = *reinterpret_cast&lt;const uint4*&gt;(a_base + a_k_start);
uint4 a_vec1 = *reinterpret_cast&lt;const uint4*&gt;(a_base + a_k_start + 8);
```

### 3. HIGH IMPACT: Multi-Wave Tiling with LDS Double Buffering

**Your problem**: 1 wave per block (64 threads). The CDNA4 CU has 4 SIMDs, each can run 2 waves. You are using **1/8th** of compute capacity.

**Petit-kernel's approach** (from `kernel_config.cuh` and `gemm_fp4_fp16_grid.cuh`):

```cpp
// Petit uses warp partitions like WarpPartition&lt;1, 4, 1&gt; = 4 warps
// or WarpPartition&lt;2, 4, 1&gt; = 8 warps per block
// With tile shapes like TileShape&lt;bf16, MxFp4, 32, 4, 4, 8&gt;
// = 64x64 output tile, K=128 per iteration
```

**The 8-wave ping-pong from the AMD blog achieves 2288 TFLOPS** vs. 30 TFLOPS with 1 wave. Key architectural pattern:

```cpp
// 8 waves, 512 threads per block
// 256x256 output tile, waves split into 2 groups of 4
// Group A: memory instructions while Group B: MFMA compute, then swap

__shared__ float A_lds[2][TILE_M][TILE_K];  // Double buffered
__shared__ float B_lds[2][TILE_K][TILE_N];

// Pipeline: prefetch tile t+1 while computing tile t
int cur = 0, nxt = 1;
prefetch_to_lds(A_lds[cur], B_lds[cur], tile=0);
__syncthreads();

for (int t = 0; t &lt; num_k_tiles; t++) {
    if (t + 1 &lt; num_k_tiles) {
        prefetch_to_lds_async(A_lds[nxt], B_lds[nxt], tile=t+1);
    }
    compute_mfma_from_lds(A_lds[cur], B_lds[cur], acc);
    __syncthreads();
    swap(cur, nxt);
}
```

### 4. HIGH IMPACT: LDS Bank Conflict Elimination via XOR Swizzle

LDS has 64 banks (32-bit each on CDNA4). Without swizzling, `ds_read_b128` (which reads in 4 phases) causes bank conflicts that serialize access.

**Petit-kernel's swizzle from `gemm_fp4_fp16_grid.cuh`**:

```cpp
// XOR-based swizzle to eliminate LDS bank conflicts
__device__ static inline unsigned XorShmLayout(
    unsigned tile_idx_m, unsigned tile_idx_k,
    unsigned batch_id, unsigned row, unsigned col)
{
    static constexpr unsigned kBatchStride = DiskLayout::kLayoutElementsM;
    unsigned base = tile_idx_m * kTile * kGroupK / kVecSize
                  + tile_idx_k * kTile * kLayoutM / kVecSize
                  + batch_id * kWarpSize;
    unsigned xor_stride = col * kBatchStride + batch_id;
    return base + col * kMmaM + row ^ xor_stride;  // XOR eliminates conflicts
}
```

**AMD FP8 GEMM blog's swizzle function**:

```cpp
int swizzle_col(int row, int col) {
    const int pair = (row &gt;&gt; 1) &amp; 7;
    const int perm = pair ^ (((pair &gt;&gt; 1) ^ (pair &gt;&gt; 2)) &amp; 1);
    const int mask = perm &lt;&lt; 4;
    return col ^ mask;
}
```

**For your kernel**: When writing B data to LDS, XOR the column index with a function of the row to spread accesses across banks.

### 5. MEDIUM IMPACT: Petit-Kernel's FP4 Dequantization Trick

Petit uses `__builtin_bitreverse32` + mask operations to convert packed FP4 to BF8 format in just a few instructions, then uses `__builtin_amdgcn_cvt_pk_f32_bf8` for fast conversion. From `dequant.cuh`:

```cpp
// Fast FP4 → BF8 conversion (gfx942/gfx950 only)
__device__ static inline void Fp4ToBf8(unsigned o[2], unsigned q) {
    unsigned qr = __builtin_bitreverse32(q);
    o[0] = q &amp; 0x8e8e8e8e;    // Mask sign + exponent bits
    o[1] = qr &amp; 0x8e8e8e8e;
}

// Then use hardware BF8→F32 conversion:
v2f out0 = __builtin_amdgcn_cvt_pk_f32_bf8(bf8[0], false);  // low 2 values
v2f out1 = __builtin_amdgcn_cvt_pk_f32_bf8(bf8[0], true);   // high 2 values
```

This replaces your 32-element scalar quantization loop with ~6 instructions per 8 FP4 values. **However, since you are using the scaled MFMA intrinsic that takes FP4 directly, you do NOT need to dequantize -- the hardware does it.** This technique is relevant if you switch to a BF16 MFMA approach.

### 6. MEDIUM IMPACT: Buffer Load Intrinsics for Branchless OOB Handling

Petit-kernel eliminates all boundary checks using AMD buffer loads that auto-discard OOB accesses:

```cpp

union BufferResource {
    v4i content;
    struct {
        uintptr_t ptr;
        unsigned range;    // Valid byte range -- OOB auto-discarded!
        unsigned config;
    } v;

    template &lt;int kAux&gt;
    __device__ inline uint4 Load(int voffset, int soffset) const {
        v4i v = llvm_amdgcn_raw_buffer_load_v4i32(content, voffset, soffset, kAux);
        return *reinterpret_cast&lt;const uint4*&gt;(&amp;v);
    }
};

// Usage -- NO if-checks needed:
```

### 7. INSTRUCTION SCHEDULING: `sched_group_barrier` for MFMA Overlap

Petit-kernel's `HotLoopScheduler` from `gemm_fp4_fp16_grid.cuh` controls instruction ordering:

```cpp
__device__ static void HotLoopScheduler() {
    // 0x100 = buffer_load group
    __builtin_amdgcn_sched_group_barrier(0x100, kInstLoadForFirstPipeline, 0);

    // Interleave ds_write (0x200) with MFMA (0x8)
    for (int i = 0; i &lt; kInstGlobals; i++) {
        __builtin_amdgcn_sched_group_barrier(0x200, 1, 0);  // 1 ds_write
        __builtin_amdgcn_sched_group_barrier(0x8, kInstMFMAPerLoad, 0);  // N MFMAs
    }

    // Then buffer_load (0x20) interleaved with MFMA
    for (int i = 0; i &lt; kInstGlobals; i++) {
        __builtin_amdgcn_sched_group_barrier(0x20, 1, 0);   // 1 buffer_load
        __builtin_amdgcn_sched_group_barrier(0x8, kInstMFMAPerLoad * 2, 0);
    }

    __builtin_amdgcn_sched_barrier(0);  // Hard barrier
}
```

Also use `__builtin_amdgcn_s_setprio()` for wave priority control and `__builtin_amdgcn_s_waitcnt()` for precise memory fence placement.

## 2. The head_dim=576 Problem

Standard flash attention (CK, FlashInfer, xFormers) all cap at head_dim &lt;= 256. MLA's 576 = 512 (latent) + 64 (RoPE) breaks every existing attention kernel.

**Three approaches to handle 576:**

### 2a. Split-D: Decompose 576 into 512 + 64
Compute `score = Q[:512] @ KV[:512]^T + Q[512:576] @ KV[512:576]^T`. Two MFMA-compatible dot products (512 and 64, both multiples of 32). This is algebraically exact. The V extraction naturally uses KV[:512], which is the first sub-dot's KV tile.

- **Pro**: Both sub-dimensions are power-of-2 (512) or cleanly tiled (64), work perfectly with MFMA
- **Pro**: V is exactly the first 512 dims, so the KV tile for the first sub-dot IS the V tile (zero extra loads)
- **Con**: Our Triton Split-D attempt was 3-15x slower because Triton's `tl.dot` on AMD has massive overhead and Q-padding to BLOCK_M=16 wastes 15/16 of MFMA compute

**Key insight**: Split-D failed in Triton, but should work well in a raw HIP kernel where we control MFMA instruction emission directly.

### 2b. FFPA (Fine-grained Tiling at MMA Level)
[FFPA](https://github.com/xlite-dev/ffpa-attn) tiles along the head dimension at the MMA instruction level rather than the attention level. This achieves O(1) SRAM complexity regardless of head_dim and supports head_dim up to 1024+.

- **Pro**: Supports arbitrary head_dim, including 576
- **Pro**: 1.8-3x faster than PyTorch SDPA for head_dim &gt;= 256 on NVIDIA GPUs
- **Con**: Currently CUDA-only (PTX instructions), would need full HIP port
- **Con**: Complex implementation (~500+ lines of MMA-level scheduling)
- **Reference**: [Issue #1483 on flash-attention](https://github.com/Dao-AILab/flash-attention/issues/1483)

### 2c. Pad to 640 (next multiple of 128)
Pad Q and KV from 576 to 640, run standard attention, extract V[:512] from output[:512]. Wastes 640/576 = 11% of compute but enables use of standard tiling.

- **Pro**: Simplest implementation, works with any standard attention kernel template
- **Con**: 11% wasted MFMA compute, extra memory for padded buffers
- **Con**: For decode (GEMV), memory bandwidth is the bottleneck, and padding increases KV load by 11%

## 3. Decode-Specific Architecture: GEMV, Not GEMM

The fundamental challenge for MLA decode: with qseqlen=1, the Q matrix is a single row. This transforms `Q @ KV^T` from GEMM to GEMV (matrix-vector multiply). Standard flash attention tile sizes (BLOCK_M=64 or 128) waste most of their compute.

**FlashDecoding / Split-K is the correct paradigm:**

1. **Split the KV sequence** across multiple workgroups (split-K)
2. Each workgroup computes a **partial score vector** `Q[1,576] @ KV[BLOCK_N,576]^T` = `[1, BLOCK_N]`
3. Apply partial softmax (online softmax with running max/sum)
4. Compute partial weighted value: `softmax_weights[1,BLOCK_N] @ V[BLOCK_N,512]` = `[1, 512]`
5. **Reduction kernel** merges partial results using log-sum-exp

**Key references:**
- [FlashInfer Split-K Decoding](https://flashinfer.ai/2024/02/02/introduce-flashinfer.html)
- [FlashMLA Tile Scheduler](https://github.com/deepseek-ai/FlashMLA/blob/main/docs/20250422-new-kernel-deep-dive.md)

## 4. Viable Kernel Architectures (ranked by feasibility)

### Architecture A: Custom HIP Split-K GEMV Attention (RECOMMENDED)

A single-launch HIP kernel via `load_inline` that:

1. **Grid**: `(num_splits, NUM_HEADS, batch)` -- each block handles one KV split for one head
2. **Block**: 256 threads (4 waves of 64)
3. **Per-block computation**:
   - Load Q row (576 bf16/fp8) into registers (shared across all threads in block)
   - Iterate over KV tiles in the split: load KV[BLOCK_N, 576] from global to LDS
   - Compute dot product Q @ KV^T using cooperative reduction across threads
   - Apply online softmax update (running max, running sum)
   - Accumulate weighted V contribution
4. **Output**: Per-split partial results (max, lse, weighted_sum[512]) to global memory
5. **Reduce kernel**: Lightweight merge of partial results via online softmax

**Why this can reach 12us:**
- Single kernel launch (no Python dispatch overhead)
- Q is broadcast across all 16 heads (GQA: 1 KV head shared by 16 Q heads)
- KV reads are sequential and can be optimized with LDS double-buffering
- 160KB LDS per CU can hold `160KB / 576 / 2 = 139` KV rows in bf16, or `160KB / 576 = 277` in fp8
- With 304 CUs, even small batches fully saturate the GPU

**Estimated register usage per thread:**
- Q fragment: 576/64 lanes x 1 row = 9 fp32 registers (or 9 fp8 packed)
- KV tile in LDS: shared, not in registers
- Partial score: 1 fp32
- Running max, sum: 2 fp32
- V accumulator: 512/64 = 8 fp32 registers
- Total: ~20 VGPRs per thread -- well within budget

### Architecture B: HipKittens-Style Tiled Attention

[HipKittens](https://github.com/HazyResearch/HipKittens) (arxiv [2511.08083](https://arxiv.org/html/2511.08083v1)) achieved parity with AMD's hand-tuned assembly for attention forward on MI355X. Key features:

- 8-wave ping-pong scheduling: overlaps MFMA compute with LDS loads
- Register pinning for Q (Q stays in VGPRs across K/V tile iterations)
- Tile sizes matching MFMA shapes (16x16x32 and 32x32x16)
- **~500 LOC** for attention forward

**For decode**, HipKittens' approach needs modification:
- BLOCK_M must be 1 (single query row) -- this means we cannot use MFMA for Q@K^T directly
- Instead, use thread-cooperative vector-matrix multiply, then MFMA for the reduction
- The V accumulation (`weights @ V`) CAN use MFMA if we batch multiple splits

**Limitation**: HipKittens validated head_dim 64 and 128 only. Head_dim 576 is untested and would require custom tiling.

### Architecture C: TileLang FlashMLA Port

[TileLang](https://github.com/tile-ai/tilelang) achieved FlashMLA performance parity with AITER assembly on MI300X using only 80 lines of Python. AMD published an [official blog post](https://rocm.blogs.amd.com/ecosystems-and-partners/rocm-tilelang-kernel/README.html) about it.

**Problem**: TileLang generates Triton kernels, and our experience shows Triton on MI355X has a ~130us dispatch floor for attention patterns. TileLang may work better than raw Triton (it generates more optimized IR), but the dispatch overhead risk is high.

### Architecture D: CK-Tile FMHA with Custom head_dim Tiling

AMD's [CK-Tile FlashAttention blog](https://rocm.blogs.amd.com/software-tools-optimization/ck-tile-flash/README.html) shows how to build FA-v2 in ~100 lines of CK-Tile code. However:

- CK-Tile's FMHA hardcodes head_dim &lt;= 256
- Extending to 576 requires modifying CK-Tile source
- CK-Tile is a compiled library, not compatible with `load_inline`
- CK-Tile IS installed on the runner (it's part of aiter/ROCm), but we can't modify it at submission time

## 5. Recommended Implementation Strategy

### Step 1: Split-K GEMV Attention Kernel via `load_inline`

Write a HIP C++ kernel that handles the complete MLA decode in a single launch:

```
Grid: (num_splits_per_head, NUM_HEADS=16, batch_size)
Block: 256 threads

Per-block:
  1. Load Q[head, :576] from global memory (broadcast from single KV head)
  2. For each KV tile in this split's range:
     a. Load KV[tile_start:tile_end, :576] into LDS (cooperative load)
     b. Compute scores: each thread handles a subset of KV rows
        score[i] = dot(Q, KV[i]) * SM_SCALE  (thread-cooperative 576-dim dot product)
     c. Online softmax update:
        m_new = max(m_old, max(scores))
        p = exp(scores - m_new)
        l = exp(m_old - m_new) * l_old + sum(p)
     d. V accumulation:
        acc = exp(m_old - m_new) * acc + sum(p * V[i, :512])
  3. Write partial result (m, l, acc[512]) to global memory

Reduce kernel:
  Grid: (NUM_HEADS, batch_size)
  Block: 256 threads
  For each split:
    Online softmax merge of partial (m, l, acc) results
  Write final output[batch, head, :512]
```

### Step 2: Optimize the Dot Product for 576-dim

The 576-dim dot product is the inner loop. For FP8 inputs:

- 576 elements / 64 threads = 9 elements per thread
- Each thread computes a partial dot product of 9 FP8 pairs
- Warp reduction (butterfly shuffle) to accumulate across 64 threads
- No MFMA needed for the Q@K^T score (it's a 1x576 @ 576x1 dot product)

For the V accumulation:
- 512 elements / 64 threads = 8 elements per thread
- Weighted accumulation: `acc[t] += weight * V[kv_idx, thread_element]`
- This is a scatter-add pattern, fully parallelizable

### Step 3: Split Count Tuning

Optimal splits depend on batch size and KV length:
- **bs=4, kv=1k**: 4 tokens x 1k = 4k KV total. With 304 CUs, use ~16 splits x 16 heads x 4 batch = 1024 blocks. Each split handles ~250 KV rows.
- **bs=256, kv=8k**: 256 x 8k = 2M KV total. Use 4 splits per head, 4 x 16 x 256 = 16,384 blocks. Each split handles 2k KV rows.

The split count should be chosen to maximize CU occupancy: `num_splits = max(1, ceil(304 / (batch * NUM_HEADS)))`.

### Why aiter Is Slow (~13.4µs): The Root Cause

aiter's `gemm_a4w4` is a **general-purpose** MXFP4 GEMM tuned for production LLM inference. ### Hypothesized Techniques (Strong Evidence)

Based on all research, here is what likely enables sub-5µs geometric mean:

#### 1. Custom HIP C++ Kernel via `load_inline` with Direct MFMA Intrinsics

The competition requires Python submissions using `torch.utils.cpp_extension.load_inline()`. The leaders almost certainly use the `__builtin_amdgcn_mfma_scale_f32_32x32x64_f8f6f4` intrinsic directly (or the 16x16x128 variant), as documented in [Salykova's Matrix Core Programming blog](https://salykova.github.io/matrix-cores-cdna) and the [AMD CDNA4 ISA Reference](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/instruction-set-architectures/amd-instinct-cdna4-instruction-set-architecture.pdf). This is how [RadeonFlow won the AMD Developer Challenge 2025](https://github.com/RadeonFlow/RadeonFlow_Kernels) -- custom HIP kernels with `load_inline` submission wrappers.

#### 2. Shape-Specialized Dispatch (Critical for Geometric Mean)

The single most impactful technique: **dispatch to different kernel configurations per shape**. Instead of one kernel for all shapes:

| M Range | Strategy | Why |
|---------|----------|-----|
| M=4,16 | Split-K + Sparse MFMA or small tiles, maximize CU occupancy | [HuggingFace MI300 kernel blog](https://huggingface.co/blog/mi300kernels) shows 1.12-1.42x over hipBLASLt |
| M=32,64 | Medium tiles, 4-wave interleave scheduling | Transitional regime |
| M=256 | 8-wave ping-pong, 256x256 tiles, double-buffered LDS | [ROCm CDNA4 GEMM blog](https://rocm.blogs.amd.com/software-tools-optimization/cdna4-gemm-kernels/README.html) achieves 97.5% of hipBLASLt |

Since scoring is geometric mean, making **every shape fast** matters more than making one shape extremely fast.

#### 3. The 8-Wave Ping-Pong + Double-Buffered LDS Pipeline

From the [FP8 GEMM Optimization on CDNA4 blog](https://rocm.blogs.amd.com/software-tools-optimization/cdna4-gemm-kernels/README.html):
- 8 waves per thread block, 2 waves per SIMD alternating between memory and compute
- Global-to-LDS direct transfer (`llvm_amdgcn_raw_buffer_load_lds`) bypassing registers
- Double-buffered LDS: compute tile t while loading tile t+1
- Explicit wave priority control: `__builtin_amdgcn_s_setprio()`, `sched_barrier()`
- Result: 2680 TFLOPS/s for FP8, approaching hipBLASLt's 2750 TFLOPS/s

For MXFP4 (FP4), throughput doubles to ~5000+ TFLOPS/s theoretical with the same technique.

#### 4. Chiplet-Aware (XCD) Block Scheduling

MI355X has multiple XCDs (chiplets). Naive row-major block assignment loses up to 20% throughput. The [HipKittens paper](https://arxiv.org/html/2511.08083v1) documents a hierarchical windowed traversal that improves L2/LLC cache reuse by up to 19%. This is critical for large-N shapes where B matrix reuse across blocks matters.

#### 5. Persistent Kernel / Grouped GEMM Pattern

For the geometric mean scoring across many shapes, launching separate kernels per shape incurs overhead (~10-40µs per launch). A persistent kernel that processes all shapes in a single dispatch, or at minimum pre-compiles and caches all shape-specific kernels to minimize JIT overhead, would save significant time.

The [CK-Tile library](https://github.com/ROCm/composable_kernel) recently added a "persistent async input scheduler" for universal GEMM on gfx950, and PyTorch's [Triton Grouped GEMM](https://pytorch.org/blog/accelerating-moes-with-a-triton-persistent-cache-aware-grouped-gemm-kernel/) shows this pattern eliminating launch overhead.

#### 6. Warp Specialization for Small-M Shapes

The [HuggingFace skinny GEMM kernel](https://huggingface.co/blog/mi300kernels) demonstrates producer-consumer warp specialization:
- 8-10 producer warps handle memory loads
- 2-3 consumer warps execute MFMA instructions
- Shared-memory semaphore queue synchronization
- This matches low arithmetic intensity (small M) by dedicating more threads to bandwidth

#### 7. Mars Compute's Likely Advantage: Automated Kernel Generation

Mars Compute's **1-submission success** strongly suggests an automated system. Their website describes an "Optimization Planning Engine" that "builds optimization graphs with conflict-aware scheduling." Prof. Bingsheng He's [research group](https://www.comp.nus.edu.sg/cs/people/hebs/) has extensive GPU systems work. They likely have a compiler/autotuner that:
1. Profiles the target hardware (MI355X topology, memory hierarchy)
2. Generates shape-specialized kernels with optimal tiling, scheduling, and instruction selection
3. Produces the final `load_inline` submission automatically

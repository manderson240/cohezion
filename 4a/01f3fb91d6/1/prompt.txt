# AMD MI355X (gfx950) GPU Kernel Optimization Research Report

## 1. HipKittens (HazyResearch)

**What:** Tile-based C++ DSL for writing high-performance AMD AI kernels, the AMD counterpart to ThunderKittens (NVIDIA). Now officially an AITER backend.

**Where:** [GitHub - HazyResearch/HipKittens](https://github.com/HazyResearch/HipKittens) | [Paper (arXiv)](https://arxiv.org/html/2511.08083v1) | [Dev-Open repo](https://github.com/HazyResearch/HipKittens-Dev-Open/blob/main/README.md)

**Key findings:**
- Validated on both CDNA3 and **CDNA4 (gfx950)** platforms. Docker image: `rocm/7.0-preview:rocm7.0_preview_pytorch_training_mi35x_beta`
- BF16 GEMM reaches ~2.5 PFLOPS, matching hand-tuned AITER assembly. **FP8 reaches 5.0 PFLOPS**.
- Outperforms Triton by 1.3x-3.0x on GEMM, 1.0-2.1x on attention forward over AITER
- **Critical architectural insight:** Wave specialization (the dominant NVIDIA pattern) **underperforms on AMD** due to static register allocation. Use **8-wave ping-pong** or **4-wave interleave** scheduling instead.
- Chiplet-aware scheduling improves performance 19% over naive row-major on MI355X (8 chiplets)
- **No explicit MXFP4 GEMM examples found yet** -- current focus is BF16 and FP8. ThunderKittens 2.0 (NVIDIA) has MXFP8/NVFP4 but the AMD port may lag.

**Applicability:** HIGH for attention and BF16/FP8 GEMM. MEDIUM for MXFP4 (likely needs extension). The tile DSL patterns and scheduling strategies are directly relevant.

**Code patterns:**
- Register tiles: `r<dtype, M, N, layout, mfma_shape>` mapping directly to MFMA instructions
- Bulk compute: `mma(A, B, C)` exposing MFMA directly
- Global-to-shared loads: auto-selects `buffer_load_dwordx4`/`dwordx3` based on dtype

**Effort:** Medium (2-4 days to port an existing HK kernel to MXFP4 if you extend the primitives, or 1-2 days to use their BF16/FP8 kernels as-is)

## 2. CK-Tile FlatMM Examples (MXFP4 GEMM on gfx950)

**What:** AMD's Composable Kernel library with a FlatMM (weight-preshuffled GEMM) pipeline specifically optimized for MXFP4 on gfx950.

**Where:** [CK GitHub](https://github.com/ROCm/composable_kernel) | [DeepWiki: MFMA Optimizations](https://deepwiki.com/ROCm/composable_kernel/6.2-hardware-specific-optimizations-and-mfma) | [DeepWiki: MoE FlatMM](https://deepwiki.com/ROCm/composable_kernel/4.4-convolution-operations) | [CK-Tile GEMM Blog](https://rocm.blogs.amd.com/software-tools-optimization/building-efficient-gemm-kernels-with-ck-tile-vendo/README.html)

**Key findings:**
- **Hardware-accelerated MXFP4 via dedicated instructions:**
  - `mfma_f32_32x32x64_f8f6f4` -- FP4/FP6/FP8 MFMA instruction
  - `mfma_scale_f32_32x32x64` -- hardware scaling with E8M0 scale factors
  - `pk_fp4_t` -- packed data type (2 FP4 values per byte)
- The `mfma_scale_*` instructions perform dequantization AND matrix multiply in a single operation: `C += dequantize(A, scale_A) * dequantize(B, scale_B)`
- MoE FlatMM extends standard FlatMM with expert routing, gating, fused activation functions
- **Requires weight pre-shuffling** (offline transformation before kernel execution)
- gfx950 has increased LDS capacity enabling larger tile sizes and more aggressive blocking

**Example code locations:**
- `example/ck_tile/18_flatmm/` -- main FlatMM examples
- `example/ck_tile/18_flatmm/flatmm_basic.hpp` -- gfx942 and gfx950 configs
- `example/ck_tile/18_flatmm/mixed_prec/a16w4_flatmm.hpp` -- A16W4 mixed precision
- `example/ck_tile/18_flatmm/mixed_prec/a16w4_moe_flatmm.cpp` -- MoE FlatMM with MXFP4
- `include/ck_tile/ops/flatmm/kernel/flatmm_kernel.hpp`
- Build with: `-D GPU_TARGETS="gfx950"`

**IREE optimization insight:** K tile size picking was suboptimal, yielding 32 MFMAs per workgroup. Fixing this gave a **5x throughput increase** ([IREE issue #22309](https://github.com/iree-org/iree/issues/22309)).

**Applicability:** VERY HIGH -- this is the reference implementation for MXFP4 GEMM on gfx950. Directly targets the competition's MXFP4 GEMM and MXFP4 MoE problems.

**Effort:** Medium (1-3 days to build, benchmark, and adapt CK FlatMM examples for competition problem shapes)

## 10. MXFP4 Quantization Fusion (bf16 to fp4 in GEMM)

**What:** Fusing the quantization step into GEMM kernels to avoid costly precision round-trips.

**Key findings:**
- **Direct FP8-to-FP4 quantization** without BF16 intermediates (bitwise conversion with hierarchical scale alignment) -- reduces memory + inter-GPU traffic by >50%
- **MR-GPTQ** (ICLR 2026): rotation fusion into weights + fast online activation computation. 3.6x layer-wise speedup on B200, 6x on RTX5090
- AMD approach: MXFP4 GEMMs dispatched to pre-tuned CK and Triton kernels from a tuned AITER
- AMD Quark + online rotation recovers 45-55% of accuracy drop, retaining >98% of BF16 accuracy
- MXFP4 format: 4-bit FP (e2m1), power-of-two scale per 32 values, 2 FP4 values packed per byte
- Key insight: `per_group_token_quant` can be **fused into the MoE GEMM kernel** (CK FlatMM pipeline does this)

**Applicability:** HIGH -- fusing quantization into GEMM avoids a separate kernel launch and memory round-trip. This is potentially the difference between top-10 and winning.

**Effort:** Medium-High (3-5 days to implement online quantization fusion if not already in CK/AITER baseline)

**Distillation workflow:**

```
For each (prompt, answer) in train.csv:
  1. Send to teacher: "Think step by step. [prompt]"
  2. Collect reasoning trace + final answer
  3. Verify teacher answer matches ground truth
  4. Format as: <thinking>{trace}</thinking>\boxed{answer}
  5. Filter: keep only correct traces (~70-85% expected match rate)
```

**Training data format after distillation:**

```
User: {prompt}\nPlease put your final answer inside \boxed{}. For example: \boxed{your answer}
```

### 2. Kaggle Submission Format (Critical Finding)

**The current pipeline is built on a completely wrong submission model.** This is the single biggest blocker.

This competition is NOT a traditional Kaggle submission where you upload a `submission.json`. It is a **hackathon** using the **Kaggle Community Benchmarks platform** and the `kaggle-benchmarks` SDK (`kbench`).

**What participants actually submit:**
1. **A Kaggle Benchmark** -- built using the `@kbench.task` decorator in a Kaggle notebook, testing frontier models (Gemini, Claude, etc.) via `kbench.llm`
2. **A 1,500-word writeup** -- on the Kaggle platform with a project link to the benchmark
3. **A public notebook** -- the code that defines and runs the benchmark
4. **A cover image**

**The correct workflow is:**
```python
import kaggle_benchmarks as kbench

@kbench.task(name="epistemic_humility_grid_trap")
def test_epistemic_humility(llm, question: str, options: list, expected: str):
    response = llm.prompt(question)
    kbench.assertions.assert_contains_regex(
        r"(?i)insufficient information",
        response,
        expectation="Model should recognize ambiguity"
    )

# Run against frontier models on Kaggle's infrastructure
test_epistemic_humility.run(
    llm=kbench.llm,
    question="...",
    options=[...],
    expected="Insufficient Information"
)
```

## Research Report: kbench SDK and Measuring AGI Pivot

### 1. Exact kbench SDK API

**Package:** `kaggle_benchmarks` (aliased as `kbench`)

**Installation:**
- On Kaggle notebooks: pre-installed, no setup needed
- Locally: `git clone https://github.com/Kaggle/kaggle-benchmarks.git && uv pip install -e .`
- Local env vars: `MODEL_PROXY_URL`, `MODEL_PROXY_API_KEY`, `LLM_DEFAULT`, `LLM_DEFAULT_EVAL`

**Core API surface:**

```python
import kaggle_benchmarks as kbench

# --- Define a task ---
@kbench.task(name="my_task_name")
def my_task(llm, param1: str, param2: str):
    response = llm.prompt("Your prompt here")
    kbench.assertions.assert_contains_regex(r"(?i)expected", response, expectation="...")

# --- Run a single task ---
my_task.run(llm=kbench.llm, param1="value1", param2="value2")

# --- Run across a dataset ---
import pandas as pd
df = pd.DataFrame([{"param1": "a", "param2": "b"}, ...])
results = my_task.evaluate(llm=[kbench.llm], evaluation_data=df)

# --- Multi-model comparison ---
models = [kbench.llms["google/gemini-2.5-flash"], kbench.llms["meta/llama-3.1-70b"]]
results = my_task.evaluate(llm=models, evaluation_data=df)

# --- Structured output ---
from dataclasses import dataclass
@dataclass
class MyOutput:
    answer: str
    confidence: float

response = llm.prompt("...", schema=MyOutput)

# --- Judge-based evaluation ---
assessment = kbench.assertions.assess_response_with_judge(
    criteria=["criterion 1", "criterion 2"],
    response_text=response,
    judge_llm=llm,
    output_schema=CustomSchema
)

# --- Multi-turn conversations ---
with kbench.chats.new("context_name"):
    llm.prompt("turn 1")
    llm.prompt("turn 2")  # maintains history

# --- Image inputs ---
from kaggle_benchmarks import images
img = images.from_url("https://...")
response = llm.prompt("Describe this", image=img)

# --- Publish to leaderboard ---
# In final cell: %choose my_task_name
```

**Return type annotations control scoring:**
- `-> bool`: pass/fail
- `-> float` / `-> int`: numerical score
- `-> tuple[int, int]`: ratio (e.g., 8/10)
- No return + assertions only: pass when all assertions pass

**Key assertions:** `assert_contains_regex`, `assess_response_with_judge`, custom via `@assertion_handler`

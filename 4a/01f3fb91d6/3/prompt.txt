4 out of 6 benchmark shapes have NO tuned CK config:

- M=32, N=4096, K=512 — not in CSV

### The splitK=0 Meaning

`v78_splitk0.py` confirms `log2_k_split=0` — no K-splitting. This is correct for small-K shapes (K=512 especially). But `compute_gemm_SplitK` in `gemm_op_a4w4.py` line 30 is hardcoded to `return 3` regardless of shape, meaning untuned shapes get 8-way K-splitting with atomic reduction overhead. This is a known bug in the fallback path.

### How aiter Dispatches Between CK and ASM

The dispatch checks whether the tuned CSV entry's `kernelName` starts with `_ZN` (mangled C++ ASM symbol). If yes → ASM path with `gemm_a4w4_asm`. If no → CK path with `gemm_a4w4_blockscale`. Most competition shapes hit the ASM path.

### Undiscovered API

`per_1x32_f4_quant_hip` in `aiter/ops/quant.py` is a HIP C++ kernel (not Triton) that quantizes BF16 to FP4 AND shuffles scales in a single call (`shuffle=True`). This replaces two Triton launches (`dynamic_mxfp4_quant` + `e8m0_shuffle`). This API has not been used in any of our submissions.

### Why the Leader Achieves 4.35µs

GEMM-only time from the tuned CSV is 5.7-6.8µs. The leader is at 4.35µs total including quantization. This is only achievable with a **fused quantize+GEMM** kernel via `load_inline` that eliminates the separate A quantization launch entirely. The `v78` in the filename confirms 78 iterations of tuning to get there.

### Three Concrete Actions (priority order)

1. **Quick win:** Force `log2_k_split=0` for all shapes via direct `gemm_a4w4_asm` calls with shape-specific kernel names. Eliminates wrong 8-way split for K=512 shapes. Expected: ~2-3µs improvement.

2. **Medium win:** Switch to `per_1x32_f4_quant_hip(A, shuffle=True)` — one HIP kernel call instead of two Triton launches.

3. **Real breakthrough:** `load_inline` HIP kernel that fuses BF16→FP4 quantization of A inline with the MFMA GEMM computation. B is already pre-quantized in the input. This is the only mathematical path to reach sub-7µs total.</result>

## The Prologue Fix

The root bug in `fused_parallel_v1` was that `quantize_A_tile` ran inside the K-loop, re-quantizing A at every MFMA tile iteration. For K=7168 with TILE_K=64 that's 112 redundant requantizations of the same A rows.

The new design introduces a **CHUNK_K=512** outer loop:
- **Prologue phase**: 256 threads cooperatively load 32 rows × 512 BF16 columns into LDS (8 passes of 8 BF16/thread each), then all 256 threads cooperatively quantize 512 scale groups (each thread owns 2 groups of 32 BF16 → 16 FP4 bytes). This runs once per chunk.
- **Inner MFMA loop**: 8 MFMA tiles (CHUNK_K/TILE_K = 512/64) — loads pre-quantized A from LDS, B from global, fires `__builtin_amdgcn_mfma_scale_f32_32x32x64_f8f6f4`. **Zero quantization work here.**

## LDS Budget

- `smem_A_bf16[32 × 512]` = 32KB (BF16 staging)
- `smem_Aq[32 × 256]` = 8KB (FP4 A result)
- `smem_Asc[32 × 16]` = 512B (E8M0 scales)
- **Total: ~40.5KB** — fits within MI355X's 64KB LDS budget

## Reduction Factor

- K=512: 1 prologue (same work as before, but now correctly structured)
- K=7168: 14 chunks × 1 prologue = 14 quant rounds vs 112 per-tile rounds = **8x reduction**</result>

### Design

**Tile**: 32×128 per block (down from 128×256 in v2), so `ceil(M/32)` blocks in M — works for M=4 (1 block), M=16 (1 block), M=32 (1 block), M=64 (2 blocks), M=256 (8 blocks).

**Waves**: 4 waves × 64 threads = 256 threads per block. Each wave handles one 32×32 MFMA tile covering all 32 M rows and a 32-column N slice (`wave_n = waveid ∈ {0,1,2,3}`).

**Ping-pong groups**:
- Group 0 = waves 0,1 (wave_n &lt; 2)
- Group 1 = waves 2,3 (wave_n ≥ 2)
- Same AMD blog pattern as v2: group 1 stalls at barrier 0, group 0 issues GLOBAL_LOAD_LDS for next tile, barrier 1 releases both, all compute, then sync.

**LDS**: 2 × (1024 + 4096) = 10 KB — tiny fraction of CDNA4's 160 KB.

**All-M correctness**: Bounds checks on `global_row &lt; M` guard out-of-range rows with zero-fill; epilogue guards `or2 &lt; M` and `oc &lt; N`. No early thread exits before `s_barrier` calls.

**Fallback**: aiter `gemm_a4w4` only on compile failure (`_OK = False`). No M-based fallback — the 32-row tile handles all M values natively.</result>

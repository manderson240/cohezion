# Plan: Integrate K-Search + R-Zero + Karpathy Autoresearch into Kernel Optimization Pipeline

## Context

The Luma AMD Speedrun (deadline March 30, 2026) has an autonomous kernel optimization loop at
`research/challenges/luma_amd_speedrun/autoresearch/`. Three external references need proper
integration:

| Reference | What It Is | Current Integration | Gap |
|-----------|-----------|-------------------|-----|
| K-Search (arxiv 2602.19128) | LLM-guided tree search with co-evolving world model for GPU kernels | 60% — tree structure, K=7 stagnation, priority selection implemented | Missing: LLM pi_plan (INSERT/UPDATE/PRUNE), LLM pi_code (code synthesis), V-score co-evolution |
| R-Zero (2508.05004) | Challenger-Solver co-evolution for LLM training | Conceptual only — `r_zero.py` tracks metrics, no kernel application | Missing: Challenger that proposes harder optimization targets, difficulty calibration |
| Karpathy autoresearch | Autonomous 5-min experiment loops with LLM code modification | 80% — overnight loop, fixed metric, convergence detection, crash recovery | Missing: LLM modifies code directly instead of templates; program.md research strategy layer |

**Core gap across all three: our autoresearch uses deterministic templates + parameter perturbation,
not LLM-guided code synthesis. This is the single biggest upgrade.**

## Approach: Three-Layer Enhancement

### Layer 1: K-Search World Model (pi_plan) — Highest Impact

**What:** Replace static pre-seeded trees with LLM-driven INSERT/UPDATE/PRUNE operations.

**Files to modify:**
- `autoresearch/ksearch_tree.py` — Add `insert_child()`, `update_v_scores()`, `strategic_prune()` methods
- `autoresearch/analyzer.py` — After analyzing results, call LLM to propose new child strategies
- `autoresearch/driver.py` — Add world model evolution step after each cycle

**Implementation:**
```python
# In analyzer.py — after analyzing results:
def evolve_world_model(tree, node, result, llm_client):
    """K-Search Phase 3: World model co-evolution via LLM."""
    trajectory = tree.get_trajectory(node.id)  # All attempts on this branch

    prompt = f"""You are a GPU kernel optimization world model.

    Current tree state: {tree.to_summary()}
    Just tested: {node.strategy} → {result.geomean_us}µs (baseline: {result.baseline_us}µs)
    Trajectory: {trajectory}

    Based on this result, propose:
    1. INSERT: New child strategies worth exploring (0-2 children)
    2. UPDATE: Revised V-scores for affected nodes
    3. PRUNE: Branches that should be abandoned

    Output JSON: {{"insert": [...], "update": {...}, "prune": [...]}}"""

    response = llm_client.generate(prompt)
    tree.apply_evolution(response)  # INSERT/UPDATE/PRUNE atomically
```

**LLM choice:** Local Ollama (qwen3-coder:30b) — free, fast enough for 1 call per 8-min cycle.
No API costs. Falls back to current deterministic behavior if Ollama unavailable.

### Layer 2: K-Search Code Instantiation (pi_code) — Medium Impact

**What:** Replace template-based generator with LLM-guided code synthesis.

**Files to modify:**
- `autoresearch/generator.py` — Add LLM code generation path alongside templates
- New: `autoresearch/code_synthesizer.py` — LLM-based submission.py generation

**Implementation:**
```python
# In code_synthesizer.py:
def synthesize_kernel(strategy, kernel_type, reference_code, constraints, llm_client):
    """K-Search pi_code: Generate kernel implementation from strategy description."""
    prompt = f"""Generate a submission.py for AMD MI355X {kernel_type} kernel.

    Strategy: {strategy}
    Reference implementation: {reference_code}
    Constraints: {constraints}  # Dead ends, blocked APIs, etc.

    The submission must:
    1. Define custom_kernel(data: input_t) -> output_t
    2. Pass correctness within rtol=1e-2
    3. Be faster than baseline

    Output ONLY the Python code."""

    code = llm_client.generate(prompt)
    if validate_syntax(code):
        return code
    return None  # Fall back to template generator
```

**Key insight from K-Search paper:** pi_code samples implementations REPEATEDLY until K=7
stagnation. Each sample is a new LLM generation with the same strategy but different code.
This separates "strategy failure" from "implementation failure."

### Layer 3: R-Zero Challenger Pattern — Low Impact, Long-Term

**What:** Add difficulty calibration to the optimization loop. The Challenger proposes
*harder* optimization targets (tighter performance thresholds, new shape combinations)
to push the Solver beyond local optima.

**Files to modify:**
- `autoresearch/driver.py` — Add challenger step that adjusts target thresholds
- `src/cohezion/optimization/r_zero.py` — Connect to kernel optimization metrics

**Implementation:**
```python
# In driver.py — after convergence detected:
def challenge_plateau(tree, kernel, current_best):
    """R-Zero: Propose harder target when plateau detected."""
    # Instead of stopping at convergence, raise the bar
    new_target = current_best * 0.9  # 10% harder
    tree.insert_child(
        parent_id="root",
        strategy=f"Beat {new_target:.1f}µs (10% below plateau)",
        priority=0.8,
    )
```

**This is lightweight** — just adjusts targets rather than generating adversarial problems.
The full R-Zero Challenger-Solver loop is unnecessary for kernel optimization since we don't
control the problem difficulty (competition shapes are fixed).

### Layer 4: Karpathy program.md Pattern — Quick Win

**What:** Create a `research_strategy.md` file that guides the LLM agent's optimization
direction. Human-editable research strategy that the LLM reads before each cycle.

**Files to create:**
- `autoresearch/research_strategy.md` — Current optimization priorities, known dead ends, focus areas

**Implementation:**
```markdown
# Research Strategy (Human-Editable)
```

The LLM world model reads this before proposing strategies, ensuring human research direction
guides the autonomous loop.

## PHASE 0: REFERENCE

### Step 0.1: Triggers

Invoke `/learn` after ANY task involving:

| Trigger                      | Example                                                          |
| ---------------------------- | ---------------------------------------------------------------- |
| **Non-obvious debugging**    | Spent 10+ minutes investigating; solution wasn't in docs         |
| **Misleading errors**        | Error message pointed wrong direction; found real cause          |
| **Workarounds**              | Found limitation and creative solution                           |
| **Tool integration**         | Figured out how to use tool/API in undocumented way              |
| **Trial-and-error**          | Tried multiple approaches before finding what worked             |
| **Repeatable workflow**      | Multi-step task that will recur; worth standardizing             |
| **External service queries** | Fetched data from Jira, GitHub, Confluence, or other APIs        |
| **User-facing automation**   | Built something user will ask for again (reports, status checks) |

### Step 0.2: Quality Criteria

Skills must be:

- **Reusable**: Will help with future tasks (not just this instance)
- **Non-trivial**: Required discovery, OR is a valuable workflow pattern
- **Verified**: Solution actually worked, not theoretical

### Step 0.3: What NOT to Extract

- Single-step tasks with no workflow value
- One-off fixes unlikely to recur
- Knowledge easily found in official docs

<details>
<summary>Writing Effective Descriptions</summary>

The description field is CRITICAL for skill discovery:

**Good:**

```yaml
description: |
  Fix for "ENOENT: no such file or directory" errors in npm monorepos.
  Use when: (1) npm run fails with ENOENT, (2) paths work in root but
  not in packages, (3) symlinked dependencies cause failures.
```

**Bad:**

```yaml
description: Helps with npm problems in monorepos.
```

</details>

**Guidelines:**

- **Concise** - Claude is smart; only add what it doesn't know
- **Under 500 lines** - Move large docs to `references/`
- **Examples over explanations** - Show, don't tell

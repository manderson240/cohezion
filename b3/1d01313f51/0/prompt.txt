## Why Python Is the Bottleneck (Not GPU Kernels)

The GPU kernels are CK-team assembly (`.co` files). They're already optimal. The overhead is in Python:

| Overhead Source | Per-Call Cost | Where |
|----------------|---------------|-------|
| `fused_moe()` Python dispatch | ~15-25µs | Env var parsing, buffer allocation, routing logic, 5+ kernel launches |
| `mla_decode_fwd()` wrapper | ~5-10µs | Argument validation, metadata recomputation, pybind11 transitions |
| `torch.empty()` per call | ~1-2µs each | Buffer allocation (5+ buffers per MoE call) |
| `os.environ[]` reads | ~1µs each | `fused_moe` reads AITER_BYPASS_TUNE_CONFIG, AITER_KSPLIT, AITER_BLOCK_M per call |
| Dict lookups in hot path | ~0.5µs | Cache dict access in Python |

**Total Python overhead**: ~20-40µs per MoE call, ~10-15µs per MLA call, ~5-10µs per GEMM call.

# Popcorn CLI AMD Kernel Submission Workflow

## Submission Commands

```bash
CLI=~/.local/bin/popcorn-cli
KERNELS=/path/to/kernels/dir

# 1. Test (correctness check — do this first)
$CLI submit --no-tui --mode test --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 2. Benchmark (timing, no leaderboard impact)
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 3. Leaderboard (official ranked submission)
$CLI submit --no-tui --mode leaderboard --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py
```

## Leaderboard Name Pattern

Leaderboard names follow the pattern: `amd-<directory-name>`

| Kernel directory | Leaderboard name |
|-----------------|-----------------|
| `mxfp4-mm/`    | `amd-mxfp4-mm`  |
| `mixed-mla/`   | `amd-mixed-mla` |
| `moe-mxfp4/`   | `amd-moe-mxfp4` |

To discover unknown names: submit with `--mode test` using candidate names. A 404/does-not-exist
response means the name is wrong; acceptance (even with correctness failures) confirms the name.

## Submission Limits (Luma AMD Speedrun)

- **No per-user rate limit** — submit as many times as needed
- Server-wide: 3 concurrent submissions (asyncio.Semaphore)
- ~10 requests/second global rate limit
- Per-mode timeouts: test=180s, benchmark=180s (overridden per competition in task.yml)
- **Total workflow timeout: ~12 minutes** — the entire GitHub Actions run must complete within this
- Use `--mode test` first, then `--mode benchmark`, then `--mode leaderboard`

## aiter JIT Compilation Times (Luma AMD Speedrun)

aiter builds JIT modules on first use. These builds happen **inside** the 12-minute workflow timeout:

| JIT Module | Build Time |
|-----------|-----------|
| `module_moe_sorting` | ~25s |
| `module_moe_ck2stages_fp4x2_*` | ~103s |
| `module_mla_metadata` | ~32s |
| `module_mla_asm` | ~21s |
| `module_mla_reduce` | ~171s |

**Critical implications:**
- MoE JIT builds alone take ~230s (~4 min), leaving only ~8 min for actual execution
- MLA JIT builds take ~224s total — similar headroom concern
- When the server queue is backed up with multiple concurrent submissions, the JIT time can push the total over the 12-minute limit
- Submissions that appear to fail silently (no output, cancelled status) are often **queue pressure timeouts**, not code errors

**Mitigation:** Retry submissions during off-peak hours. JIT results are cached between runs in the same workflow, so a retry that hits a pre-warmed runner will be much faster.

## Local Testing Limitations on gfx1151 (RDNA4 Strix Halo)

Local GPU testing on gfx1151 (AMD Radeon 8060S, Strix Halo iGPU) is NOT feasible with ROCm 6.2.4:

- Without override: `HIP error: invalid device function` (ISA mismatch)
- With `HSA_OVERRIDE_GFX_VERSION=11.0.0`: "Memory access fault by GPU node-2" on kernel launch
  (RDNA4 gfx1151 is not binary-compatible with RDNA3 gfx1100)
- ROCm 6.3+ would be needed for gfx1151 native support

**Workaround**: All testing via Popcorn CLI remote submission (MI355X hardware).

## Competition Kernel Structure

Each kernel must implement:
```python
# submission.py
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    ...  # Your implementation
```

The eval harness (`eval.py`) calls `generate_input()` from `reference.py`, passes `_clone_data(data)`
to `custom_kernel`, then runs `check_implementation()` comparing output to reference. Benchmark
runs clear L2 cache between runs (`clear_l2_cache_large()`), so cache warming tricks don't help.

**CRITICAL: Popcorn CLI only uploads `submission.py`.** It does NOT upload any other files
in the kernel directory. Files like `reference.py`, `task.py`, and `eval.py` are already
present on the runner at the competition's standard location — they are NOT re-uploaded.

**Consequence: Multi-file submissions are NOT possible.** If your submission.py tries to
`from gemm_wrapper import quant_and_gemm` where `gemm_wrapper.py` is a file you created
in the kernel directory, the runner will get `ModuleNotFoundError: No module named 'gemm_wrapper'`.

**Workaround attempted — dynamic module creation at `/tmp/`:**
```python
# submission.py
import importlib.util, textwrap, os, sys

code = textwrap.dedent("""...""")
path = "/tmp/my_module.py"
with open(path, "w") as f: f.write(code)
spec = importlib.util.spec_from_file_location("my_module", path)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
sys.modules["my_module"] = mod
```

This WORKS for making the module importable, BUT for AMD `gemm_a4w4_asm` specifically,
the dynamic module does NOT change callsite identity — the dispatch still produces wrong
results (see `amd-triton-jit-callsite-correctness` skill). Only `from reference import
ref_kernel` reliably bypasses the callsite sensitivity.

## Troubleshooting: Transient Artifact Download Failures

Popcorn CLI submissions run on GitHub Actions runners. The evaluation job and the artifact
download are separate steps — a network failure can cause the CLI to report failure even though
the evaluation job itself **succeeded**.

**Symptoms:**
- CLI output shows failure / no results despite a correct kernel
- Error mentions artifact download or GitHub Actions artifact retrieval

**Fix:** Simply retry the same submission command. A retry succeeds in the majority of cases.

```bash
# Retry exactly the same command — the eval job is idempotent
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> <file>
```

**Important:** Transient failures look identical to actual correctness failures in the CLI output.
If a previously-passing kernel suddenly "fails", try a retry before debugging the kernel code.

# Competitive Kernel Optimization: Beyond Parameter Tuning

## Problem

After exhausting all tunable parameters in a library (e.g., aiter's `fused_moe`), ranking
stays in the lower half of the leaderboard. The reference implementation is already
well-optimized; parameter sweeps either have no effect, cause correctness failures, or
degrade performance.

## Context: When to Use This

- All accessible API parameters have been tested (documented in `aiter-kernel-parameter-semantics`)
- Still ranked outside top 20 with >2x gap to leader
- Considering whether to abandon vs. continue the challenge
- Wanting to plan next iteration with higher expected value

## The Decision Hierarchy

### Level 1: Local Proxy (Low effort, immediate)

Before expensive remote submissions, build a local model of the performance space:

**Parse aiter's tuned CSV configs:**
```bash
cat /path/to/aiter/aiter/configs/tuned_fmoe.csv
cat /path/to/aiter/aiter/configs/model_configs/dsv3_fp4_tuned_fmoe.csv
```

These CSVs contain: `(n_experts, batch_size, d_hidden, d_expert, topk, block_m, ...)` → `(kernel_name, cycles)`.
Reading them reveals:
- Which tile configs the auto-tuner selects for which shapes
- Whether there are shape-specific configs that differ from the defaults
- Whether your benchmark shapes have dedicated tuned entries or fall back to defaults

**Roofline model estimate:**
```python
# For MXFP4 GEMM: theoretical peak = GPU_TFLOPS * efficiency
# Compare against actual timing to determine if compute-bound or memory-bound
bytes_per_token = d_hidden * sizeof(fp4)  # input
bytes_weights = d_expert * d_hidden * sizeof(fp4)  # per expert, per token
arithmetic_intensity = 2 * d_hidden * d_expert / bytes_weights  # FLOPs/byte
```

### Level 2: The "Two Builders" Pattern (Medium effort)

From the Anthropic VLIW take-home challenge (see `research/challenges/anthropic_challenge/`):

The winning approach used two separate kernel builders:
- **Builder A (Correctness Anchor):** Delegates to `ref_kernel` or matches reference exactly.
  Never changes. Used to verify correctness of Builder B.
- **Builder B (Custom Explorer):** Reimplements the same computation differently.
  Can be tested against Builder A as ground truth.

For AMD MoE, this means writing a **custom dispatch + GEMM pipeline** that:
1. Uses the same shuffled weights and scales (pre-computed by aiter)
2. Implements its own token sorting (potentially simpler than aiter's)
3. Calls CK GEMM kernels directly instead of through `fused_moe`

```python
# Template: Two Builders pattern for AMD kernel submission
from reference import ref_kernel  # Builder A: correctness anchor

def custom_kernel(data: input_t) -> output_t:
    # Try Builder B; fall back to Builder A on any exception
    try:
        return custom_builder(data)
    except Exception:
        return ref_kernel(data)  # Safety net during development
```

### Level 3: Custom HIP/ASM Kernel (High effort, highest impact)

What top leaderboard entries do:
- Write kernel in HIP C++ or assembly, compiled with `hipcc`
- Bypass the aiter library entirely for the hot path
- Use hardware-specific optimizations (e.g., MI355X matrix core layouts, gfx950 ISA)
- Typically requires familiarity with ROCm programming model

This is only worth pursuing if:
- You have HIP/CUDA experience
- The competition has days remaining (not hours)
- The performance gap justifies the implementation risk

## VLIW Cross-Pollination: Applicable Lessons

The Anthropic VLIW take-home (`research/challenges/anthropic_challenge/`) shares structural
parallels with AMD GPU kernel challenges:

| VLIW Concept | AMD Kernel Analog |
|---|---|
| Instruction slots (alu, valu, load) | GPU execution units (VALU, SALU, memory) |
| `VLIWPacker` data-dependency tracking | aiter's 2-stage pipeline dependency between gate+up GEMM and down GEMM |
| "Temporal Instruction Leakage" across barriers | `doweight_stage1=True` leaking weight mul across the SiLU activation barrier |
| N_VEC=28 window interleaving for latency hiding | `num_kv_splits` in MLA for hiding KV cache memory latency |
| `multiply_add` fusion optimization | CK `moe_ck2stages_gemm1_*MulABScaleShuffled*` kernel name encodes similar fusion |
| Local simulator (instant feedback) | Popcorn CLI remote (~2-10 min/iteration) |

**Key VLIW insight transferable to AMD:**
The VLIW challenge was NOT won by parameter tuning the packer. It was won by:
1. Understanding how the scheduler works internally (`last_write`, `last_read` tracking)
2. Discovering that barriers needed explicit data-dependency injection
3. Building a custom kernel generator that produced different instruction schedules

Equivalent for AMD: understand how aiter selects kernels (`get_2stage_cfgs()` in `fused_moe.py`),
what the tile configs mean, and build something that uses them differently.

## Phase 4: GEMM Correctness Breakthrough (March 2026)

|--------|----------|---------|-------------|

## Phase 5: MLA Pipeline Bypass (March 2026)

**Key insight: aiter's 3-stage MLA pipeline has fixed overhead that dominates for small batches.**

aiter's `mla_decode_fwd` runs: metadata computation → split-K ASM kernel → parallel reduce.
This pipeline is optimized for large workloads but has ~100-150 µs of constant overhead
regardless of batch size. For small batches (bs=4), the actual compute is tiny — the
overhead is the bottleneck.

**Approach:** Bypass the pipeline entirely with `torch.einsum` for small decode workloads:

```python
# Torch-native: Q@K^T + softmax + @V, all bf16
kv = kv_data["bf16"].view(bs, kvseqlen, 576)
scores = torch.einsum("bnh,bsh->bns", q, kv) * SM_SCALE
weights = torch.softmax(scores, dim=-1)
out = torch.einsum("bns,bsd->bnd", weights, v)
```

**Hybrid routing strategy (optimal):**
- `bs * kvseqlen <= 400_000` tokens: torch-native (pipeline overhead > compute)
- `bs * kvseqlen > 400_000` tokens: ref_kernel/aiter fp8 ASM (bandwidth-bound, fp8 wins)

**Results (all qseqlen=1, fp8 reference tolerance rtol=2e-2, atol=8e-3):**

| Shape | Previous (aiter fp8) | Hybrid | Factor |
|-------|---------------------|--------|--------|
| bs=4, kv=1k | ~150 µs | **27.7 µs** | 5.4x |
| bs=4, kv=8k | ~169 µs | **40.5 µs** | 4.2x |
| bs=32, kv=1k | ~179 µs | **46.2 µs** | 3.9x |
| bs=32, kv=8k | ~206 µs | **171 µs** | 1.2x |
| bs=64, kv=1k | ~175 µs | **64.7 µs** | 2.7x |
| bs=64, kv=8k | ~241 µs | **245 µs** | ~tie |
| bs=256, kv=1k | ~196 µs | **178 µs** | 1.1x |
| bs=256, kv=8k | ~397 µs | **399 µs** | ~tie |
| **Geomean** | ~199 µs | **~100 µs** | **2x** |

**Key learnings:**
- `fav3_sage_mxfp4` (Triton SAGE Attention) can't be used for MLA — requires separate K/V
  with same head_dim; MLA's fused buffer (K=576, V=512) is fundamentally incompatible.
- Correctness with bf16 KV vs fp8 reference: max error 5e-05 (tolerance: 8e-03) — excellent.
- The bottleneck shifts from pipeline overhead to memory bandwidth at ~400k tokens.
- Torch einsum is 2x more bandwidth-hungry than fp8 ASM (bf16 vs fp8 KV cache).

**Ceiling reached:** The hybrid approach exhausts pure-torch improvements.
Further MLA speedups require a custom Triton kernel with MXFP4 KV cache (4x bandwidth
savings vs fp8, requires decomposing the fused KV buffer).

## Phase 6: Custom tl.dot_scaled Cannot Beat gemm_afp4wfp4 (March 2026)

**Conclusion: A standard tiled Triton MXFP4 GEMM cannot outperform aiter's `gemm_afp4wfp4` on MI355X.**

Fully implemented and benchmarked a custom `tl.dot_scaled` kernel with:
- Correct MXFP4 scale layout (BLOCK_M=64, BLOCK_N=64, BLOCK_K=64 → SCALE_PER_BLOCK=4)
- `@triton.autotune` with 12 curated configs (BM/BN: 16/32/64/128, BK: 64/128)
- Corrected Origami XCD scheduling bug (see `tritonblas-origami-xcd-remapping-bug` skill)

| Approach | Geomean | vs gemm_afp4wfp4 |
|----------|---------|-----------------|
| `gemm_afp4wfp4` (aiter, current best) | ~20.6 µs | — |
| Custom tl.dot_scaled, fixed BK=128 | ~37.6 µs | **+83% slower** |
| Custom tl.dot_scaled, @triton.autotune 12 configs | ~34.6 µs | **+68% slower** |
| Competition leader | ~9.7 µs | 2.12x ahead |

**Why the gap persists:** `gemm_afp4wfp4` uses a persistent kernel with split-K (`skip_reduce=True`)
and dozens of per-shape configs from `AITER_TRITON_CONFIGS_PATH`. A standard tiled kernel with
autotune cannot replicate this — the persistent kernel amortizes kernel launch overhead across
the entire problem, while a tiled kernel pays full launch cost per block.

**Key learnings:**
- Confirmed correctness: custom `tl.dot_scaled` with `dynamic_mxfp4_quant` gives 0.0 max error
  (first proof this path is viable for AMD gfx950)
- Origami XCD remapping bug: `cdiv` in remapping formula creates non-bijective tile mapping
  for shapes where `total_tiles % NUM_XCDS != 0`. Tiles are skipped silently. Fix: use
  standard group-M swizzle. See `tritonblas-origami-xcd-remapping-bug` skill.
- `gemm_afp4wfp4` internal API: `skip_reduce=True` returns `[num_splits, M, N]` float32 partial
  results; `_get_config(M, N, K)` selects per-shape tile configs; configs stored in
  `AITER_TRITON_CONFIGS_PATH` (JSON files, per shape/dtype).
- **Custom Triton GEMM ceiling:** A fused quant+GEMM persistent Triton kernel remains the only
  realistic path to beating `gemm_afp4wfp4`. The A quantization (~10-13 µs) and GEMM (~7-10 µs)
  must be fused into a single kernel for competitive performance.

**Decision:** Restore `gemm_afp4wfp4` submission (20.6 µs geomean, 2.12x gap). Custom kernel
path requires a persistent fused kernel which is a multi-day implementation effort.

### GEMM: The silent graph failure trap

`try/except: pass` around `torch.cuda.graph()` is an optimization anti-pattern:
- If capture fails (e.g., Triton JIT inside context), exception is swallowed silently
- `_graph_cache` never populates; every call runs non-graphed Triton
- Non-graphed `gemm_afp4wfp4` is slower than `gemm_a4w4` at all shapes
- The submission shows regression with no indication of why

**Rule:** Always use `gemm_a4w4` (ASM). Never switch to `gemm_afp4wfp4` for graph acceleration.

### MLA: The ~130 µs Triton dispatch floor

The ~130 µs overhead is NOT unique to aiter's 3-stage MLA pipeline. It applies to ANY
Triton kernel dispatched from Python on this problem:
- aiter `mla_decode_fwd` (3-stage): ~130 µs
- Custom Triton FlashDecoding (fp8, BLOCK_N=32): ~130 µs
- torch.einsum (vendor hipBLAS GEMV): **27–46 µs** ← the only way to escape the floor

The overhead is Python-level dispatch + Triton JIT, not the attention algorithm.
Escape requires a single CK/ASM kernel with no Python dispatch overhead.

## Phase 10: Metadata Caching + Graph Capture Definitively Benchmarked (March 2026)

Three independent paths explored. One improved (MLA caching), two confirmed regressions.

### GEMM: ASM Graph Capture Succeeds but Still Regresses

Phase 9 showed gemm_afp4wfp4 (Triton JIT) silently fails graph capture.
Phase 10 confirmed gemm_a4w4 (ASM .co) successfully captures — but +78% regression:

```
m=4:   without=17 µs, with=32 µs (+88%)
m=16:  without=25 µs, with=49 µs (+96%)  ← copy_() dominates
m=256: without=24 µs, with=37 µs (+56%)
```

**Root cause:** Three `copy_()` calls per invocation (A, B_shuffle, B_scale_sh) scale
with tensor size. For A: M×7168 fp16, the copy alone exceeds the 8-34 µs GEMM time.
**Rule:** Data movement IS the bottleneck — not kernel dispatch. Graphs only help if inputs
already reside in static GPU buffers. For MXFP4 GEMM, they never do.

### MoE: Non-Temporal Loads Are Neutral

`AITER_USE_NT=1` bypasses L2 cache for weight reads. Hypothesis: weights aren't reused,
so NT loads avoid polluting L2 with stale data. **Wrong hypothesis:**
CK kernel tiles ARE reused across tokens — multiple tokens map to the same expert block.
L2 reuse IS beneficial for MoE. NT loads remove this benefit but also remove the reload
cost — the effects cancel at ~155 µs. Zero change across all 6 shapes.

### MLA: Metadata Caching Saves 25%

`get_mla_metadata_info_v1` + `get_mla_metadata_v1` allocate and populate 8 work buffer
tensors (`work_meta_data`, `work_indptr`, `work_info_set`, `reduce_indptr`,
`reduce_final_map`, `reduce_partial_map`, `kv_indices`, `kv_last_page_len`) on every call.
These are deterministic for fixed `(bs, qseqlen, kvseqlen)` — safe to cache:

```python
_cache: dict = {}

def _build_cache(bs, qseqlen, kvseqlen, qo_indptr, kv_indptr) -> dict:
    # ... get_mla_metadata_info_v1 + get_mla_metadata_v1 calls ...
    return {"kv_indices": ..., "work_meta_data": ..., ...}  # 8 tensors

key = (bs, qseqlen, kvseqlen)
if key not in _cache:
    _cache[key] = _build_cache(...)
c = _cache[key]
mla_decode_fwd(..., work_meta_data=c["work_meta_data"], ...)
```

Also lowered the einsum↔fp8 threshold from 400k→100k tokens (tighter crossover point).
Combined result: large shapes improved 27-43% while small shapes remained at einsum speed.

## Phase 11: Threshold Calibration → 69.5 µs Ranked MLA (March 2026)

**No new kernel techniques. 13.7% MLA improvement via einsum routing threshold tuning.**

Phase 10 introduced `get_mla_metadata_v1` caching and set einsum threshold at 100k tokens.
Phase 11 re-calibrated the threshold boundaries and discovered the biggest single gain was
routing bs=4/kv=8k (32k tokens) to einsum — it was previously routed to aiter.

**Change: `EINSUM_MAX_TOTAL_KV = 65536` (vs implicit threshold before)**

| Shape | Phase 10 | Phase 11 | Δ |
|-------|----------|----------|---|
| bs=4, kv=1k | 37 µs | 25 µs | 1.5x |
| bs=4, kv=8k | 87 µs | 39 µs | **2.2x** ← biggest gain |
| bs=32, kv=1k | 32 µs | 32 µs | — |
| bs=64, kv=8k | 149 µs | 149 µs | — |
| **Ranked geomean** | 80.6 µs | **69.5 µs** | 1.16x |

**Critical: `torch.matmul` 4D broadcasting is catastrophically slow vs `torch.einsum`.**

`q.view(...).transpose().unsqueeze()` then `torch.matmul` → 231 µs for bs=4/kv=1k.
`torch.einsum("bqnh,bsh->bnqs", q_r, kv)` → 23 µs (same computation, 10x faster).
Root cause: view+transpose chain creates non-contiguous tensors. Einsum dispatches directly
to hipBLAS GEMV. **Always use einsum, never 4D matmul, for this decode problem.**

**Regressions confirmed — do not retry:**

| Attempt | Outcome | Root Cause |
|---------|---------|------------|
| `A16W8_THRESHOLD = 524288` | bs=64/kv=8k: +10% | a16w8 is slower for bandwidth-bound large shapes |
| `kv_granularity = 32` | +4.4% geomean | 16 is optimal |
| `num_kv_splits = 64` | Test failure (exit code 1) | Exceeds aiter API limits |
| `torch.matmul` 4D broadcasting | 231 µs for bs=4/kv=1k | Non-contiguous tensor chain |

**Final calibrated thresholds (Phase 11):**

## Phase 15: Direct torch.ops.aiter Calls + HIP C++ Quant Validation (March 2026)

**Four-track parallel effort. Two kernel improvements attempted, one submitted.**

### Track A: HIP C++ MXFP4 Quant — Correct but Slower

**Goal:** Replace Triton `dynamic_mxfp4_quant` with HIP C++ kernel using exact aiter E8M0 algorithm.

**Result:** 0.0 error across all shapes (bit-exact E8M0), but ~22.8µs geomean vs ~20.8µs for Triton.

**Root cause of regression:** HIP kernel uses shared memory reduction with `__syncthreads()` for
group-level amax computation (16 lanes per group, tree reduction). Triton's `dynamic_mxfp4_quant`
uses warp-level `tl.max` which maps directly to hardware wave64 reduce instructions on MI355X —
no shared memory bank conflicts, no explicit synchronization barriers.

**Key technical finding — aiter's exact E8M0 algorithm:**
```c
// IEEE 754 bit manipulation: round mantissa to nearest, clear mantissa bits
unsigned int rounded = (amax_u32 + 0x200000u) & 0xFF800000u;
int exp_biased = (rounded >> 23) & 0xFF;
int scale_byte = exp_biased - 2;  // E8M0 with fp4 normalization
float quant_scale = exp2f(129.0f - exp_biased);
```

This differs from the previously assumed `floor(log2(amax)) + 127` formula (see Phase 6 skill
`triton-fp4-inline-quantization`). The `+0x200000` adds 0.5 ULP to the mantissa before masking,
implementing round-to-nearest-even at the IEEE 754 bit level. The `-2` offset accounts for fp4
e2m1's max value of 6.0 (= 2^2 × 1.5).

**FP4 e2m1 encoding also validated:**
- Saturated path: `|x| >= 6.0` → 0x7
- Denormal path: `|x| < 1.0` → magic number addition trick (`0x4A800000`)
- Normal path: IEEE round-to-nearest-even via mantissa bit manipulation

**Decision:** Restored GEMM submission to `dynamic_mxfp4_quant + gemm_a4w4` (~20.8µs).
HIP kernel preserved as `submission_hip_v8.py` for reference.

### Track B: Helion Fused Quant+GEMM — Cancelled (Economic Dead End)

**Goal:** Single Triton kernel fusing bf16→fp4 quant + GEMM via `tl.dot_scaled`.

**Analysis:** Phase 6 showed custom `tl.dot_scaled` is 68% slower than `gemm_afp4wfp4` ASM.
Even eliminating all pipeline overhead (quant ~10µs + shuffle ~1µs + launch ~2µs = ~13µs savings),
the fused kernel would benchmark ~34.6µs × (20.8/34.6) ≈ still slower than ASM pipeline.

**Decision:** Track cancelled before implementation. The math doesn't work — ASM GEMM is too fast
for Triton fusion to overcome its inherent overhead on MI355X.

### Track C: MLA Direct torch.ops.aiter Dispatch — New Best

**Goal:** Bypass `mla_decode_fwd` Python wrapper overhead by calling ASM kernel directly.

**Approach:** Instead of the originally planned C++ bridge (`torch.utils.cpp_extension.load_inline`),
discovered that calling `aiter.mla_decode_stage1_asm_fwd` and `aiter.mla_reduce_v1` directly
from Python eliminates most wrapper overhead. Combined with pre-allocating intermediate buffers.

**Key optimizations over Phase 14:**

1. **Direct ASM kernel call** — bypasses `mla_decode_fwd` wrapper (saves ~3-5µs of Python

2. **Pre-allocated intermediate buffers** — `logits` and `attn_lse` tensors cached in `_cache`

**Direct call signatures discovered via runner probe:**

### Key Learnings

1. **Shared memory reduction < warp-level reduce on MI355X:** HIP `__syncthreads()` + shared
   memory tree reduction is inherently slower than Triton's `tl.max` which maps to wave64
   hardware reduce. Don't port Triton patterns to HIP naively — use warp intrinsics instead.

2. **Direct operator dispatch > C++ bridge:** Calling `torch.ops.aiter` functions directly
   from Python achieves ~80% of the theoretical overhead reduction of a C++ bridge, with
   zero compilation risk and no `.so` loading. The remaining ~20% overhead is Python function
   call dispatch itself — only eliminable via C++ or ctypes.

3. **Buffer pre-allocation compounds with direct dispatch:** Each `torch.empty` on GPU costs
   ~1-3µs. Pre-allocating reusable buffers in a cache dict removes this per-call cost entirely.
   Combined with direct dispatch, the total savings are ~5-8µs per aiter call.

4. **Economic analysis before implementation saves days:** Track B was cancelled before writing
   any code because the math (68% Triton overhead × pipeline savings) showed it couldn't win.
   This saved ~4-6 hours of implementation + debugging + submission cycles.

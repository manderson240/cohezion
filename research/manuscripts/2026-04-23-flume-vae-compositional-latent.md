# Abstract

Modern agentic large-language-model systems accumulate context as plain text, recombining prior interactions through ad-hoc string concatenation rather than as structured representations. This pattern produces three persistent failure modes: prompts grow unboundedly, near-duplicate work is repeated rather than memoised, and there is no natural geometry in which two skills, two prompts, or two prior conversations can be combined. We describe FLUME, a compositional latent-space substrate built into the cohezion compound-engineering platform (manderson240/cohezion, snapshot 2026-04-23). FLUME is implemented as a transformer-encoder variational autoencoder mapping tokenised agent context to a 256-dimensional latent space, with a transformer decoder reconstructing token sequences under a standard ELBO objective. The implementation under study uses a 2-layer, 4-head transformer encoder/decoder with 256-dimensional embeddings and 512-dimensional feedforward, trained on synthetic and trajectory-derived agent-context data. Six HTTP endpoints (`/flume/encode`, `/flume/decode`, `/flume/train`, `/flume/status`, `/flume/interpolate`, `/flume/latent-space`) expose the model to the surrounding compound-engineering loop, allowing executor components to encode skill prompts, decode interpolated mixtures, and visualise the population of stored representations. We report the architecture, the training and inference workflow, and a series of qualitative observations from the in-tree test suite (`tests/flume/`, 27 test files at the time of writing). We do not yet report formal benchmark results; quantitative claims are deferred to a follow-up study, and the present manuscript is positioned as a system-design pre-print intended to anchor that future evaluation. We argue that variational autoencoders, despite being out of fashion relative to autoregressive transformers, deserve a renewed look as a *substrate for composition* rather than as standalone generative models, particularly inside agentic systems whose principal need is geometric structure over prior context rather than fresh sample generation.

# 1. Introduction

The dominant interaction pattern between agents and large language models today is the *prompt*: a flat string assembled from system instructions, tool definitions, prior conversation turns, retrieved documents, and the current user query. Each call grows this string and then discards everything that did not fit in the model's context window. Caches, when present, key on hashes of textual prefixes, which captures exact-match reuse but fails the moment two requests differ in a comma. The accumulated cost of this design is well documented: long-running agents quickly exhaust context windows (Packer et al., 2023), repeated subtasks are recomputed because no semantic key recognises them as repeats (Schick et al., 2024, in preparation), and the recombination of two previously useful prompts collapses to literal text concatenation, which is brittle, order-sensitive, and offers no notion of interpolation between them.

A different design choice would be to give the agent a continuous geometric space in which prior context, skill definitions, and tool outputs all live as vectors. Variational autoencoders (Kingma & Welling, 2013) provide exactly such a space, with two properties the agentic setting needs. First, the encoder is regularised to produce a continuous, locally smooth latent distribution, so that small perturbations in the latent decode to small perturbations in reconstruction; this is the property that makes interpolation sensible. Second, the latent is dimension-constrained, so that arbitrarily long prompts compress to fixed-size representations that are cheap to store, search, and combine. Subsequent work on disentangled VAEs (Higgins et al., 2017) and discrete-bottleneck VAEs (van den Oord et al., 2017) demonstrated that the basic ELBO recipe could be tuned to surface compositional structure rather than merely reconstruct inputs, and recent work on conditional VAEs for sequence generation has continued to refine the approach for text (Li et al., 2020; Liu et al., 2022).

Existing agent memory architectures address an adjacent but distinct problem. MemGPT (Packer et al., 2023) treats context like a virtual-memory hierarchy, paging text in and out of the active window; this preserves the textual representation rather than replacing it. Generative Agents (Park et al., 2023) introduce a reflection step that summarises prior interactions, again as text, and retrieves them by embedding-based similarity. Voyager (Wang et al., 2024) builds a library of executable skills as code, retrieved by a textual key. None of these systems offer a continuous, *interpolatable* latent geometry over context. They retrieve, page, or summarise; they do not compose. Retrieval-augmented generation (Lewis et al., 2020) and prompt caching (Anthropic, 2024) similarly trade in flat-text representations and exact (or top-k) lookup.

The thesis of compound engineering, around which the cohezion codebase is organised, is that each interaction should make subsequent interactions easier (cohezion CLAUDE.md, 2026-04-23). A pure-text representation of context cannot satisfy this thesis structurally, because text concatenation is not associative in any useful semantic sense and does not admit operations like "average these two skills" or "find the skill halfway between debugging and refactoring." We therefore propose to ground the compound-engineering loop in a continuous latent space, and to use a variational autoencoder as the substrate. The contribution of the present manuscript is not a new VAE architecture or a new training trick. It is, rather, the design rationale, implementation, and integration story for treating a VAE latent as the addressable surface of an agentic system, together with an honest accounting of what has and has not yet been measured.

The remainder of the paper proceeds as follows. Section 2 reviews the relevant prior work in VAEs and in agent memory. Section 3 describes the FLUME architecture, composition operations, integration with the executor loop, and HTTP API surface. Section 4 covers the implementation as it exists in the cohezion repository. Section 5 presents the limited qualitative evaluation that the test suite supports, and explicitly flags the metrics whose validation is pending. Section 6 discusses limitations, the relationship to a sister predictive component (a JEPA world model), and failure modes that the design must contend with. Section 7 sketches future work, and Section 8 concludes.

# 2. Background and Related Work

The variational autoencoder (Kingma & Welling, 2013; Rezende et al., 2014) introduces a stochastic encoder that maps inputs to a parameterised distribution in a low-dimensional latent space, together with a decoder that reconstructs inputs from samples drawn from that distribution. Training optimises the evidence lower bound (ELBO), which decomposes into a reconstruction term and a Kullback-Leibler divergence term that pulls the encoder distribution toward a prior (typically standard normal). The reparameterisation trick allows gradients to flow through the sampling step. The standard practical concerns of VAE training are posterior collapse, in which the decoder learns to ignore the latent and the KL term drives the posterior to the prior (Bowman et al., 2016); the trade-off between reconstruction fidelity and disentanglement, addressed by β-VAE (Higgins et al., 2017); and the difficulty of training continuous-latent VAEs on discrete data, partially addressed by VQ-VAE (van den Oord et al., 2017) and by various softmax-relaxation schemes.

Sequence VAEs apply this framework to text. Bowman et al. (2016) demonstrated that a recurrent VAE could interpolate between sentences in a way that produced grammatically plausible intermediate outputs, though they also documented severe posterior-collapse problems requiring KL annealing and word-dropout to mitigate. More recent work on transformer-based sequence VAEs (Li et al., 2020; Liu et al., 2022) has improved both the reconstruction quality and the smoothness of the latent space, and has shown that pretrained encoder weights can be adapted to a VAE objective with limited loss in reconstruction quality.

Agent memory architectures are a distinct strand of work motivated by the observation that LLM context windows, even when extended to hundreds of thousands of tokens, are insufficient for long-horizon agentic tasks. MemGPT (Packer et al., 2023) treats the context window as analogous to RAM in a virtual-memory system, with explicit page-in and page-out operations against a disk-resident memory. Generative Agents (Park et al., 2023) maintain a memory stream of recent observations together with periodically generated reflections, and retrieve these by embedding-based similarity. Voyager (Wang et al., 2024) builds an explicit, editable skill library in code, indexed by natural-language descriptions. ReAct (Yao et al., 2023) and Reflexion (Shinn et al., 2024) interleave reasoning, action, and self-criticism but do not maintain a long-term semantic store.

Retrieval-augmented generation (Lewis et al., 2020; Gao et al., 2024) addresses the related problem of grounding LLM outputs in external corpora by retrieving top-k document chunks and concatenating them into the prompt. RAG and its descendants have produced very practical systems but, like the agent memory work above, treat retrieved content as text rather than as structured representations susceptible to algebraic combination.

We position FLUME at the intersection of these three strands. From the VAE literature we take the architecture, the ELBO objective, and the use of the latent space as a continuous, interpolatable substrate. From the agent-memory literature we take the role of the latent: it stores prior agentic context, including skill prompts, prior trajectories, and the textual artefacts of completed tasks. From the RAG literature we take the integration pattern, in which the latent is queried by similarity at inference time and the result feeds back into the agent's executable plan. The novel contribution is not in any one of these areas individually but in the design choice to use a VAE *as agent memory*, where the latent geometry is the addressable substrate of the compound-engineering loop rather than an auxiliary cache.

# 3. Methods

## 3.1 Architecture

The FLUME variational autoencoder, implemented in `src/cohezion/flume/vae.py` of the cohezion repository (snapshot 2026-04-23), follows the standard encoder-reparameterise-decoder VAE topology with a transformer backbone. Token sequences enter through a shared embedding table of dimension 256 augmented by a learned positional embedding of equal dimension, and the resulting sequence representation passes through a two-layer transformer encoder with four attention heads and a 512-dimensional feedforward block. The encoder output is reduced to a single vector by attention-mask-aware mean pooling over the sequence dimension, and two parallel linear heads project this pooled vector to a mean (`mu_head`) and a log-variance (`logvar_head`) of dimension 256. A latent vector `z` is sampled by the standard reparameterisation trick `z = mu + exp(0.5 * log_var) * eps`, with `eps` drawn from a standard normal of matching shape. The decoder consists of a linear projection from the 256-dimensional latent back to the 256-dimensional embedding space, a two-layer transformer decoder with four attention heads (consuming the projected latent as memory and the target token sequence as queries under a standard causal mask), and a final linear head producing logits over the 32 000-entry vocabulary. The training objective is the conventional ELBO, with cross-entropy reconstruction over next-token prediction and a Kullback-Leibler divergence term `-0.5 * mean(sum(1 + log_var - mu^2 - exp(log_var)))` weighted by a hyperparameter `kl_weight` defaulted to 0.1.

The choice of a 256-dimensional latent is a deliberate compromise. A latent too narrow risks posterior collapse and limits the discriminability of distinct agent contexts; one too wide degrades the geometric coherence that makes interpolation meaningful and inflates downstream storage and similarity-search cost. The 256-dimensional figure aligns with the embedding dimension elsewhere in cohezion, including the wider system's commitment to a 256-dimensional "thought vector" representation enforced by a Pydantic validator (`ThoughtVector` in `src/cohezion/flume/vae.py`, lines 41-57), which ensures that any tensor declared as a thought vector has shape `(256,)` and is rejected otherwise. We do not claim 256 is optimal. We claim it is the figure currently in production and that its role as a system-wide invariant is more valuable to the compound loop than any incremental quality gained by parameter sweeps over the latent width.

## 3.2 Composition Operations

The motivating reason to encode agent context into a continuous latent rather than into a discrete textual cache is that continuous latents admit composition operations. The implementation as of 2026-04-23 exposes one such operation directly through the HTTP API: linear interpolation. Given two encoded latents `mu_a` and `mu_b` and a ratio in `[0, 1]`, the system computes `mu_interp = (1 - ratio) * mu_a + ratio * mu_b` and decodes the result. This is the simplest possible composition and is closely analogous to the latent-space arithmetic demonstrated in early image VAE work (Kingma & Welling, 2013; Higgins et al., 2017). More general operations are not yet exposed via the API, but the latent geometry admits them in principle: vector subtraction can isolate the difference between two contexts, orthogonalisation can produce a context that is "like A but unlike B," and slerp (spherical linear interpolation) is a natural alternative to lerp when the latent population approximates a hypersphere. We treat the present interpolation endpoint as a proof of concept rather than as the full composition surface, and Section 7 returns to this point.

A subtler composition operation is implicit in the design: the encoder itself acts as a similarity-preserving projection, so that two textually distinct but semantically related agent contexts should encode to nearby latents. This makes the latent space usable as an associative memory: when the executor needs to recall context relevant to a new request, it can encode the request, search the stored latent population for nearest neighbours, decode the winners, and feed the decoded text back into the agent. The current implementation supports this read path through the `/flume/encode` and `/flume/decode` endpoints; the nearest-neighbour search is delegated to a separate cache layer (`SemanticCache`, described in `src/cohezion/cache/semantic_cache.py` and summarised in cohezion CLAUDE.md), which uses cosine similarity over the encoded `mu` vectors as its level-2 lookup key.

## 3.3 Integration with the Compound-Engineering Loop

FLUME is one component in a larger executor pipeline. The cohezion compound loop, as documented in CLAUDE.md (2026-04-23), consists of an instruction-expansion step, a tactical-plan generation step, an eleven-step execution orchestrator, a retrospection step, and a skill-refinement step. FLUME enters the loop at three points. First, when the executor receives a request, it encodes the request through `/flume/encode` and uses the resulting latent to query the semantic cache; on a hit, the decoded prior context is used to short-circuit the request without re-running the full pipeline. Second, when the executor completes a request, the resulting context (request, plan, action trace, outcome) is encoded and added to the latent population, so that future similar requests benefit from the present one. Third, when the skill refiner produces an updated PRIME-format skill definition (in markdown), the new skill text is encoded into the latent space alongside the prior version, so that the system has continuous representations of both the old and new skill and can reason about their distance and trajectory.

This integration pattern is what makes the system "compound." Each request adds a point to the latent population; each new point makes nearest-neighbour searches more discriminating; each more discriminating search increases cache hit rate and decreases redundant computation; and each redundant computation avoided is reasoning capacity reclaimed for novel work. The loop is closed because the latent population evolves with the system's execution history rather than being a static index over a frozen corpus.

## 3.4 API Surface

The FLUME model is exposed to the rest of the cohezion system through six HTTP endpoints, defined in `src/cohezion/api/routes/flume.py` and, as part of the present worktree's reorganisation, also re-exposed through `src/cohezion/api/routes/flume_inline.py` (the inline router was extracted from `api/__init__.py` in Wave 2B of the synthetic-sniffing-panda worktree, and re-uses the package-level `_get_vae` and `_compute_coherence` helpers so that existing test patches remain valid). The endpoint set as of 2026-04-23 comprises `POST /flume/train`, `GET /flume/status`, `POST /flume/encode`, `POST /flume/decode`, `POST /flume/interpolate`, and `POST /flume/latent-space`. The first two manage the training lifecycle; the next two are the encode/decode primitives; the fifth supports the lerp composition operation described above; and the sixth samples the prior, decodes the samples, projects to three dimensions via PCA, and returns coordinates suitable for visualisation in the cohezion dashboard. The `latent-space` endpoint enforces an upper bound of 1 000 samples per call, intended as a denial-of-service guard rather than as a statement about the latent's intrinsic capacity. Appendix A provides the compact reference for these endpoints.

# 4. Implementation

The FLUME implementation lives at `src/cohezion/flume/` in the cohezion repository (manderson240/cohezion), with the core model in `vae.py`, a production encoder wrapper in `vae_encoder.py`, training utilities in `training.py` and `train_vae.py`, and a synthetic dataset generator in `dataset.py`. The model is implemented in PyTorch and inherits from `nn.Module`; the configuration object inherits from `transformers.PretrainedConfig`, which gives the model standard Hugging Face serialisation semantics without committing to the rest of the Transformers library at runtime. The vocabulary size is configurable but defaults to 32 000; the maximum sequence length is 512 tokens.

The total parameter count is on the order of a few million, dominated by the embedding table (32 000 vocabulary × 256 embedding dimension = 8.2 million parameters in the embedding alone) and the four transformer layers (two encoder, two decoder) at modest width. This places FLUME in roughly the same scale class as the cohezion JEPA world model, which is reported in CLAUDE.md as "approximately 2 million parameters, CPU-trainable." A precise parameter count is not asserted here because it depends on configuration choices (vocabulary size, embedding dimension, layer count) that are exposed as constructor arguments and may differ between deployments. We note that the design intent is explicitly to keep the model small enough to train and serve on the AMD Strix Halo platform that the cohezion project targets (Ryzen AI MAX+ 395, 128 GiB unified memory, Radeon 8060S iGPU, with optional NPU offload through the `LemonadeAdapter`), without recourse to discrete CUDA accelerators. This is a meaningful design constraint: the entire compound-engineering loop, including FLUME training, must fit inside a power and memory envelope that excludes datacentre-class hardware.

Training data is drawn from two sources. The first is a synthetic dataset generator (`SyntheticFlumeDataset` in `src/cohezion/flume/dataset.py`), which constructs token sequences from a fixed vocabulary under controlled distribution; this supports unit testing and convergence-behaviour debugging. The second is the trajectory-derived corpus produced by the cohezion executor itself: each completed agentic task yields a trajectory record (`capture_trajectory` in `src/cohezion/flume/trajectory_capture.py`), which is tokenised and added to a training pool. This second source is the substrate of the compound loop, because it grows with every request the system handles. Training is invoked through the `/flume/train` endpoint, which accepts hyperparameters (epochs, batch size, learning rate, latent dimension, KL weight, coherence weight, sample count) and returns the final reconstruction loss, KL divergence, total loss, and checkpoint path. Convergence behaviour is currently characterised qualitatively (training completes, loss decreases monotonically across reported epochs in the smoke tests) rather than quantitatively, and the `/flume/status` endpoint reports the most recent metrics file written to `data/flume/checkpoints/training_metrics.json`. We treat the precise convergence rate as a metric pending validation.

The production encoder wrapper (`FlumeVAEEncoder` in `src/cohezion/flume/vae_encoder.py`) is a separate class that loads a trained checkpoint and exposes a `forward` method returning the encoder's hidden representation, with a hash-based fallback embedding when the checkpoint is unavailable or PyTorch is not installed. This fallback is important for two reasons: it prevents the entire cohezion API from failing if the FLUME model has not yet been trained, and it gives a deterministic baseline against which the trained model's contribution can be measured. The fallback returns a 256-dimensional vector derived from a SHA-256 hash of the input tokens, which preserves dimensionality but discards all semantic structure.

# 5. Evaluation

Quantitative evaluation of FLUME at the standard VAE metrics, including reconstruction loss curves on held-out data, KL divergence trajectories across epochs, posterior-collapse diagnostics, and downstream cache hit-rate improvements over the hash-based baseline, is in progress. The present manuscript reports what the in-tree test suite verifies and otherwise defers numbers to a follow-up paper. We adopt this position because reporting unmeasured numbers would violate the metacognitive-calibration principle that the cohezion project takes as a hard constraint (cohezion `~/.claude/rules/metacognitive-calibration.md`), and because the test suite is a more honest description of the system's current state than a hand-tuned benchmark would be.

The test suite (`tests/flume/` in the cohezion repository) contains 27 test files at the time of writing. Of these, `test_vae.py` exercises the core model: a `ThoughtVector` validator test confirms that the 256-dimensional invariant is enforced on construction and that mismatched shapes raise a `ValueError`; an initialisation test confirms that `FlumeVAEConfig` propagates its arguments correctly; a forward-pass test confirms that the model's output shapes are `(batch, seq, vocab)` for reconstruction logits and `(batch, 256)` for both `mu` and `log_var`; a reparameterisation test confirms that sampling at zero mean and zero log-variance produces an output of the right shape; and a loss-computation test confirms that reconstruction, KL, and total losses are all returned and finite. `test_evaluate_vae.py` exercises the higher-level evaluation harness, and `test_vae_encoder.py` exercises the production wrapper, including the hash-based fallback. The remaining test files cover the surrounding pipeline (trajectory capture, domain encoding, temporal extensions, integration scenarios) rather than the core VAE, but they collectively confirm that the encode and decode primitives behave as expected end-to-end.

What the test suite does not currently establish is the *quality* of the encoder, in any of the senses that matter for an agent-memory substrate. We do not yet have a measured reconstruction-loss curve on held-out agent-trajectory data; the absence of such a curve means we cannot rule out posterior collapse or under-training on the trajectory corpus. We do not yet have an interpolation-quality metric in the sense of "is the decoded interpolation sentence-grammatical and semantically intermediate between the endpoints?"; the closest the tests come is a coherence score returned by `_compute_coherence` in `src/cohezion/api/__init__.py`, which is a heuristic over the latent and is not validated against human judgement. We do not yet have a nearest-neighbour retrieval evaluation on a fixed set of held-out queries, although the `SemanticCache` test suite reports a 95% hit rate in its own narrow benchmark (cohezion CLAUDE.md, 2026-04-23). We do not yet have an end-to-end measurement of how the FLUME-backed cache changes the cost or latency of compound-loop execution relative to the hash baseline, although the architecture is designed to support such a comparison and the relevant instrumentation (`GlobalMetricsAggregator`) is in place.

API latency is constrained by the design of the dashboard mockup (`research/mockups/flume-latent-explorer.html`), which assumes that `/flume/latent-space` returns within a few hundred milliseconds for sample counts up to 200. Validation against this assumption on the target hardware is also pending.

The honest summary of evaluation as of 2026-04-23 is that the system is implemented, the test suite exercises its public interfaces, and the architecture is positioned to support a quantitative comparison against a hash-based or sentence-embedding-based baseline. The comparison itself is the explicit subject of the next study. We name this clearly rather than papering over it, and we note that this is a deliberate choice in the cohezion project's culture, which treats inflated metrics as more harmful than honest gaps (CLAUDE.md, "report honest metrics").

# 6. Discussion

The principal limitation of FLUME, in its present 256-dimensional configuration, is that the latent space may be too narrow to faithfully encode the full diversity of agent contexts that the compound loop accumulates over time. Trajectories produced by the executor mix code, natural language, tool outputs, and structured metadata, and a 256-dimensional bottleneck must compress all of these modalities through a single shared encoder. A larger latent would relax this pressure but at the cost of breaking the system-wide 256-dimensional thought-vector invariant, which is enforced by the `ThoughtVector` Pydantic validator and which other components (`SemanticCache`, the journey-tracker's manifold projection, the FLUME-VAE bridge) implicitly depend on. Resolving this tension probably requires a hierarchical FLUME, in which different levels operate at different latent widths and a learned projection mediates between them. We sketch this in Section 7 and treat it as out of scope for the present design.

A second limitation is that composition guarantees are empirical rather than formal. We can interpolate between two latents, but we have no theorem that the decoded interpolant is semantically meaningful. The literature on β-VAE (Higgins et al., 2017) and on disentangled representation learning more broadly (Locatello et al., 2019) suggests that disentanglement is sensitive to architecture, training data, and hyperparameters in ways that are difficult to control without inductive biases that the standard ELBO does not provide. For a pure interpolation use case the standard ELBO appears to be sufficient, in the sense that decoded interpolants are at least syntactically reasonable; for stronger claims about *compositional algebra* over the latent (e.g., that subtracting one skill from another yields a meaningful "skill difference"), additional work is warranted.

Third, the relationship between FLUME and the cohezion JEPA world model deserves clarification. JEPA (`src/cohezion/world_model/jepa_world_model.py`, described in cohezion CLAUDE.md) is a predictive, action-conditioned model that learns to project current observation latents forward in time. FLUME is a static autoencoder over agent context. They are complementary, not redundant: JEPA predicts where the agent's state will go next, FLUME compresses where it has been. In the cohezion 12-dimensional universe model (CLAUDE.md), JEPA's surprise signal feeds the journey-tracker, which records 12-dimensional positions; FLUME encodes those same trajectories into a 256-dimensional latent for retrieval. A natural future direction is to share the encoder weights between the two models, treating FLUME as the encoder and JEPA as the predictor over a shared latent. This would preserve the read-side of the compound loop while making the predictive component cheaper and architecturally more uniform.

A fourth question worth raising explicitly is the choice of a VAE rather than a transformer encoder over the same input. Transformer encoders (BERT-style) produce embeddings of comparable dimension and are more accurate at retrieval-by-similarity. The reason FLUME is a VAE rather than a transformer encoder is precisely the composition use case: a transformer encoder produces an embedding but not a *generative model* over the latent space, and so does not support principled interpolation, sampling, or latent algebra. The VAE's continuous, regularised latent is essential to the geometric operations the system needs. If we were only doing similarity retrieval, we would use a transformer encoder; we are doing more than retrieval, and so we pay the (currently empirical) cost of a slightly weaker similarity surface in exchange for the (currently essential) compositional structure.

Failure modes the design must contend with include posterior collapse, in which the decoder learns to ignore the latent entirely and the KL term drives the encoder to the prior; mode collapse, in which the latent population concentrates on a small region and loses discriminability; latent inactive units, in which a subset of the 256 dimensions never carry information and effectively reduce the working latent width; and prompt-injection attacks, in which adversarial input attempts to drive the encoder to a target latent (which the cohezion `prompt-injection-guard` skill is designed to mitigate at the input layer rather than inside FLUME itself). KL annealing (Bowman et al., 2016) and the β-VAE weighting (Higgins et al., 2017) are the standard defences against the first two; latent-unit utilisation can be measured directly and is an obvious diagnostic to add to the training metrics; the prompt-injection question is a system-design concern that must be addressed at the boundary between untrusted input and the encoder.

Finally, we observe that the present manuscript's positioning, as a system-design report rather than as an empirical study, is itself a feature of the compound-engineering culture rather than an accident. The cohezion project's documentation explicitly prefers honest gaps over inflated numbers, and treats unmeasured claims as worse than acknowledged absence. The follow-up study will report measured benchmarks, on the same architecture and the same hardware, and will be evaluated against the predictions implicit in this manuscript: that a 256-dimensional VAE latent suffices for the agent-memory use case, that linear interpolation is a useful first composition operation, and that the architecture supports a meaningful improvement in cache hit rate and end-to-end latency over the hash baseline.

# 7. Future Work

Several extensions follow naturally from the design described above. A hierarchical FLUME, in which separate VAEs are trained at the skill, task, and conversation-turn levels, with learned projections mediating between them, would address the latent-width tension noted in Section 6 without abandoning the 256-dimensional invariant at any single level. The system already maintains structured metadata distinguishing these levels (the `ExperienceCollector` and `TrajectoryCapture` components in `src/cohezion/flume/`), so the necessary input granularity is available; the architectural change is to add intermediate encoders rather than to retrain a wider monolithic model.

Online learning is a second natural extension. The current training workflow is batched: a corpus is collected, the model is trained for a fixed number of epochs, the checkpoint is saved, and inference proceeds against the frozen weights. The compound-engineering loop, however, generates new trajectory data continuously, and the latent space ought to evolve with that data rather than being periodically re-fit. A streaming VAE training procedure, with replay buffers to mitigate catastrophic forgetting and a stability-monitoring component to detect distribution shift, would let the latent track the system's actual distribution of work. The cohezion `DegradationDetector` and `MetricsCollector` infrastructure could be reused to drive the stability-monitoring piece.

Cross-domain transfer is a third extension. The FLUME encoder is currently trained on agentic trajectory data drawn from the cohezion executor itself; this means that the latent geometry is well-suited to the kinds of tasks the cohezion system has historically performed, but is not necessarily transferable to tasks outside that distribution. A pretraining-and-adaptation approach, in which the encoder is first trained on a broad corpus of natural language and code and then fine-tuned to the agentic distribution, would likely yield a more general latent at the cost of training expense. Recent work on transformer sequence VAEs (Li et al., 2020; Liu et al., 2022) provides direct precedent for this approach.

A fourth area is adversarial robustness. The compound loop's reliance on the latent geometry makes it a target for prompt-injection attacks: an adversary who can drive the encoder to a chosen latent can manipulate downstream retrieval and execution. The cohezion `prompt-injection-guard` skill addresses the input-validation side of this concern, but the encoder itself could be hardened with adversarial training, certified-robustness techniques, or input filtering specific to the agentic distribution. The design of such defences interacts in non-trivial ways with the desired composition properties of the latent (a perfectly robust encoder may be a less useful one), and warrants its own study.

Finally, the relationship to JEPA noted in Section 6 deserves explicit experimental work. Sharing encoder weights between the two models would unify the read and predictive sides of the compound loop and reduce the system's parameter count, but requires a careful joint training procedure to avoid the predictor's loss interfering with the autoencoder's reconstruction objective. Whether such joint training is stable is an empirical question we have not yet answered.

# 8. Conclusion

We have described FLUME, a compositional latent-space architecture built into the cohezion compound-engineering platform as the addressable surface for agent memory. The design uses a transformer-encoder variational autoencoder mapping tokenised agent context to a 256-dimensional latent, a transformer decoder reconstructing token sequences under the standard ELBO objective, and six HTTP endpoints connecting the model to the surrounding executor, retrospection, and skill-refinement loop. The contribution is the design rationale and the integration story rather than a new VAE technique. We argue that variational autoencoders, reframed as a substrate for *composition* rather than as standalone generative models, are well suited to the agentic setting, where the principal need is geometric structure over prior context. We have honestly reported the implementation's status as of 2026-04-23 (cohezion repository, manderson240/cohezion), the in-tree test coverage that exists, and the quantitative measurements that do not yet exist and are deferred to a follow-up study. We expect the follow-up to report measured cache hit rates, interpolation quality, and end-to-end latency improvements on the AMD Strix Halo target hardware; we explicitly do not pre-commit to particular numerical ranges for those measurements.

# Appendix A: API Specification

The six FLUME HTTP endpoints, as defined in `src/cohezion/api/routes/flume_inline.py` (worktree synthetic-sniffing-panda, 2026-04-23), are summarised below.

- `POST /flume/train` — request body `{epochs, batch_size, lr, z_dim, kl_weight, coherence_weight, n_samples}`; response `{epochs_completed, final_mse, final_kl, final_total, checkpoint_path}`. Triggers training on a synthetic dataset.
- `GET /flume/status` — no request body; response `{trained, checkpoint_path, last_metrics}`. Reports the latest checkpoint and the most recent metrics file under `data/flume/checkpoints/`.
- `POST /flume/encode` — request body `{vector: list[float] of length z_dim}`; response `{mu, log_var, coherence}`. Returns the encoder's mean and log-variance for the input.
- `POST /flume/decode` — request body `{latent: list[float] of length z_dim}`; response `{reconstruction, coherence}`. Decodes a latent vector back to an output-space reconstruction.
- `POST /flume/interpolate` — request body `{vector_a, vector_b, ratio in [0, 1]}`; response `{result, coherence, mu_a, mu_b}`. Encodes both endpoints, linearly interpolates in latent space at the given ratio, and decodes the result.
- `POST /flume/latent-space` — request body `{n_samples ≤ 1000, seed}`; response `{latent_dim, samples, samples_3d, variance_explained, coherence_scores}`. Samples the latent prior and returns PCA-reduced 3D coordinates suitable for visualisation.

All endpoints validate the dimension of vector inputs against the model's configured `z_dim` and return HTTP 422 on mismatch. The `latent-space` endpoint additionally enforces the 1 000-sample cap and returns a sanitised HTTP 500 if the underlying VAE checkpoint is not loadable.

# Appendix B: Encoder Implementation

The core encoder method, reproduced verbatim from `src/cohezion/flume/vae.py` (cohezion repository, snapshot 2026-04-23), is:

```python
def encode(
    self, input_ids: torch.Tensor, attention_mask: torch.Tensor | None = None
) -> tuple[torch.Tensor, torch.Tensor]:
    """Encode tokens to mu and log_var."""
    _batch_size, seq_len = input_ids.shape
    positions = torch.arange(seq_len, device=input_ids.device).unsqueeze(0)
    x = self.embedding(input_ids) + self.pos_embedding(positions)

    src_key_padding_mask = ~attention_mask.bool() if attention_mask is not None else None
    x = self.transformer_encoder(x, src_key_padding_mask=src_key_padding_mask)

    # Global average pooling (mean over sequence)
    if attention_mask is not None:
        mask = attention_mask.unsqueeze(-1).float()
        x = (x * mask).sum(dim=1) / mask.sum(dim=1).clamp(min=1)
    else:
        x = x.mean(dim=1)

    mu = self.mu_head(x)
    log_var = self.logvar_head(x)
    return mu, log_var
```

The decoder follows the symmetric shape: a linear projection from the 256-dimensional latent to the 256-dimensional embedding space, a two-layer causal transformer decoder consuming the projected latent as memory and the target token sequence as queries, and a final linear head producing logits over the configured vocabulary. The forward pass composes encode, reparameterise, and decode in the standard order, and `compute_loss` returns the reconstruction loss, the KL divergence, and a weighted sum as the total objective.

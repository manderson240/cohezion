# Experience → VAE Training Pipeline

## Context

Cohezion's FLUME VAE trains on **synthetic gaussian noise** (0.5 ± 0.15) because no real data pipeline exists. Meanwhile, the compound executor captures rich execution experiences (12D trajectories, coherence, anomaly scores, alignment metrics) and persists them to Parquet, SurrealDB, and vault JSON — but none of this feeds back into the VAE.

This pipeline closes the loop: collect real agentic experiences, encode them as 256D vectors, and train the VAE on actual behavior distributions. The trained VAE can then generate novel plausible experiences for universe simulation.

## 256D Encoding Scheme

```
Dims [0:12]   — 12D axiomatic trajectory (from JourneyTracker)
                0:novelty 1:logic 2:field 3:spatial 4:temporal
                5:precipitation 6:coherence 7:efficiency 8:convergence
                9:smoothness 10:resonance 11:harmony

Dims [12:24]  — 12 scalar execution metrics (from CompoundExecutor)
                12:phi_score 13:anomaly_score 14:misalignment_score
                15:intent_confidence 16:duration_norm(log) 17:tokens_norm(log)
                18:cache_hit_rate 19:success(0|1) 20:token_efficiency_norm
                21:quality_score 22:convergence_trend 23:cost_norm

Dims [24:29]  — 5 operation type one-hot
                24:generate 25:analyze 26:search 27:transform 28:persist

Dims [29:256] — 227 semantic fingerprint (deterministic SHA-256 hash expansion)
```

## Key Design Decisions

1. **256D not 12D VAE**: Encode full experience context (trajectory + metrics + semantics), not just spatial position. Preserves compatibility with existing 256D VAE architecture.

2. **Deterministic fingerprints**: Use SHA-256 hash expansion (like JourneyTracker does), not Python `hash()` which varies across sessions.

3. **Actual FlumeVAETrainer API**: Use `TrainConfig(z_dim=256, ...)` + `FlumeVAETrainer(config).train(dataset=custom_ds)` — the existing hook.

4. **Parquet schema**: Handle actual schema where trajectories are in `state_trajectory` field as nested float lists.

5. **Non-blocking SurrealDB**: try/except around all SurrealDB calls; skip tier if DB unavailable.

### Level 1: CompoundExecutor (`src/cohezion/compound/executor.py`)
- **Entry point** for all individual task execution
- **11-step execution pipeline** including:
  1. Vault experience guidance lookup
  2. Request alignment analysis
  3. Degradation checking
  4. Journey state recording
  5. Skill selection
  6. Model routing
  7. Guardrail execution
  8. Anomaly detection
  9. Vault logging
  10. Metrics collection
  11. Skill refinement
- Returns `ExecutionResult` with detailed token metrics

### Level 2: TeamExecutor (`src/cohezion/compound/team_executor.py`)
- Orchestrates **multiple CompoundExecutors** working together
- Manages **task dependencies** via topological sorting
- Parallel execution with **configurable degree** (default 4)
- Computes **compound scoring**: 60% success rate + 25% coherence + 15% efficiency
- Result type: `TeamExecutionResult` with per-agent metrics

### Level 3: TeamOrchestrator (`src/cohezion/swarm/team_orchestrator.py`)
- **Generates team plans from PRIME skills**
- Converts skills into `AgentSpec` + `TaskSpec` + dependency graph
- Integrates capability registry and template engine
- **Task→Model mapping** (verified in code):
  - "verify", "test", "lint" → phi3:mini
  - "code", "implement", "refactor" → qwen3-coder:30b
  - "reason", "architect", "plan", "research" → deepseek-r1:70b
- Generates **3-phase plans**: research → implementation → testing

### Level 4: ExecutionOrchestrator (`src/cohezion/swarm/execution_orchestrator.py`)
- Executes TeamOrchestrator plans with **wave-based parallelism**
- Topological sort transforms dependency graph into independent execution waves
- Each wave runs tasks in parallel (respecting semaphore)
- Returns `ExecutionReport` with aggregated metrics

## 4. MODEL LOADING AND LIFECYCLE

### No Explicit Load/Unload
Cohezion **delegates entirely to Ollama's native model management**:
- Models are **implicitly loaded** on first API call
- **Cached in Ollama memory** with ~5min TTL
- **Automatic LRU eviction** when memory pressure exceeds threshold
- **No explicit `model.unload()`** API — relies on Ollama internals

### Model Swap Overhead
- Small ↔ Large: 2-3 seconds per transition
- Same size class: <100ms (already cached)
- **Bottleneck during multi-agent execution** when agents need different models

### Semantic Cache (L1/L2/L3)
- **L1 SHA-256**: Exact hash match, 5-10ms, 95%+ hit on repeats
- **L2 Cosine**: Similarity threshold 0.95, 15-20ms
- **L3 Vault**: Pattern-based learning, 100-500ms (async)

## 11. CRITICAL BOTTLENECKS IDENTIFIED

### 1. Model Loading During Multi-Agent Execution
- **Problem**: Sequential 2-3 second loads when agents need different models
- **Example**: 84GB qwen3 → 51GB qwen2 → 5GB phi3 = 8-12 second overhead per wave
- **Mitigation**: Memory bandwidth analyzer prevents >0.8 pressure
- **Opportunity**: Pre-load models during planning phase

### 2. Semaphore Limit at 4 Concurrent
- **Problem**: Hard cap prevents >4 simultaneous Ollama calls
- **Impact**: 5 analyst perspectives need queuing
- **Workaround**: Phase sequential + parallel (wave-based execution)

### 3. Vault Search Latency
- **Problem**: Full-text search first query = 100-500ms
- **Mitigation**: Hierarchical search in SurrealDB (5-10× faster)
- **Cached**: Subsequent queries 10-50ms

### 4. No Explicit Model Unload Strategy
- **Problem**: Models stay in memory until Ollama LRU evicts (5min TTL)
- **Risk**: Memory fragmentation during long-running swarms
- **Future**: Implement explicit unload for models below threshold

# Optimal Multi-Agent Local LLM Orchestration via Ollama on Strix Halo

## 1. Ollama Model Loading/Unloading Behavior

### Memory Management Model

Ollama keeps loaded models fully resident in RAM (CPU inference) or VRAM (GPU inference). When a new model request arrives and insufficient memory is available, Ollama queues the request and unloads idle models in FIFO order to make room.

**Key parameters:**

| Parameter | Default | Description |
|-----------|---------|-------------|
| `OLLAMA_KEEP_ALIVE` | `5m` | Duration models stay loaded after last use |
| `OLLAMA_MAX_LOADED_MODELS` | `3` (CPU mode) | Max concurrent models in memory |
| `OLLAMA_NUM_PARALLEL` | `1` or `4` (auto) | Parallel requests per model |
| `OLLAMA_MAX_QUEUE` | `512` | Max queued requests before 503 errors |
| `OLLAMA_KV_CACHE_TYPE` | `f16` | KV cache precision (`q8_0`, `q4_0` available) |
| `OLLAMA_FLASH_ATTENTION` | `0` | Required for KV cache quantization |

**Per-request override:** The `keep_alive` parameter in `/api/generate` and `/api/chat` overrides the global `OLLAMA_KEEP_ALIVE`. Set to `-1` to keep loaded indefinitely, `0` to unload immediately after response.

**Cold-start penalty (NVMe):**
- ~9 GB model (e.g., deepcoder:14b): **24-30 seconds** to load from NVMe
- ~19 GB model (e.g., glm-4.7-flash): **~45-60 seconds** estimated (scales roughly linearly with size)
- ~24 GB model (e.g., nemotron-3-nano): **~60-75 seconds** estimated

**Model preloading/warming:** Send an empty prompt to the generate endpoint to preload without generating:
```bash
curl http://localhost:11434/api/generate -d '{"model": "glm-4.7-flash", "keep_alive": -1}'
```

This loads the model into RAM and keeps it resident indefinitely. The response returns immediately once loading completes.

**New model scheduling (Ollama v0.12+):** As of September 2025, Ollama uses exact memory allocation instead of estimates, reducing OOM crashes by up to 70%. The scheduler loops through Fit and Alloc operations, progressively learning memory requirements until a stable layout is found.

## 2. Optimal Concurrent Model Combinations

### Memory Budget Calculation

Total system RAM: **128 GiB**
OS + system overhead: **~4-6 GiB**
Available for models: **~122-124 GiB**

**Formula:** `Total per model = model_weights + KV_cache + overhead (~0.5-1 GB)`

KV cache (FP16 default): Scales linearly with context length. For reference:
- 8B model at 32K context: ~4.5 GB KV cache
- 14B model at 8K context: ~2 GB KV cache
- 30B MoE model at 8K context: ~2-3 GB KV cache (based on active params for KV)

**With KV cache quantization (Q8_0):** Halves KV cache memory. **Q4_0:** Cuts to 1/4. Requires `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0`.

## 3. MoE vs Dense Inference Characteristics

### Critical finding: MoE models load ALL parameters into RAM

Even though a MoE model like glm-4.7-flash (30B total, 3B active) only activates 3B parameters per token, **all 30B parameters must be resident in RAM**. The router selects which experts to activate at inference time, but the selection requires all expert weights to be addressable.

This means:
- **Memory footprint:** Same as a dense model of equivalent total parameter count. A 30B MoE model uses the same RAM as a 30B dense model.
- **Compute cost per token:** Proportional to **active** parameters only (3B), not total (30B).
- **The advantage:** Much faster inference than a dense 30B model, because only 3B parameters participate in matrix multiplications per token.

### CPU Inference Speed Comparison (Strix Halo benchmarks)

| Model | Type | Size | Generation Speed | Prompt Processing |
|-------|------|------|----------------:|------------------:|
| phi4-mini-reasoning | Dense 3.8B | ~2.4 GB | ~60-80 t/s | ~300+ t/s |
| deepcoder:14b | Dense 14B | 9 GB | ~15-20 t/s | ~200+ t/s |
| gpt-oss:20b | MoE 21B/3.6B | 13 GB | ~24-47 t/s | ~1,900 t/s |
| glm-4.7-flash | MoE 30B/3B | 19 GB | ~20-35 t/s (est.) | ~1,000+ t/s (est.) |
| qwen3-coder:30b | MoE 30B/3B | 18 GB | ~20-35 t/s (est.) | ~1,000+ t/s (est.) |
| nemotron-3-nano | MoE 31.6B/3.2B | 24 GB | ~15-25 t/s (est.) | ~800+ t/s (est.) |

Key observations:
1. **MoE prompt processing is exceptionally fast** on CPU (gpt-oss:20b achieves ~1,940 t/s prompt eval) because the router + active expert computation is lightweight relative to the full parameter count.
2. **MoE generation speed** is comparable to a dense model of the active parameter size (3-4B), not the total size. This makes MoE models excellent for CPU inference.
3. **Dense 14B** (deepcoder) is slower for generation than MoE 30B models because it activates all 14B parameters per token, versus ~3B for MoE.

### Memory bandwidth bottleneck

On the Strix Halo, CPU memory bandwidth is ~84 GB/s (CPU to unified memory). For generation (which is memory-bandwidth bound), the theoretical maximum for a model that needs to read `W` GB of weights per token is `84 / W` tokens/second for the memory-read portion alone. For a dense 14B model (~9 GB weights in Q4), that is ~9 t/s minimum read overhead. MoE models only read the active expert weights (~1-2 GB effective), giving much better bandwidth utilization.

## 4. Ollama API Features for Orchestration

### Batch Requests

**No native batch endpoint.** Ollama processes requests individually via `/api/generate` and `/api/chat`. However, you can achieve batching through:
- `OLLAMA_NUM_PARALLEL=N`: Allows N concurrent requests to the same model (shares KV cache memory, multiplied by N)
- Concurrent HTTP requests: Send multiple requests in parallel; Ollama queues them internally (up to `OLLAMA_MAX_QUEUE=512`)

### Priority Queuing

**No built-in priority queue.** All requests are processed FIFO. You must implement priority routing at the orchestration layer (which Cohezion's `dynamic_model_router.py` already does with `IDEPriority`).

### Model Preloading/Warming

**Yes.** Send an empty prompt to load the model:
```python
import httpx
# Preload model (non-blocking once loaded)
httpx.post("http://localhost:11434/api/generate", json={
    "model": "glm-4.7-flash",
    "keep_alive": -1  # Keep loaded indefinitely
})
```

### Structured Output / JSON Mode

**Yes.** Use the `format` parameter:
```python
# JSON schema enforcement
response = httpx.post("http://localhost:11434/api/chat", json={
    "model": "qwen3-coder:30b",
    "messages": [{"role": "user", "content": "List 3 colors"}],
    "format": {
        "type": "object",
        "properties": {
            "colors": {"type": "array", "items": {"type": "string"}}
        },
        "required": ["colors"]
    }
})
```

Simple JSON mode: `"format": "json"` in the request body.

### Function Calling / Tool Use

**Yes.** Supported via the `tools` parameter in `/api/chat`:
```python
response = httpx.post("http://localhost:11434/api/chat", json={
    "model": "qwen3-coder:30b",
    "messages": [{"role": "user", "content": "What's the weather in Paris?"}],
    "tools": [{
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get weather for a location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {"type": "string", "description": "City name"}
                },
                "required": ["location"]
            }
        }
    }]
})
```

Models that support tools are tagged with a "tools" badge on the Ollama registry. The parser uses structural understanding (not just JSON extraction) for reliable tool call detection. **Streaming tool calls are also supported.**

### Keep-Alive Control Per Request

**Yes.** Every `/api/generate` and `/api/chat` request accepts `keep_alive`:
```python
# Keep loaded for 1 hour after this request
{"model": "glm-4.7-flash", "prompt": "...", "keep_alive": "1h"}

# Unload immediately after response
{"model": "phi4-mini-reasoning", "prompt": "...", "keep_alive": 0}
```

## 5. Best Practices for Multi-Agent Local Orchestration

### Agent-to-Model Assignment Strategy

Based on research and your available models, the optimal assignment pattern is a **tiered specialization** approach:

| Agent Role | Primary Model | Fallback Model | Rationale |
|-----------|---------------|----------------|-----------|
| **Router/Classifier** | phi4-mini-reasoning (3.8B) | - | Ultra-fast classification, ~60-80 t/s, always loaded |
| **Reasoning/Planning** | glm-4.7-flash (30B MoE) | gpt-oss:20b | Strong reasoning, MoE efficiency |
| **Coding** | qwen3-coder:30b (30B MoE) | deepcoder:14b | Specialized for code, MoE speed |
| **General/Synthesis** | gpt-oss:20b (21B MoE) | phi4-mini-reasoning | Versatile, good throughput |
| **Long-context Analysis** | nemotron-3-nano (1M ctx) | glm-4.7-flash-256k | Load on-demand only |
| **Embeddings** | nomic-embed-text (274M) | snowflake-arctic-embed2 | Always loaded, minimal RAM |

### Hot/Cold Model Rotation Pattern

```
TIER 1 - ALWAYS HOT (permanently loaded, keep_alive=-1):
  - phi4-mini-reasoning  (~4 GB)  -- router, fast decisions
  - nomic-embed-text     (~0.5 GB) -- embeddings, always needed
  Total: ~4.5 GB

TIER 2 - WARM (loaded on first use, keep_alive=30m):
  - glm-4.7-flash        (~22 GB) -- reasoning tasks
  - qwen3-coder:30b      (~21 GB) -- coding tasks
  Total: ~43 GB (with Tier 1: ~48 GB)

TIER 3 - COLD (loaded on-demand, keep_alive=5m):
  - gpt-oss:20b          (~16 GB) -- general overflow
  - deepcoder:14b        (~12 GB) -- coding fallback
  - nemotron-3-nano      (~27 GB) -- long-context only
  Total: loaded one at a time as needed
```

**Orchestration logic:**
1. All requests hit the router (phi4-mini-reasoning) first for classification
2. Router dispatches to warm Tier 2 model based on task type
3. If Tier 2 model is overloaded (queue depth > threshold), escalate to Tier 3 fallback
4. Monitor memory pressure; if >75%, force-unload Tier 3 models (`keep_alive: 0`)

### Context Window Management Across Agents

- **Default context:** 4K-8K tokens per agent request (minimizes KV cache pressure)
- **Extended context:** Only for nemotron-3-nano when document analysis requires it
- **Cross-agent context:** Use a shared context store (e.g., Cohezion's `SemanticCache`) rather than passing full context between agents
- **KV cache optimization:** Set `OLLAMA_KV_CACHE_TYPE=q8_0` globally. This halves KV memory with negligible quality loss.

With Q8_0 KV cache at 8K context:
- 3B active MoE model: ~0.5 GB KV (vs 1 GB FP16)
- 14B dense model: ~1 GB KV (vs 2 GB FP16)

### Token Throughput Optimization

1. **Use `OLLAMA_NUM_PARALLEL=2`** for the warm tier models. This doubles throughput at the cost of 2x KV cache memory per model (still affordable with Q8_0).
2. **Batch similar requests** to the same model rather than alternating between models, to avoid context switching.
3. **Streaming responses** reduce perceived latency for interactive use cases.
4. **Set `num_ctx` explicitly** in requests to avoid allocating unnecessarily large context windows:
```python
{"model": "qwen3-coder:30b", "prompt": "...", "options": {"num_ctx": 4096}}
```

### Recommended Startup Sequence

```bash
# 1. Configure environment
export OLLAMA_MAX_LOADED_MODELS=4
export OLLAMA_NUM_PARALLEL=2
export OLLAMA_KEEP_ALIVE="30m"
export OLLAMA_FLASH_ATTENTION=1
export OLLAMA_KV_CACHE_TYPE=q8_0

# 2. Start Ollama
systemctl restart ollama  # or: ollama serve

# 3. Preload Tier 1 (always hot)
curl -s http://localhost:11434/api/generate \
  -d '{"model": "phi4-mini-reasoning", "keep_alive": -1}' &
curl -s http://localhost:11434/api/generate \
  -d '{"model": "nomic-embed-text", "keep_alive": -1}' &

# 4. Preload Tier 2 (warm)
curl -s http://localhost:11434/api/generate \
  -d '{"model": "glm-4.7-flash", "keep_alive": -1}' &
curl -s http://localhost:11434/api/generate \
  -d '{"model": "qwen3-coder:30b", "keep_alive": -1}' &

wait
echo "All models loaded. Memory usage: $(free -h | grep Mem | awk '{print $3}')"
```

### Architecture Pattern: Model Pool Manager

The pattern that works best for multi-agent orchestration is a **Model Pool Manager** that sits between agents and Ollama:

```
Agent Layer:  [Router] [Reasoner] [Coder] [Analyst]
                  |         |         |        |
                  v         v         v        v
Pool Manager: ┌─────────────────────────────────────┐
              │  Request Queue (priority-aware)      │
              │  Model Affinity Map                  │
              │  Memory Pressure Monitor             │
              │  Load/Unload Controller              │
              └─────────────────────────────────────┘
                  |         |         |        |
                  v         v         v        v
Ollama:       [phi4]   [glm-4.7] [qwen3] [nomic]
```

This is essentially what Cohezion's `OllamaModelManager` (at `/home/mike-anderson/dev/cohezion/src/cohezion/swarm/model_manager.py`) and `DynamicModelRouter` (at `/home/mike-anderson/dev/cohezion/src/cohezion/swarm/dynamic_model_router.py`) already implement. The model manager tracks per-model per-task metrics (latency, quality, confidence) and the dynamic router enforces the global concurrency limit of 4 with memory-bandwidth-aware tier selection.

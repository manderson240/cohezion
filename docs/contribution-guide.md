# Contribution Guide (BMAD summary)

_Generated by BMAD `/bmad-document-project` on 2026-04-22. Canonical source is [`CONTRIBUTING.md`](../CONTRIBUTING.md) at the repo root — this is a structured summary with cross-references._

## Branch strategy

| Branch | Purpose |
|---|---|
| `main` | Stable releases only |
| `develop` | Active development |
| `feature/*` | New features |
| `fix/*` | Bug fixes |

Workflow: branch from `develop` → atomic commits → PR to `develop` → review → merge → periodic `develop` → `main` release.

## Pre-commit hooks

Run automatically on commit:

- **ruff** — lint + format Python
- **mypy** — type checking
- **trailing-whitespace** — remove trailing spaces
- **check-yaml / check-json** — validate config files
- **lfs-pointer-check** — block large binaries that aren't LFS-tracked

On push:
- **pytest** — full suite

Manual:

```bash
uv run pre-commit run --all-files            # all hooks
uv run pre-commit run ruff --all-files       # specific hook
```

> ⚠️ **Never** skip hooks with `--no-verify` unless the user has explicitly asked — the hooks exist to catch the anti-patterns in `CLAUDE.md` (e.g. LFS drift, schema violations, `entire/` branch bloat).

## Commit conventions

Conventional commits (`.claude/rules/git-operations.md`):

| Prefix | Use |
|---|---|
| `feat:` | New feature |
| `fix:` | Bug fix |
| `docs:` | Docs only |
| `refactor:` | Refactor without behavior change |
| `test:` | Tests only |
| `chore:` | Build/infra/tooling |

**Atomic commits, focused subjects**. Avoid squashing many changes — per `git-operations.md` Strategic Checkpointing, each commit captures full reasoning context via Entire.io; focused commits = better cross-session memory.

Surgical-commit discipline (L363 + L368): against high-churn trees, enumerate paths explicitly, never `git add .`, and verify `git diff --cached --name-only` matches your intent before committing.

## Code style

- **Python**: Ruff `target-version = py311`, **line-length 100** (repo override of the Ruff default, per `pyproject.toml`). Enabled rule sets: `E`, `F`, `W`, `I`, `N`, `UP`, `S`, `B`, `A`, `C4`, `SIM`, `TCH`, `RUF`.
- **Types**: mypy permissive; `disallow_untyped_defs = false` (start permissive, tighten later)
- **Docstrings**: required for public classes and methods
- **Naming**: descriptive intent-revealing names (e.g. `calculate_discount`, not `process`)

> ⚠️ The pre-BMAD `CONTRIBUTING.md` lists line length 88 (Ruff default). The **authoritative** line length is **100**, set in `pyproject.toml` `[tool.ruff]` (Retrospective Session 14, to accommodate f-strings + comprehensions).

## Adding a skill

1. Create `src/cohezion/skills/MY_SKILL_PRIME.md` (YAML frontmatter + markdown body)
2. Register:

    ```python
    from cohezion.registry.skill_registry import register_skill
    register_skill("MY_SKILL_PRIME", "Description", ["keywords"], "skills/MY_SKILL_PRIME.md")
    ```

3. Run `make skill-guard` to validate metadata + FLUME compatibility

235 skill definitions exist (215 PRIME) — see `src/cohezion/skills/`.

## Adding an MCP server

1. Copy `cloud-vault-mcp/` as a starting template (it has 40+ working tools)
2. Create `src/cohezion/mcp/my_server.py` with tools
3. Add to `src/cohezion/mcp/mcp_registry.json`
4. Ensure:
   - **Silent on stdout** during init (stdio MCP channel)
   - **Lazy config lookups** (don't run Bitwarden vault at module import)
   - **YAML frontmatter** on any `AGENTS.md`
5. Smoke test:

    ```python
    from cohezion.mcp.my_server import get_server
    server = get_server()
    ```

See `CLAUDE.md` "MCP stdio Server Rules" (L273–L275).

## Documentation requirements

- **CLAUDE.md** is the canonical AI working reference. Update it when adding major architecture.
- Vault-first: log session learnings to `~/vaults/cohezion-vault/`, not directly to `MEMORY.md` (which is auto-generated weekly).
- ADRs live in `docs/adr/` as YAML.
- Skills and agent definitions use YAML frontmatter `.md` (not JSON) for consistency with vault + `.context/`.

## Verification before completion

(from `~/.claude/rules/verification-before-completion.md`)

- Tests passing ≠ program working. **Run the actual program** after tests pass.
- Show concrete evidence ("Ran `python app.py` — output: …"), not assumptions ("Tests pass, should work").
- Fix all errors revealed by verification without asking — never "Should I fix these?"

## Pull requests

Target `develop`. Include:
- Short description + rationale
- Linked issue (if any)
- Screenshots / logs for UI or behavior changes
- Note on whether `make validate` + `make all` pass

`.github/workflows/claude-code-review.yml` runs an automated review; respond to findings before merge.

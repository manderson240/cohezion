# Popcorn CLI AMD Kernel Submission Workflow

## Submission Commands

```bash
CLI=~/.local/bin/popcorn-cli
KERNELS=/path/to/kernels/dir

# 1. Test (correctness check — do this first)
$CLI submit --no-tui --mode test --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 2. Benchmark (timing, no leaderboard impact)
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py

# 3. Leaderboard (official ranked submission)
$CLI submit --no-tui --mode leaderboard --gpu MI355X --leaderboard <name> $KERNELS/<kernel>/submission.py
```

## Leaderboard Name Pattern

Leaderboard names follow the pattern: `amd-<directory-name>`

| Kernel directory | Leaderboard name |
|-----------------|-----------------|
| `mxfp4-mm/`    | `amd-mxfp4-mm`  |
| `mixed-mla/`   | `amd-mixed-mla` |
| `moe-mxfp4/`   | `amd-moe-mxfp4` |

To discover unknown names: submit with `--mode test` using candidate names. A 404/does-not-exist
response means the name is wrong; acceptance (even with correctness failures) confirms the name.

## Submission Limits (Luma AMD Speedrun)

- **No per-user rate limit** — submit as many times as needed
- Server-wide: 3 concurrent submissions (asyncio.Semaphore)
- ~10 requests/second global rate limit
- Per-mode timeouts: test=180s, benchmark=180s (overridden per competition in task.yml)
- **Total workflow timeout: ~12 minutes** — the entire GitHub Actions run must complete within this
- Use `--mode test` first, then `--mode benchmark`, then `--mode leaderboard`

## aiter JIT Compilation Times (Luma AMD Speedrun)

aiter builds JIT modules on first use. These builds happen **inside** the 12-minute workflow timeout:

| JIT Module | Build Time |
|-----------|-----------|
| `module_moe_sorting` | ~25s |
| `module_moe_ck2stages_fp4x2_*` | ~103s |
| `module_mla_metadata` | ~32s |
| `module_mla_asm` | ~21s |
| `module_mla_reduce` | ~171s |

**Critical implications:**
- MoE JIT builds alone take ~230s (~4 min), leaving only ~8 min for actual execution
- MLA JIT builds take ~224s total — similar headroom concern
- When the server queue is backed up with multiple concurrent submissions, the JIT time can push the total over the 12-minute limit
- Submissions that appear to fail silently (no output, cancelled status) are often **queue pressure timeouts**, not code errors

**Mitigation:** Retry submissions during off-peak hours. JIT results are cached between runs in the same workflow, so a retry that hits a pre-warmed runner will be much faster.

## Local Testing Limitations on gfx1151 (RDNA4 Strix Halo)

Local GPU testing on gfx1151 (AMD Radeon 8060S, Strix Halo iGPU) is NOT feasible with ROCm 6.2.4:

- Without override: `HIP error: invalid device function` (ISA mismatch)
- With `HSA_OVERRIDE_GFX_VERSION=11.0.0`: "Memory access fault by GPU node-2" on kernel launch
  (RDNA4 gfx1151 is not binary-compatible with RDNA3 gfx1100)
- ROCm 6.3+ would be needed for gfx1151 native support

**Workaround**: All testing via Popcorn CLI remote submission (MI355X hardware).

## Competition Kernel Structure

Each kernel must implement:
```python
# submission.py
from task import input_t, output_t

def custom_kernel(data: input_t) -> output_t:
    ...  # Your implementation
```

The eval harness (`eval.py`) calls `generate_input()` from `reference.py`, passes `_clone_data(data)`
to `custom_kernel`, then runs `check_implementation()` comparing output to reference. Benchmark
runs clear L2 cache between runs (`clear_l2_cache_large()`), so cache warming tricks don't help.

**CRITICAL: Popcorn CLI only uploads `submission.py`.** It does NOT upload any other files
in the kernel directory. Files like `reference.py`, `task.py`, and `eval.py` are already
present on the runner at the competition's standard location — they are NOT re-uploaded.

**Consequence: Multi-file submissions are NOT possible.** If your submission.py tries to
`from gemm_wrapper import quant_and_gemm` where `gemm_wrapper.py` is a file you created
in the kernel directory, the runner will get `ModuleNotFoundError: No module named 'gemm_wrapper'`.

**Workaround attempted — dynamic module creation at `/tmp/`:**
```python
# submission.py
import importlib.util, textwrap, os, sys

code = textwrap.dedent("""...""")
path = "/tmp/my_module.py"
with open(path, "w") as f: f.write(code)
spec = importlib.util.spec_from_file_location("my_module", path)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
sys.modules["my_module"] = mod
```

This WORKS for making the module importable, BUT for AMD `gemm_a4w4_asm` specifically,
the dynamic module does NOT change callsite identity — the dispatch still produces wrong
results (see `amd-triton-jit-callsite-correctness` skill). Only `from reference import
ref_kernel` reliably bypasses the callsite sensitivity.

## Troubleshooting: Transient Artifact Download Failures

Popcorn CLI submissions run on GitHub Actions runners. The evaluation job and the artifact
download are separate steps — a network failure can cause the CLI to report failure even though
the evaluation job itself **succeeded**.

**Symptoms:**
- CLI output shows failure / no results despite a correct kernel
- Error mentions artifact download or GitHub Actions artifact retrieval

**Fix:** Simply retry the same submission command. A retry succeeds in the majority of cases.

```bash
# Retry exactly the same command — the eval job is idempotent
$CLI submit --no-tui --mode benchmark --gpu MI355X --leaderboard <name> <file>
```

**Important:** Transient failures look identical to actual correctness failures in the CLI output.
If a previously-passing kernel suddenly "fails", try a retry before debugging the kernel code.

# Competitive Kernel Optimization: Beyond Parameter Tuning

## Problem

After exhausting all tunable parameters in a library (e.g., aiter's `fused_moe`), ranking
stays in the lower half of the leaderboard. The reference implementation is already
well-optimized; parameter sweeps either have no effect, cause correctness failures, or
degrade performance.

## Context: When to Use This

- All accessible API parameters have been tested (documented in `aiter-kernel-parameter-semantics`)
- Still ranked outside top 20 with >2x gap to leader
- Considering whether to abandon vs. continue the challenge
- Wanting to plan next iteration with higher expected value

## The Decision Hierarchy

### Level 1: Local Proxy (Low effort, immediate)

Before expensive remote submissions, build a local model of the performance space:

**Parse aiter's tuned CSV configs:**
```bash
cat /path/to/aiter/aiter/configs/tuned_fmoe.csv
cat /path/to/aiter/aiter/configs/model_configs/dsv3_fp4_tuned_fmoe.csv
```

These CSVs contain: `(n_experts, batch_size, d_hidden, d_expert, topk, block_m, ...)` → `(kernel_name, cycles)`.
Reading them reveals:
- Which tile configs the auto-tuner selects for which shapes
- Whether there are shape-specific configs that differ from the defaults
- Whether your benchmark shapes have dedicated tuned entries or fall back to defaults

**Roofline model estimate:**
```python
# For MXFP4 GEMM: theoretical peak = GPU_TFLOPS * efficiency
# Compare against actual timing to determine if compute-bound or memory-bound
bytes_per_token = d_hidden * sizeof(fp4)  # input
bytes_weights = d_expert * d_hidden * sizeof(fp4)  # per expert, per token
arithmetic_intensity = 2 * d_hidden * d_expert / bytes_weights  # FLOPs/byte
```

### Level 2: The "Two Builders" Pattern (Medium effort)

From the Anthropic VLIW take-home challenge (see `research/challenges/anthropic_challenge/`):

The winning approach used two separate kernel builders:
- **Builder A (Correctness Anchor):** Delegates to `ref_kernel` or matches reference exactly.
  Never changes. Used to verify correctness of Builder B.
- **Builder B (Custom Explorer):** Reimplements the same computation differently.
  Can be tested against Builder A as ground truth.

For AMD MoE, this means writing a **custom dispatch + GEMM pipeline** that:
1. Uses the same shuffled weights and scales (pre-computed by aiter)
2. Implements its own token sorting (potentially simpler than aiter's)
3. Calls CK GEMM kernels directly instead of through `fused_moe`

```python
# Template: Two Builders pattern for AMD kernel submission
from reference import ref_kernel  # Builder A: correctness anchor

def custom_kernel(data: input_t) -> output_t:
    # Try Builder B; fall back to Builder A on any exception
    try:
        return custom_builder(data)
    except Exception:
        return ref_kernel(data)  # Safety net during development
```

### Level 3: Custom HIP/ASM Kernel (High effort, highest impact)

What top leaderboard entries do:
- Write kernel in HIP C++ or assembly, compiled with `hipcc`
- Bypass the aiter library entirely for the hot path
- Use hardware-specific optimizations (e.g., MI355X matrix core layouts, gfx950 ISA)
- Typically requires familiarity with ROCm programming model

This is only worth pursuing if:
- You have HIP/CUDA experience
- The competition has days remaining (not hours)
- The performance gap justifies the implementation risk

## VLIW Cross-Pollination: Applicable Lessons

The Anthropic VLIW take-home (`research/challenges/anthropic_challenge/`) shares structural
parallels with AMD GPU kernel challenges:

| VLIW Concept | AMD Kernel Analog |
|---|---|
| Instruction slots (alu, valu, load) | GPU execution units (VALU, SALU, memory) |
| `VLIWPacker` data-dependency tracking | aiter's 2-stage pipeline dependency between gate+up GEMM and down GEMM |
| "Temporal Instruction Leakage" across barriers | `doweight_stage1=True` leaking weight mul across the SiLU activation barrier |
| N_VEC=28 window interleaving for latency hiding | `num_kv_splits` in MLA for hiding KV cache memory latency |
| `multiply_add` fusion optimization | CK `moe_ck2stages_gemm1_*MulABScaleShuffled*` kernel name encodes similar fusion |
| Local simulator (instant feedback) | Popcorn CLI remote (~2-10 min/iteration) |

**Key VLIW insight transferable to AMD:**
The VLIW challenge was NOT won by parameter tuning the packer. It was won by:
1. Understanding how the scheduler works internally (`last_write`, `last_read` tracking)
2. Discovering that barriers needed explicit data-dependency injection
3. Building a custom kernel generator that produced different instruction schedules

Equivalent for AMD: understand how aiter selects kernels (`get_2stage_cfgs()` in `fused_moe.py`),
what the tile configs mean, and build something that uses them differently.

## Phase 4: GEMM Correctness Breakthrough (March 2026)

**Root cause was NOT "JIT callsite sensitivity" — it was an UNPATCHED QUANTIZATION BUG.**

`get_triton_quant(QuantType.per_1x32)` dispatches to the unpatched `fp4_utils.py` kernel
(ROCm/aiter issue #974). The fix is `dynamic_mxfp4_quant` from `aiter.ops.triton.quant`
(PR #975 patched this path). See `amd-triton-jit-callsite-correctness` v1.4.0 for details.

| Kernel | Approach | Outcome | Key Insight |
|--------|----------|---------|-------------|
| GEMM | `dynamic_mxfp4_quant` + `gemm_a4w4` | ✅ 0.0 error, ~24.1 µs | Patched Triton quant bypasses buggy dispatch |
| GEMM | `gemm_a4w4` with `log2_k_split=N` | ❌ RuntimeError | Torch op schema is fixed — no `log2_k_split` kwarg |
| GEMM | `gemm_a4w4_asm` direct call | ❌ Kernel name not found | Only 2 pre-compiled `.co` files; name selection is internal |
| GEMM | CUDA/HIP graph replay | ❌ ~36 µs (+50% overhead) | `copy_()` for 3 static input tensors exceeds kernel time |

**GEMM performance ceiling:** ~24.1 µs vs leader's 9.7 µs (2.49x gap).
The bottleneck is quantization time (~10-13 µs per call), which equals the GEMM time itself.
To close the gap requires a **fused quant+GEMM kernel** — not achievable via public aiter API.

**Key lesson:** When 2+ independent approaches all fail with similar-magnitude errors, suspect
the shared downstream component (here: the quantization output being wrong), not the
infrastructure connecting them (here: wrongly blamed callsite dispatch mechanism).

## Phase 5: MLA Pipeline Bypass (March 2026)

**Key insight: aiter's 3-stage MLA pipeline has fixed overhead that dominates for small batches.**

aiter's `mla_decode_fwd` runs: metadata computation → split-K ASM kernel → parallel reduce.
This pipeline is optimized for large workloads but has ~100-150 µs of constant overhead
regardless of batch size. For small batches (bs=4), the actual compute is tiny — the
overhead is the bottleneck.

**Approach:** Bypass the pipeline entirely with `torch.einsum` for small decode workloads:

```python
# Torch-native: Q@K^T + softmax + @V, all bf16
kv = kv_data["bf16"].view(bs, kvseqlen, 576)
scores = torch.einsum("bnh,bsh->bns", q, kv) * SM_SCALE
weights = torch.softmax(scores, dim=-1)
out = torch.einsum("bns,bsd->bnd", weights, v)
```

**Hybrid routing strategy (optimal):**
- `bs * kvseqlen <= 400_000` tokens: torch-native (pipeline overhead > compute)
- `bs * kvseqlen > 400_000` tokens: ref_kernel/aiter fp8 ASM (bandwidth-bound, fp8 wins)

**Results (all qseqlen=1, fp8 reference tolerance rtol=2e-2, atol=8e-3):**

| Shape | Previous (aiter fp8) | Hybrid | Factor |
|-------|---------------------|--------|--------|
| bs=4, kv=1k | ~150 µs | **27.7 µs** | 5.4x |
| bs=4, kv=8k | ~169 µs | **40.5 µs** | 4.2x |
| bs=32, kv=1k | ~179 µs | **46.2 µs** | 3.9x |
| bs=32, kv=8k | ~206 µs | **171 µs** | 1.2x |
| bs=64, kv=1k | ~175 µs | **64.7 µs** | 2.7x |
| bs=64, kv=8k | ~241 µs | **245 µs** | ~tie |
| bs=256, kv=1k | ~196 µs | **178 µs** | 1.1x |
| bs=256, kv=8k | ~397 µs | **399 µs** | ~tie |
| **Geomean** | ~199 µs | **~100 µs** | **2x** |

**Key learnings:**
- `fav3_sage_mxfp4` (Triton SAGE Attention) can't be used for MLA — requires separate K/V
  with same head_dim; MLA's fused buffer (K=576, V=512) is fundamentally incompatible.
- Correctness with bf16 KV vs fp8 reference: max error 5e-05 (tolerance: 8e-03) — excellent.

## Phase 9: Team-Parallel Custom Kernels — Both Regressed (March 2026)

Three-agent team (Lead + mla-dev + gemm-dev) worked in parallel. Both kernels regressed.
Do not retry these paths.

| Kernel | Approach | Geomean | vs. Existing | Root Cause |
|--------|----------|---------|--------------|------------|

### GEMM: The silent graph failure trap

`try/except: pass` around `torch.cuda.graph()` is an optimization anti-pattern:
- If capture fails (e.g., Triton JIT inside context), exception is swallowed silently
- `_graph_cache` never populates; every call runs non-graphed Triton
- Non-graphed `gemm_afp4wfp4` is slower than `gemm_a4w4` at all shapes
- The submission shows regression with no indication of why

**Rule:** Always use `gemm_a4w4` (ASM). Never switch to `gemm_afp4wfp4` for graph acceleration.

### MLA: The ~130 µs Triton dispatch floor

The ~130 µs overhead is NOT unique to aiter's 3-stage MLA pipeline. It applies to ANY
Triton kernel dispatched from Python on this problem:
- aiter `mla_decode_fwd` (3-stage): ~130 µs
- Custom Triton FlashDecoding (fp8, BLOCK_N=32): ~130 µs
- torch.einsum (vendor hipBLAS GEMV): **27–46 µs** ← the only way to escape the floor

The overhead is Python-level dispatch + Triton JIT, not the attention algorithm.
Escape requires a single CK/ASM kernel with no Python dispatch overhead.

## Phase 10: Metadata Caching + Graph Capture Definitively Benchmarked (March 2026)

Three independent paths explored. One improved (MLA caching), two confirmed regressions.

### GEMM: ASM Graph Capture Succeeds but Still Regresses

Phase 9 showed gemm_afp4wfp4 (Triton JIT) silently fails graph capture.
Phase 10 confirmed gemm_a4w4 (ASM .co) successfully captures — but +78% regression:

```
m=4:   without=17 µs, with=32 µs (+88%)
m=16:  without=25 µs, with=49 µs (+96%)  ← copy_() dominates
m=256: without=24 µs, with=37 µs (+56%)
```

**Root cause:** Three `copy_()` calls per invocation (A, B_shuffle, B_scale_sh) scale
with tensor size. For A: M×7168 fp16, the copy alone exceeds the 8-34 µs GEMM time.
**Rule:** Data movement IS the bottleneck — not kernel dispatch. Graphs only help if inputs
already reside in static GPU buffers. For MXFP4 GEMM, they never do.

### MoE: Non-Temporal Loads Are Neutral

`AITER_USE_NT=1` bypasses L2 cache for weight reads. Hypothesis: weights aren't reused,
so NT loads avoid polluting L2 with stale data. **Wrong hypothesis:**
CK kernel tiles ARE reused across tokens — multiple tokens map to the same expert block.
L2 reuse IS beneficial for MoE. NT loads remove this benefit but also remove the reload
cost — the effects cancel at ~155 µs. Zero change across all 6 shapes.

### MLA: Metadata Caching Saves 25%

`get_mla_metadata_info_v1` + `get_mla_metadata_v1` allocate and populate 8 work buffer
tensors (`work_meta_data`, `work_indptr`, `work_info_set`, `reduce_indptr`,
`reduce_final_map`, `reduce_partial_map`, `kv_indices`, `kv_last_page_len`) on every call.
These are deterministic for fixed `(bs, qseqlen, kvseqlen)` — safe to cache:

```python
_cache: dict = {}

def _build_cache(bs, qseqlen, kvseqlen, qo_indptr, kv_indptr) -> dict:
    # ... get_mla_metadata_info_v1 + get_mla_metadata_v1 calls ...
    return {"kv_indices": ..., "work_meta_data": ..., ...}  # 8 tensors

key = (bs, qseqlen, kvseqlen)
if key not in _cache:
    _cache[key] = _build_cache(...)
c = _cache[key]
mla_decode_fwd(..., work_meta_data=c["work_meta_data"], ...)
```

Also lowered the einsum↔fp8 threshold from 400k→100k tokens (tighter crossover point).
Combined result: large shapes improved 27-43% while small shapes remained at einsum speed.

## Phase 15: Direct torch.ops.aiter Calls + HIP C++ Quant Validation (March 2026)

**Four-track parallel effort. Two kernel improvements attempted, one submitted.**

### Track A: HIP C++ MXFP4 Quant — Correct but Slower

**Goal:** Replace Triton `dynamic_mxfp4_quant` with HIP C++ kernel using exact aiter E8M0 algorithm.

**Result:** 0.0 error across all shapes (bit-exact E8M0), but ~22.8µs geomean vs ~20.8µs for Triton.

**Root cause of regression:** HIP kernel uses shared memory reduction with `__syncthreads()` for
group-level amax computation (16 lanes per group, tree reduction). Triton's `dynamic_mxfp4_quant`
uses warp-level `tl.max` which maps directly to hardware wave64 reduce instructions on MI355X —
no shared memory bank conflicts, no explicit synchronization barriers.

**Key technical finding — aiter's exact E8M0 algorithm:**
```c
// IEEE 754 bit manipulation: round mantissa to nearest, clear mantissa bits
unsigned int rounded = (amax_u32 + 0x200000u) & 0xFF800000u;
int exp_biased = (rounded >> 23) & 0xFF;
int scale_byte = exp_biased - 2;  // E8M0 with fp4 normalization
float quant_scale = exp2f(129.0f - exp_biased);
```

This differs from the previously assumed `floor(log2(amax)) + 127` formula (see Phase 6 skill
`triton-fp4-inline-quantization`). The `+0x200000` adds 0.5 ULP to the mantissa before masking,
implementing round-to-nearest-even at the IEEE 754 bit level. The `-2` offset accounts for fp4
e2m1's max value of 6.0 (= 2^2 × 1.5).

**FP4 e2m1 encoding also validated:**
- Saturated path: `|x| >= 6.0` → 0x7
- Denormal path: `|x| < 1.0` → magic number addition trick (`0x4A800000`)
- Normal path: IEEE round-to-nearest-even via mantissa bit manipulation

**Decision:** Restored GEMM submission to `dynamic_mxfp4_quant + gemm_a4w4` (~20.8µs).
HIP kernel preserved as `submission_hip_v8.py` for reference.

### Track B: Helion Fused Quant+GEMM — Cancelled (Economic Dead End)

**Goal:** Single Triton kernel fusing bf16→fp4 quant + GEMM via `tl.dot_scaled`.

**Analysis:** Phase 6 showed custom `tl.dot_scaled` is 68% slower than `gemm_afp4wfp4` ASM.
Even eliminating all pipeline overhead (quant ~10µs + shuffle ~1µs + launch ~2µs = ~13µs savings),
the fused kernel would benchmark ~34.6µs × (20.8/34.6) ≈ still slower than ASM pipeline.

**Decision:** Track cancelled before implementation. The math doesn't work — ASM GEMM is too fast
for Triton fusion to overcome its inherent overhead on MI355X.

### Track C: MLA Direct torch.ops.aiter Dispatch — New Best

**Goal:** Bypass `mla_decode_fwd` Python wrapper overhead by calling ASM kernel directly.

**Approach:** Instead of the originally planned C++ bridge (`torch.utils.cpp_extension.load_inline`),
discovered that calling `aiter.mla_decode_stage1_asm_fwd` and `aiter.mla_reduce_v1` directly
from Python eliminates most wrapper overhead. Combined with pre-allocating intermediate buffers.

**Key optimizations over Phase 14:**

1. **Direct ASM kernel call** — bypasses `mla_decode_fwd` wrapper (saves ~3-5µs of Python
   conditionals, shape assertions, and buffer allocation logic per call)

2. **Pre-allocated intermediate buffers** — `logits` and `attn_lse` tensors cached in `_cache`
   dict, eliminating 2× `torch.empty` GPU allocations per call (~2-3µs each)

**Direct call signatures discovered via runner probe:**

```python
# Stage 2: C++ reduce
```

### Key Learnings

1. **Shared memory reduction < warp-level reduce on MI355X:** HIP `__syncthreads()` + shared
   memory tree reduction is inherently slower than Triton's `tl.max` which maps to wave64
   hardware reduce. Don't port Triton patterns to HIP naively — use warp intrinsics instead.

2. **Direct operator dispatch > C++ bridge:** Calling `torch.ops.aiter` functions directly
   from Python achieves ~80% of the theoretical overhead reduction of a C++ bridge, with
   zero compilation risk and no `.so` loading. The remaining ~20% overhead is Python function
   call dispatch itself — only eliminable via C++ or ctypes.

3. **Buffer pre-allocation compounds with direct dispatch:** Each `torch.empty` on GPU costs
   ~1-3µs. Pre-allocating reusable buffers in a cache dict removes this per-call cost entirely.
   Combined with direct dispatch, the total savings are ~5-8µs per aiter call.

4. **Economic analysis before implementation saves days:** Track B was cancelled before writing
   any code because the math (68% Triton overhead × pipeline savings) showed it couldn't win.
   This saved ~4-6 hours of implementation + debugging + submission cycles.

# aiter Kernel Parameter Semantics (AMD MI355X)

## Problem

aiter's `fused_moe` and `mla_decode_fwd` have parameters that sound like performance flags
but actually change computation or have counter-intuitive effects on MI355X.

## fused_moe: doweight_stage1

### What it does

`doweight_stage1=True` moves the `topk_weights` multiplication from **stage 2** (after SiLU
activation) to **stage 1** (before SiLU activation).

- `doweight_stage1=False` (default): `output = SiLU(gate(x)) * up(x)`, then multiply weights in stage 2
- `doweight_stage1=True`: multiply weights in stage 1 BEFORE activation

### Why it causes correctness failure

SiLU is a **nonlinear** activation. Multiplying weights before vs after a nonlinear activation
produces mathematically different results:

```
w * SiLU(gate(x)) * up(x)   ≠   SiLU(w * gate(x)) * (w * up(x))
```

This is not a subtle numerical difference — it produces ~80% element mismatches with 10-30%
per-element error (well above the 5e-2 tolerance for MoE).

**Rule:** `doweight_stage1=True` only produces correct results for linear activations (ReLU-like),
not for SiLU/GELU. For MXFP4 MoE with SiLU, always use `doweight_stage1=False`.

## fused_moe: OPUS Sorting (AITER_USE_OPUS_MOE_SORTING)

Setting `os.environ["AITER_USE_OPUS_MOE_SORTING"] = "1"` before calling `fused_moe` switches
to the OPUS sorting backend (`moe_sorting_opus_fwd` instead of `moe_sorting_fwd`).

**Correctness:** OPUS sorting only changes token dispatch order — the computation is identical.
Setting this env var passes correctness tests (verified, max error 0.015625).

**Performance on MXFP4 variant:** NO EFFECT. The env var is not wired into the fp4x2 code path
in `fused_moe.py`. JIT still builds `module_moe_sorting` (not `module_moe_sorting_opus`), and
benchmark times are identical to reference. This was verified by running the full benchmark suite.

## fused_moe: block_size_M

Override the auto-selected tile size for the token dimension:

```python
fused_moe(..., block_size_M=64)  # or 32, 128
```

Default is `-1` (auto-selects from tuned CSV configs). For MXFP4 with different model configs:
- bs=8 (small): auto-selects `block_m=32`
- bs=128 (medium): auto-selects `block_m=64`

**DANGER: Forcing `block_size_M=64` causes GPU memory access faults on benchmark configs.**
When `estimated_m_per_expert` is low (e.g., bs=16 with 256 experts = ~1 token/expert), a tile
size of 64 exceeds the actual data bounds and causes a hardware-level `Memory access fault by
GPU node-2`. The auto-tuner correctly selects smaller tiles for these shapes. **Never override
`block_size_M` without verifying it's safe for ALL shapes in the benchmark suite.**

## mla_decode_fwd: fast_mode is SLOWER on MI355X

### What it does

`fast_mode=True` in `get_mla_metadata_info_v1` and `get_mla_metadata_v1` changes the work
distribution strategy: `(bs + cu_num) * tiles` work items vs `tile_cnt * cu_num`.

### Test results (MI355X, DeepSeek R1 MLA, fp8)

| Config | fast_mode=False (reference) | fast_mode=True, adaptive splits | fast_mode=True, fixed splits=32 |
|--------|----------------------------|--------------------------------|--------------------------------|
| bs=4, kv=1024 | ~131 us | ~154 us | ~152 us |
| bs=256, kv=8192 | ~462 us | ~536 us | ~542 us |
| Geomean | ~191 us | ~224 us (+17%) | ~232 us (+21%) |

**fast_mode=True is 17-21% SLOWER than fast_mode=False on MI355X for decode workloads.**

The reference implementation already uses well-tuned defaults. Changing `fast_mode` to `True`
and `num_kv_splits` from 32 to adaptive values (4-16 depending on batch size) both made
performance worse, not better.

**Rule:** For MLA decode on MI355X with the DeepSeek R1 forward_absorb architecture, use:
```python
fast_mode=False
num_kv_splits=32
intra_batch_mode=True
```

## fused_moe: AITER_KSPLIT (Environment Variable)

`AITER_KSPLIT=N` switches `fused_moe` between two entirely different kernel implementations:

- **KSPLIT=0 (default / unset):** Uses `module_moe_ck2stages_fp4x2_fp4x2_preshuffle_*` — MXFP4-optimized CK kernels, fast for dense token distributions
- **KSPLIT>0:** Uses `module_moe_cktile2stages` — generic cktile kernels (not MXFP4-specialized), but better for sparse token distributions

**Critical:** AITER_KSPLIT is **completely ignored** for shapes with pre-tuned CSV configs (e.g., 257-expert DeepSeek-V3 configs in `tuned_fmoe.csv`). Only affects shapes that fall back to default kernel selection.

### ⚠️ DANGER: KSPLIT=4 Causes Catastrophic Overflow for 32/33-expert shapes

**Confirmed 2026-03-15:** Widening the KSPLIT=4 threshold to cover all sparse shapes (e.g., `est_m < 100`) causes **catastrophic numerical overflow (~1e27 output values)** for 32/33-expert shapes with dexp=512.

**Root cause:** For 33E/dexp=512, `K = 512` → `K / KSPLIT = 512 / 4 = 128`. The cktile reduction kernel has a minimum effective K-chunk requirement that 128 violates. Result: garbage values, not an error — silently produces ~1e27 where max error should be ~0.015.

**Symptom:** Correctness tests with ONLY 257E shapes pass (max error 0.015625 within 5e-2 tolerance). Benchmarks with 33E shapes produce `1e27`. Easy to miss if test suite doesn't cover all expert topologies.

**Safe KSPLIT=4 condition:** `num_experts >= 200` only (257E topology: dexp=256, K/4=64 safe). For any 32/33-expert shape: KSPLIT ≤ 2.

```python
# SAFE — confirmed correct for all 7 competition shapes
if estimated_m >= 50:
    ks = "default"                              # CK MXFP4 path
elif num_experts >= 200 and estimated_m < 10:
    ks = "4"                                    # 257E only — dexp=256, K/4=64 safe
else:
    ks = "2"                                    # 33E — dexp=512, K/4=128 overflows

# DANGEROUS — causes 1e27 for bs=16, 33 experts, dexp=512:
# if estimated_m < 100: ks = "4"   ← NEVER DO THIS
```

### Expert-Count-Aware Adaptive KSPLIT Pattern

Setting env var per-call works because AITER checks it at dispatch time (not module import):

```python
import os

num_experts = gate_up_weight_shuffled.shape[0]
estimated_m = topk_ids.numel() // num_experts

if estimated_m >= 50:
    # Dense: CK MXFP4-optimized path
    os.environ.pop("AITER_BYPASS_TUNE_CONFIG", None)
    os.environ.pop("AITER_KSPLIT", None)
elif num_experts >= 200 and estimated_m < 10:
    # Large expert count, very sparse: KSPLIT=4 for K-parallelism
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"
    os.environ["AITER_KSPLIT"] = "4"
else:
    # Moderately sparse or small expert count: KSPLIT=2
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"
    os.environ["AITER_KSPLIT"] = "2"

return fused_moe(...)
```

### Stderr Diagnostics: Reading Kernel Path Selection

The aiter log output tells you definitively which path was taken — critical for debugging KSPLIT behavior:

**CSV-tuned shape (KSPLIT ignored):**

The parenthetical `(kernelName1=...)` means a specific CSV-tuned kernel was selected. AITER_KSPLIT has no effect here.

**Default shape (KSPLIT applies):**

The `using 2stage default` message confirms KSPLIT was read and applied. `ksplit = 2` confirms the cktile path was selected.

## fused_moe: AITER_BYPASS_TUNE_CONFIG (Environment Variable)

`AITER_BYPASS_TUNE_CONFIG=1` forces the **heuristic path** for all shapes, even those with pre-tuned CSV configs:

```python
if cfg is None or int(os.environ.get("AITER_BYPASS_TUNE_CONFIG", "0")):
    # Heuristic path — AITER_KSPLIT applies here
    ksplit = get_ksplit(token, topk, expert, inter_dim, model_dim)
    ...
```

**Use case:** When CSV-tuned configs exist (e.g., 257-expert DeepSeek TP=8 shapes) but you want to test the cktile (split_k) path for cold-cache benchmarks.

Combined strategy:
```python
if estimated_m < 50:
    os.environ["AITER_BYPASS_TUNE_CONFIG"] = "1"  # Ignore CSV for sparse shapes
    os.environ["AITER_KSPLIT"] = "2"              # Force cktile path
else:
    os.environ.pop("AITER_BYPASS_TUNE_CONFIG", None)
    os.environ.pop("AITER_KSPLIT", None)           # CK path for dense
```

**Risk:** CSV configs were pre-tuned (possibly at hot cache). Cold-cache benchmarks may or may not prefer cktile — requires empirical testing.

**AITER_ONLINE_TUNE Warning:** `AITER_ONLINE_TUNE=1` blocks on running `gemm_moe_tune.py` (a full benchmark sweep) before returning for the FIRST call. This adds many minutes to the first call and will TIMEOUT a 12-minute workflow.

## fused_moe: cktile Path Trigger Conditions

The cktile kernels (`cktile_moe_stage1` + `cktile_moe_stage2`) are used instead of CK when ALL of:
1. `dtype in [bf16, fp16]`
2. `q_type == QuantType.per_1x32` (MXFP4)
3. `q_dtype_w in [dtypes.fp4x2]` (MXFP4 weights)
4. **`ksplit > 1`** — set by AITER_KSPLIT or get_ksplit()
5. **`is_shuffled=True`** — requires pre-shuffled weights (shuffled variants in submission)

If any condition is false, the CK path is used. Using `gate_up_weight_shuffled` and `down_weight_shuffled` (shuffled=True) is required for cktile.

## mla_decode_fwd: A16W8 vs A8W8 ASM Kernel Tile Configs

### Critical Discovery (March 2026)

aiter loads **two different MLA ASM binaries** with different tile configurations. The choice
between them is made based on `q_scale` parameter: `q_scale=None` → a16w8 kernel,
`q_scale=<tensor>` → a8w8 kernel.

```
mla_a16w8_qh16_m16x4_n16x1_coex0_mask1_ps  # Small-batch tile config (m16x4=16M, n16x1=small N)
mla_a8w8_qh16_qseqlen1_gqaratio16_ps        # Large-batch tile config (gqaratio16=GQA-aware)
```

### Performance Impact (MI355X, bs=256, kv=8192)

| Kernel | Total KV | Median | Notes |
|--------|----------|--------|-------|
| A8W8 (`q_scale=<tensor>`) | 2,097,152 | **302 µs** | GQA-aware tile, bandwidth-optimal |
| A16W8 (`q_scale=None`) | 2,097,152 | **591 µs** | Small-batch tile, 2x slower at scale |

At large shapes, A8W8 is **2x faster** despite paying ~3µs in Q quantization cost
(3 kernel launches: amax → scale → cast+clamp).

### Breakeven: A16W8_THRESHOLD = 262144

Geomean analysis shows A16W8 wins at `total_kv ≤ 262144` (small-to-medium shapes).
For larger shapes, the A8W8 kernel's GQA-aware tile configuration fully compensates
for the Q quantization cost.

### Why the assumption "Q is tiny, skip quantization" is wrong for large shapes

The 3-kernel Q quantization overhead (~3 µs) is irrelevant compared to the ASM kernel
tile config difference (~289 µs at bs=256, kv=8192). The two ASM binaries have fundamentally
different memory access patterns — the a8w8 variant is tuned for large GQA ratios.

**Rule:** Never "always A16W8". Use the threshold pattern:

```python
A16W8_THRESHOLD = 262144  # total_kv at which A8W8 begins to win

use_a16w8 = (bs * kvseqlen) <= A16W8_THRESHOLD
# A16W8: q_scale=None, q passes bf16 directly
# A8W8:  q_scale=<float32 tensor>, q quantized to fp8 first
```

### Updated mla_decode_fwd Quick Reference

| Parameter | Value | Effect | Change? |
|-----------|-------|--------|---------|
| `q_scale` | `None` for A16W8, `<tensor>` for A8W8 | Kernel binary selection | Set by A16W8_THRESHOLD |
| `fast_mode` (metadata) | `True` (production) | Work distribution | Use True in production |
| `num_kv_splits` | 1/4/8/16 by KV size | K-parallelism | Cap at 16 (32 adds reduction overhead) |
| `intra_batch_mode` | `True` | Intra-batch parallelism | Do not change |

## 1. Sparse Dispatch Opportunities

### The Ultra-Sparse Regime You Are In

For 256 experts at bs=16 with topk=2 (standard DeepSeek routing), expected tokens per expert ≈ 16×2/256 = **0.125 tokens/expert**. Even at topk=8, that's only 0.5. The overwhelming majority of your 256 experts receive zero tokens at every inference step.

This is a profoundly different regime from the shapes AITER's `fused_moe` was tuned for (bs=512–4096). The CK kernel's sorting and dispatch overhead is paid for all 256 expert slots regardless.

### Align & Sort is the Primary Target

AMD's own analysis showed that the token-sorting step (align & sort) was spending **33M cycles on alignment + 8M cycles on placement** for each `fused_moe` call. At bs=16/256 experts, this sorting overhead likely represents 20–40% of your total kernel time — and the actual GEMM work is trivially small.

The AMD-optimized multi-block align & sort achieved **7x speedup on MI300X** over the original. The key insight from their implementation: they use aggressive LDS (5kB) and VGPRs (52 per wave, zero register spills) to parallelize expert counting across all 256 slots simultaneously. For gfx950, the gains should be equal or better given the improved CDNA4 register file.

**The actionable lever**: If you can call `aiter.moe_sorting_fwd` directly and pass its outputs (`sorted_ids`, `sorted_weights`, `sorted_expert_ids`, `num_valid_ids`) to `ck_moe_stage1/ck_moe_stage2`, you can potentially replace the built-in sorting with a version that skips zero-count experts before dispatching to stage2. The `num_valid_ids` output already encodes valid token count — the question is whether stage1/stage2 can accept a masked expert list that excludes zero-token experts.

### Triton Sparse Dispatch (Python-Legal Path)

A fully Python/Triton-legal approach: implement a **sparse expert dispatch wrapper** that:
1. Runs `torch.bincount` on the routing decisions (cheap, ~5µs)
2. Builds a compact `active_expert_ids` tensor containing only experts with token_count > 0
3. Calls a custom Triton grouped GEMM only over those active experts
4. Scatters results back

At bs=16/256 experts, you'd expect roughly 16×topk ≈ 32 active experts out of 256. Running GroupGEMM over 32 experts instead of 256 with proper tile sizing is the fundamental win. The challenge: the MXFP4 weight dequantization requires the CK/ASM backend, so pure Triton will be slower per-FLOP. ## 2. GEMV vs GEMM Path

### When the Regime Changes

The theoretical crossover point from GEMM-efficient to GEMV-efficient is at approximately M=8–16 tokens per expert per batch. Below this threshold, matrix-vector multiply avoids the overhead of tiled GEMM block setup.

Your shapes:
- **256 experts, bs=16**: ~0.125 tokens/expert → deep GEMV regime
- **256 experts, bs=128**: ~1 token/expert → borderline
- **256 experts, bs=512**: ~4 tokens/expert → GEMM begins to be worthwhile
- **32 experts, bs=16**: ~1 token/expert → GEMV regime
- **32 experts, bs=128**: ~8 tokens/expert → GEMM crossover
- **32 experts, bs=512**: ~32 tokens/expert → GEMM clearly beneficial

For the bs=16 shapes specifically, a dedicated MXFP4 GEMV kernel (matrix-vector multiply where M=1 for most experts) could be substantially faster than trying to pack empty tiles into a GEMM. The problem: MXFP4 GEMV requires hardware dequantization support (the `v_cvt_scalef32_pk_fp4_f32` instruction on gfx950), which is not yet exposed cleanly in pure Triton without intrinsic injection.

### What Is Achievable in Triton

A BF16 or FP8 fallback path for the GEMV regime is viable in Triton. For the bs=16 ultra-sparse case, you could:
- Run CK/AITER at full precision for the ~32 active experts (GEMV mode)
- Accept the quantization round-trip cost (dequant MXFP4 → BF16 → GEMV → requant) 
- This may still beat running a 256-expert CK grouped GEMM that mostly processes empty tiles

The competition's 145µs likely comes from expert-aware dispatching that correctly identifies the GEMV regime and handles it separately. MoE-Gen's architecture paper ([arxiv.org/abs/2503.09716](https://arxiv.org/abs/2503.09716)) demonstrates that module-based batching with per-expert sequential dispatch can achieve 9–63x throughput improvement specifically by avoiding the empty-tile problem.

## 3. AMD-Specific Insights for gfx950 / MI355X

### K Tile Size Is Likely Wrong for Your Shapes

This is the highest-confidence actionable finding. IREE's open work ([github.com/iree-org/iree/issues/22309](https://github.com/iree-org/iree/issues/22309)) directly found that for gfx950 MXFP4 matmuls, the default K tile size heuristic was assigning **too many MFMAs per loop**, preventing software pipelining. The fix yielded 5x in the extreme case, and 0.95x–5.67x across shapes. For your MoE shapes:

- **dexpert=256, bs=16**: K=256, M≈2 → K tile = 16 or 32 would likely pipeline better than K=64 or K=128
- **dexpert=512, bs=16**: K=512, M≈1 → K tile = 32 is likely better than K=128
- **dexpert=2048, bs=512**: K=2048, M≈32 → K tile = 64–128 may be optimal

The `AITER_BYPASS_TUNE_CONFIG=1` you're already using forces the cktile/ksplit=2 path, but the underlying `block_m` and K-dimension tile sizes within that path may still not be optimal for your specific expert shapes. Directly inspecting `aiter/hsa/gfx950/fmoe_2stages/*.csv` (if accessible) to verify what `block_m` values are being used for your exact (token, model_dim, inter_dim, expert) tuples would tell you immediately whether there's headroom.

### XCD-Aware Grid Sizing

MI300X/MI355X have multiple compute dies (XCDs). Cross-XCD L2 traffic is expensive. The ROCm optimization guide explicitly states: adapt grid size to a multiple of the number of XCDs per chip. For your grouped GEMM over 256 experts with sparse occupancy, if the grid size isn't a multiple of the XCD count, you're paying unnecessary cross-die synchronization. MI355X has 8 XCDs (carrying forward from MI300X architecture). Your expert count of 256 divides evenly by 8, which is favorable.

### `__builtin_nontemporal_load` for Non-Reused Weight Tiles

For the ultra-sparse bs=16 case, expert weights that receive 0–1 tokens will not be reused in L2. Using nontemporal loads (bypassing L2) for non-active expert weights frees L2 capacity for the active experts' weights, increasing effective cache bandwidth for the ~32 experts that actually need it. This is a kernel-level trick not accessible through the Python API surface, but it's what separates custom implementations from `fused_moe`.

## 1. JIT Pre-warming Opportunities

### The Core Mechanism

AITER's JIT system is built on the `@compile_ops` decorator in `aiter/jit/core.py`. When any decorated function (like `ck_moe_stage1`, `moe_sorting_fwd`) is first called, it:
1. Checks the in-process `__mds` dict via `get_module()` (wrapped with `@functools.lru_cache(maxsize=1024)`)
2. On cache miss, compiles via Ninja/hipcc and writes a `.so` to disk
3. On subsequent process invocations, re-reads the `.so` from disk (fast)

The `.so` files are stored persistently. The ROCm blog confirms: "JIT compiles operators during the first run and stores dynamic libraries under `aiter/jit/` for reuse in subsequent executions." The DeepWiki analysis surfaces `AITER_JIT_DIR` as the env var controlling that directory.

### Critical Finding: PREBUILD_KERNELS + GitHub Actions Cache

The most actionable path to eliminating the 155s JIT overhead is to prebuild kernels as a separate CI step and cache the resulting `.so` files using `actions/cache`. Here is what the aiter CI itself does ([PR #2100](https://github.com/ROCm/aiter/pull/2100), merged Feb 25 2026):

```bash
# WRONG - does not actually compile kernels (setup.py develop skips build_ext)
PREBUILD_KERNELS=1 GPU_ARCHS=gfx950 pip install -e .

# CORRECT - forces NinjaBuildExtension.run() to fire
PREBUILD_KERNELS=1 GPU_ARCHS=gfx950 python setup.py build_ext --inplace
pip install -e .  # editable install separately
```

[Issue #2099](https://github.com/ROCm/aiter/issues/2099) (now closed) documented that CI was shipping without prebuilt kernels because `pip install -e .` intercepts via `pyproject.toml` and skips the Ninja build. The symptom: "Prebuilding kernels completed" printed in ~20s instead of ~40min, because zero kernels were actually compiled. That bug is now fixed in the CI but you may be hitting the same issue if you prebuild incorrectly.

### What PREBUILD_KERNELS Controls

From the DeepWiki analysis and issue #1096:
- `PREBUILD_KERNELS=1` — prebuild decode-focused kernels (includes `module_moe_asm`, `module_gemm_a8w8`)
- `PREBUILD_KERNELS=2` — prebuild decode + prefill kernels

**Critical caveat ([Issue #1096](https://github.com/ROCm/aiter/issues/1096))**: `PREBUILD_KERNELS=1` currently fails with an `AssertionError` in `_write_ninja_file` because `setup.py` omits the `gradlib/` directory from `aiter_meta/`. The workaround is to ensure `gradlib/csrc/` and `gradlib/include/` are present.

### AITER_JIT_DIR: The Cache Directory Pointer

Setting `AITER_JIT_DIR=/path/to/cached/so/files` redirects where aiter looks for (and writes) compiled `.so` modules. This is the key to a GitHub Actions workflow strategy:

```yaml
- name: Restore aiter JIT cache
  uses: actions/cache@v4
  with:
    path: /tmp/aiter-jit-cache
    key: aiter-jit-${{ runner.os }}-gfx950-${{ hashFiles('requirements.txt') }}

- name: Pre-warm aiter JIT
  env:
    AITER_JIT_DIR: /tmp/aiter-jit-cache
    GPU_ARCHS: gfx950
  run: |
    python -c "import aiter; from aiter.fused_moe import fused_moe; ..."
    # Force all 3 expensive modules to compile

- name: Run benchmark
  env:
    AITER_JIT_DIR: /tmp/aiter-jit-cache  # reuse cached .so
  run: python eval_moe_mxfp4.py
```

**However**, the competition runs on GPU hardware that aiter's CI doesn't have at the Actions cache stage — so the runner that compiles `.so` files must be the same GPU architecture (gfx950). If the popcorn-cli evaluation uses MI355X runners, you cannot pre-warm from a CPU-only Actions step. The `.so` files are architecture-specific HSACO binaries.

### AMD's Own Strategy

From AMD's MLPerf Inference v5.1 blog: "AMD pre-compiles Triton kernel shapes to prevent JIT compilation overheads during performance runs, and uses HipGraph mode to streamline kernel launches." This confirms the approach — but it only works when you control the pre-compile step on the same hardware.

## 2. Direct Kernel Invocation: Bypassing fused_moe

### The Two-Stage Architecture

`fused_moe` internally calls:
1. `moe_sorting_ck()` / `moe_sorting_fwd()` → produces `sorted_token_ids`, `sorted_weight_buf`, `sorted_expert_ids`, `num_valid_ids`
2. `ck_moe_stage1` → FC1 projection (hidden → intermediate, with activation)
3. `ck_moe_stage2` → FC2 projection (intermediate → output)

### Direct Stage API

From [Issue #822](https://github.com/ROCm/aiter/issues/822) and the DeepWiki analysis, `ck_moe_stage1` and `ck_moe_stage2` are directly accessible Python functions:

```python
from aiter.ops.moe_op import ck_moe_stage1, ck_moe_stage2
from aiter.fused_moe import moe_sorting
```

Both are decorated with `@compile_ops("module_moe_ck2stages")` — they share the same compiled module, so loading either one loads both. The earlier decorator form had `gen_func=cmdGenFunc_ck_moe_stage` for blob code generation; the fix in Issue #822 removed `gen_func` to use a prebuilt blob.

### vLLM's `rocm_aiter_fused_moe_impl` Signature

The most complete documented function signature for direct invocation is the vLLM wrapper ([docs.vllm.ai](https://docs.vllm.ai/en/v0.9.0/api/vllm/model_executor/layers/fused_moe/rocm_aiter_fused_moe.html)):

```python
rocm_aiter_fused_moe_impl(
    hidden_states: Tensor,
    w1: Tensor,
    w2: Tensor,
    topk_weight: Tensor,
    topk_ids: Tensor,
    expert_mask: Optional[Tensor] = None,
    activation_method: int = 0,  # ActivationMethod.SILU
    quant_method: int = 0,       # QuantMethod.NO
    doweight_stage1: bool = False,
    w1_scale: Optional[Tensor] = None,
    w2_scale: Optional[Tensor] = None,
    a1_scale: Optional[Tensor] = None,
    a2_scale: Optional[Tensor] = None,
) -> Tensor
```

`doweight_stage1` controls whether router weights are applied at stage 1 or stage 2 — this can affect throughput.

### Sorting Bypass Potential

The sorting step compiles `module_moe_sorting` (~25s JIT) and runs `moe_sorting_fwd` via CK. There is **no documented way to skip it** short of pre-computing sorted tensors and passing them directly to `ck_moe_stage1`. If your benchmark shapes are fixed (they are — 7 specific shapes), you could pre-sort once and reuse the sort outputs.

**New: topk_sigmoid DPP kernel ([PR #1909](https://github.com/ROCm/aiter/pull/1909))**: This is a 1.66x faster GFX9-optimized DPP kernel for `topk_sigmoid`. However, it explicitly dispatches only on `gfx9` architectures — gfx950 (MI355X) is **gfx9x**, and the PR specifies GFX9 dispatch with CK fallback for others. Whether gfx950 is covered under the GFX9 dispatch branch needs verification. This PR adds no new JIT module — it patches into the existing topk path.

     ```python
     def ollama_generate(model: str, prompt: str, *, timeout: int = 600) -> str:
         """Call local Ollama model via HTTP streaming API for hypothesis generation."""
         import urllib.request
         import urllib.error
         url = "http://localhost:11434/api/generate"
         payload = json.dumps({
             "model": model,
             "prompt": prompt,
             "stream": True,
             "keep_alive": "30m",
             "options": {"num_predict": 1024, "temperature": 0.7},
         }).encode()
         req = urllib.request.Request(url, data=payload, headers={"Content-Type": "application/json"})
         try:
             chunks: list[str] = []
             t0 = time.time()
             with urllib.request.urlopen(req, timeout=300) as resp:
                 for raw_line in resp:
                     line = raw_line.decode().strip()
                     if not line: continue
                     try:
                         data = json.loads(line)
                     except json.JSONDecodeError:
                         continue
                     token = data.get("response", "")
                     if token: chunks.append(token)
                     if data.get("done", False): break
                     if time.time() - t0 > timeout:
                         print(f"[ollama] hard timeout after {timeout}s", file=sys.stderr)
                         break
             elapsed = time.time() - t0
             result = "".join(chunks).strip()
             n_tokens = len(chunks)
             speed = n_tokens / elapsed if elapsed > 0 else 0
             print(f"[ollama] {model}: {n_tokens} tokens in {elapsed:.0f}s ({speed:.1f} tok/s)")
             return result
         except urllib.error.URLError as e:
             print(f"[ollama] HTTP error: {e}", file=sys.stderr)
             return ""
         except TimeoutError:
             print(f"[ollama] {model} socket timeout (no tokens for 120s)", file=sys.stderr)
             return ""
         except Exception as e:
             print(f"[ollama] unexpected error: {e}", file=sys.stderr)
             return ""
     ```

## HipKittens Runner Viability: **NO**

### How HipKittens Works

HipKittens is a **C++ embedded DSL** compiled via **hipcc** (AMD's HIP compiler). The build pipeline is:

1. **C++ source files** (e.g., `256_256_64_32_with16x32.cpp`) contain HIP kernel code with inline assembly and explicit register pinning
2. **Makefile** compiles them with `hipcc --offload-arch=gfx9XX -shared -fPIC` using **pybind11** headers
3. **Output**: a shared library named `tk_kernel<python-extension-suffix>.so` (e.g., `tk_kernel.cpython-312-x86_64-linux-gnu.so`)
4. **Python usage**: `import tk_kernel` then `tk_kernel.dispatch_micro(A, Bt, C)`

### Why It Cannot Run on the Competition Runner

**Three blocking issues:**

1. **Requires hipcc compilation at build time.** The Makefile invokes `/opt/rocm/bin/hipcc` with `-shared -fPIC` to produce the `.so`. The runner blocks `subprocess+amdclang++` patterns, and hipcc is a wrapper around amdclang++. Even if hipcc itself isn't literally string-matched, the compilation step requires invoking a subprocess to run the compiler, which the runner's static source scanning would catch.

2. **Produces and loads `libamdhip64.so` dependent shared libraries.** The compiled `tk_kernel.so` links against the HIP runtime (`libamdhip64.so`), which is explicitly blocked by the runner's static scanner.

3. **HK is NOT Triton-based.** The entire point of HipKittens is to bypass both Triton and hipcc's optimizer by using explicit register scheduling and inline assembly wrapped in C++ templates. There is no Triton JIT path. The paper explicitly criticizes Triton's limitations on AMD as a motivation for building HK.

### Detailed Constraint Check

| Runner Constraint | HK Triggers It? | Explanation |
|---|---|---|
| `hipModuleLaunchKernel` | Likely YES | pybind11 HIP extensions use HIP runtime launch APIs under the hood |
| `hipLaunchKernelGGL` | Likely YES | Standard HIP kernel launch macro used by hipcc-compiled code |
| `<<<>>>` | Possibly | HIP C++ syntax for kernel launch (hipcc translates these) |
| `load_inline` | NO | HK uses Makefile pre-compilation, not `torch.utils.cpp_extension.load_inline` |
| `subprocess+amdclang++` | YES if compiling at runtime | hipcc wraps amdclang++; any JIT compilation attempt would trigger this |
| `libamdhip64.so` | YES | The compiled `.so` dynamically links against `libamdhip64.so` |

### What HK Is NOT

- **Not a Python library** -- it's a C++ framework with pybind11 wrappers
- **Not pip-installable** -- requires `git clone`, `source env.src`, `make`
- **Not Triton-based** -- explicitly an alternative to Triton
- **Not JIT-compiled** -- AOT compilation via hipcc + Makefile

### Could It Be Adapted?

No practical path exists. HK's value proposition is direct hardware control via C++ templates wrapping AMD ISA instructions. The entire compilation and runtime stack (hipcc, pybind11 `.so`, HIP runtime) is blocked by the runner. You cannot translate HK kernels to Triton because HK exists specifically because Triton cannot express the optimizations HK provides (explicit AGPR/VGPR pinning, wave scheduling, chiplet-aware grid policies).

### 2. `asm_moe` (Assembly-Optimized MoE)

**Status:** Exists, accessible, enabled by default in vLLM when `VLLM_ROCM_USE_AITER=1`.

**Import path:** `from aiter.fused_moe_bf16_asm import asm_moe`

**Signature:**
```python
def asm_moe(
    hidden_states: Tensor,
    w1: Tensor,
    w2: Tensor,
    topk_weight: Tensor,
    topk_ids: Tensor,
    fc1_scale: Optional[Tensor] = None,
    fc2_scale: Optional[Tensor] = None,
    fc1_smooth_scale: Optional[Tensor] = None,
    fc2_smooth_scale: Optional[Tensor] = None,
    a16: bool = False,
    per_tensor_quant_scale: Optional[Tensor] = None,
    block_shape: Optional[tuple] = None,
    expert_mask: Optional[Tensor] = None,
    activation: ActivationType = ActivationType.Silu,
    local_expert_hash: Optional[Tensor] = None,
)
```

**Supports:** Pure BF16, A16W8, A8W8, INT8, and FP8 block-scaled quantization. It auto-dispatches internally based on whether scales/block_shape are provided. Dynamic per-tensor FP8 quantization is the key use case for models like Mixtral.

**Performance:** Hand-tuned assembly for gfx942/gfx950. This is the "best performance on AMD platform" per AMD's own documentation.

Several kernels exist that are not directly exposed through the high-level `fused_moe()` API but are accessible through lower-level imports:

| `fmoe_int8_g1u0_a16` | `aiter.ops.moe_op` | INT8 MoE with BF16 input |
| `fmoe_g1u1` | `aiter.ops.moe_op` | FP8 per-tensor with gate-up split |
| `fmoe_g1u1_a16` | `aiter.ops.moe_op` | FP8 per-tensor MoE with BF16 input |
| `fmoe_g1u1_tkw1` | `aiter.ops.moe_op` | Per-token weight quantization variant |

**MXFP4 MoE kernels** (gfx950/MI355X only): The `_moe_mxfp4_sort_kernel` was optimized in March 2026 (PR #2414) with 30-52% speedup for prefill. MXFP4 W4A4 MoE is supported via CK-Tile dispatch but requires gfx950 hardware.

**`fused_moe_dp_share_expert`** is notable -- it handles data-parallel shared expert routing for DeepSeek, partitioning tokens across DP ranks with FP4/FP8/INT8 support.

### 4. MLA Kernels

**Known MLA kernels in AITER:**

| Kernel | Location | Purpose |
|--------|----------|---------|
| `mla_decode_fwd` | `aiter.mla` | High-level decode wrapper (8 required + 3 optional params) |
| `mla_stage1_asm_fwd` | `aiter.ops.mla` (C++ compiled) | Assembly stage 1 decode kernel |
| `_fwd_kernel_stage2_asm` | `aiter.mla` (Triton JIT) | Triton reduction kernel for stage 2 |
| `mla_prefill_fwd` | `aiter.mla` | Prefill with CK/ASM auto-dispatch |
| `mla_prefill_ps_fwd` | `aiter.mla` | Parallel-sequence prefill with causal masking |
| `mla_prefill_reduce` | `aiter.mla` | Reduction for prefill partials (Triton or PyTorch) |
| `mla_prefill_reduce_triton` | `aiter.mla` | Triton-specific prefill reduction |

**`mla_decode_fwd` signature:**
```python
def mla_decode_fwd(
    q,                    # [batch_size, num_heads, kv_lora_rank + qk_rope_dim]
    kv_buffer,            # [num_pages, page_size, num_kv_heads, qk_head_dim]
    o,                    # [batch_size, num_heads, kv_lora_rank]
    qo_indptr,            # [batch_size + 1]
    kv_indptr,            # [batch_size + 1]
    kv_indices,           # [kv_indptr[-1]]
    kv_last_page_lens,    # [batch_size]
    max_seqlen_q,         # int
    sm_scale=None,        # float, default 1.0/sqrt(qk_head_dim)
    logit_cap=0.0,        # float, under development
    num_kv_splits=None,   # int, auto-determined
)
```

**Key finding:** `mla_prefill_ps_fwd` is a parallel-sequence variant not documented in the official API. It modifies output in-place and supports causal masking for parallel sequence processing.

**March 2026 addition:** PR #2378 added **LSE-aware kernel dispatch** for MLA attention operations, enabling log-sum-exp aware routing between kernels.

**Performance:** MLA decode assembly kernel provides up to **17x decode speedup** and 1.2-1.6x end-to-end speedup. vLLM exposes this via `ROCM_AITER_MLA` backend.

### Summary: What Might Be Faster Than Our Current Approach

| Kernel | When Faster | Constraint |
|--------|-------------|------------|
| `fmoe_fp8_blockscale_g1u1` | FP8 block-quantized MoE (DeepSeek) | 3x over non-block-scaled FP8; requires (128,128) block shape |
| `asm_moe` | Any MoE on MI300X/MI355X | Best overall; auto-selects quant path |
| `fused_moe()` top-level API | General use | Auto-dispatches to best kernel via CSV tuning |
| `mla_decode_fwd` | MLA decode (DeepSeek V3/R1) | 17x decode speedup; use `ROCM_AITER_MLA` backend |
| `mla_prefill_ps_fwd` | Parallel-sequence MLA prefill | Undocumented; handles causal masking in-place |
| MXFP4 MoE (CK-Tile) | W4A4 MoE on MI355X | gfx950 only; 30-52% faster after March 2026 optimization |

**Package note:** AITER has been renamed to `amd-aiter` in recent vLLM releases. The Python import remains `import aiter`.

**Key limitation from our existing skills:** The `aiter-kernel-parameter-semantics` and `amd-moe-mxfp4-optimization` skills note that the Python dispatch overhead is ~20-25us per torch op, and top competition entries bypass library APIs entirely. The `fused_moe()` API is at its parameter-tuning ceiling (~155us vs leader 145us). Further gains require custom CK/ASM kernels below the Python API layer.
